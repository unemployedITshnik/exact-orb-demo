# exact-orb — негативные сценарии и corner cases построения карты

**Статус:** рабочий документ  
**Версия:** 1.1  
**Дата:** 2026-09-04  
**Область:** MVP-flow построения базовой натальной карты или космограммы через форму.

Документ описывает поведение системы при обрыве клиентского соединения, отказах application-слоя, ошибках разрешения входных данных, ошибках расчёта, проблемах сохранения и чтения состояния, истечении сессии, конкурентных запросах и изменении данных во время интерпретации.

## Ревизия 1.1 (2026-09-04)

| Что | Почему |
|---|---|
| Добавлены `N11` (отказ хранилища при **чтении**) и `N12` (данные меняются во время интерпретации) | `exact-orb_session_requirements.md` §8.1 и §7.1 |

## 1. Общие контракты и инварианты

### 1.1. Временное состояние попытки построения — отложено

> **Отложено (ADR-0012, замер `build_natal_components.md` §1.4).** `BuildAttempt`, `build_revision`, статусы попытки и reaper зависших попыток **не реализуются в MVP**. Расчёт натальной карты занимает медианно 18.9 мс; машинерия восстановления незавершённой операции защищала бы окно такой длины. Пользователь закрывает вкладку либо до отправки запроса (N1.1 — реагировать не на что), либо после получения ответа.
>
> **Чем заменено:** compare-and-set по `state_version` (ADR-0014). Этим покрываются N6, N10 и все ветки «кто закончил первым». `build_revision` добавлял только возможность отличить «намерение устарело» от «состояние изменилось под тобой» — качество диагностики, не корректность.
>
> **Условие возврата:** расчёт, устойчиво превышающий несколько сотен миллисекунд, либо появление асинхронного build. `calculate_transit` — 0.51 с на окно ±12 месяцев (`session_requirements.md` §13.4) — это условие выполняет.
>
> Раздел сохранён как описание целевой модели: ниже он читается «когда вернёмся», а не «как сейчас».

Для восстановления после закрытия вкладки и защиты от конкурирующих запросов в сессии хранится временное состояние текущей попытки:

```text
BuildAttempt {
    run_id: UUID
    revision: int
    idempotency_key: str | None
    expected_state_version: int
    birth_input: BirthInput
    status: PROCESSING | FAILED | INTERRUPTED
    error_code: str | None
    started_at: datetime
}
```

В сессионном состоянии:

```text
SessionState {
    ...
    current_build: BuildAttempt | None    # отложено
}
```

`BuildAttempt` не является долговременным профилем. Он хранился бы в `SessionStore` с тем же TTL, что и анонимная сессия, и нужен только для управления незавершённой пользовательской операцией.

### 1.2. Состояние успешной карты

```text
SessionState {
    session_id: str
    birth_input: BirthInput
    birth_resolved: ResolvedBirthData
    state_version: int

    base_chart: {
        state_version: int
        spec: ChartSpec
    } | None

    created_at, expires_at, hard_expires_at
}
```

`SessionState` изменяется только после полностью успешного расчёта и подтверждённого сохранения состояния.

`derived_chart` и `active_view` **в MVP отсутствуют**: они нужны транзитам, которых в первом срезе нет (ревизия ADR-0016). Сессия хранит одну карту.

**Ходы диалога — отдельная запись** (`DialogStore`), а не поле состояния. Дописывание хода не выполняет CAS и `state_version` не меняет, поэтому интерпретация не конкурирует с построением карты за версию.

### 1.3. Правило latest accepted build wins

Результат попытки разрешено сохранить в `SessionState`, только если выполняется проверка:

```text
attempt.expected_state_version == actual_state_version
```

Проверка выполняется **внутри** compare-and-set, а не перед ним: `SELECT` с последующим `UPDATE` оставляет окно между чтением и записью, в которое проходит конкурент.

> **Отложено.** Вторая проверка версии 1.0 — `attempt.revision == current_build.revision` — снята вместе с `BuildAttempt` (§1.1). Она отвечала за актуальность пользовательского *намерения*, тогда как CAS защищает *состояние*. Различие проявляется только в диагностике: с ней можно отличить «намерение устарело» от «состояние изменилось под тобой», без неё оба случая дают `Superseded`.

### 1.4. Calculation Cache не является пользовательским состоянием

Даже если расчёт оказался устаревшим для конкретной сессии, полностью корректный `ChartArtifact` можно сохранить в `Calculation Cache`.

Нельзя:

- применять stale-результат к `SessionState`;
- делать stale-карту активной;
- откатывать более новый успешный результат.

### 1.5. Только полный успех меняет профиль

Успешная пользовательская операция состоит из двух частей:

1. получен полностью валидный `ChartArtifact`;
2. `StateDelta` успешно сохранена в `SessionStore`.

Если расчёт прошёл, но состояние не сохранилось, операция считается неуспешной.

### 1.6. Пользовательская неоднозначность и системный отказ — разные outcomes

Недостаточные, некорректные или неоднозначные данные возвращаются как:

```text
InputRequired
```

Техническая недоступность resolver, calculation engine или session storage возвращается как typed system failure и `5xx`.

Техническую ошибку нельзя маскировать под просьбу исправить пользовательский ввод.

# N1. Закрытие вкладки или обрыв соединения с последующим открытием страницы

Сценарий делится на три случая в зависимости от того, успел ли backend принять и завершить запрос.

> **Что из этого есть в MVP.** Построение карты синхронно (ADR-0012): запрос живёт внутри одного HTTP-обмена и занимает медианно 18.9 мс. Состояния `PROCESSING` в хранилище не существует, восстанавливать после reopen нечего — при возврате пользователь либо видит карту (commit прошёл), либо форму с прежним состоянием (не прошёл). Ветки N1.2 и N1.3 ниже описывают целевую модель на случай асинхронного build и включаются вместе с `BuildAttempt` (§1.1).
>
> Единственное, что действует уже сейчас: **закрытие вкладки не удаляет анонимную сессию** — она живёт по TTL (ADR-0009), и при возврате состояние восстанавливается через `RestoreSessionQuery` (N11).

## N1.1. Запрос не успел попасть на backend

### Предусловия

- пользователь заполнил форму;
- успешной карты в сессии может не быть либо может существовать старая карта;
- HTTP-запрос оборвался до приёма API.

### Шаги

1. Пользователь нажимает кнопку построения карты.
2. Frontend начинает отправку `BuildNatalCommand`.
3. Вкладка закрывается или соединение обрывается до того, как API принял команду.
4. Backend не создаёт `BuildAttempt` и не увеличивает `revision`.
5. Пользователь снова открывает страницу.
6. Browser передаёт существующую HttpOnly session cookie, если её TTL ещё не истёк.
7. `ContextService` загружает последнее успешно сохранённое состояние.
8. Если `SessionState` отсутствует, Frontend показывает форму ввода.
9. Если существует старая успешная карта, Frontend показывает её.

### Результат

Backend не восстанавливает ввод, который никогда не получил. Состояние сессии остаётся прежним.

### Инварианты

- `BuildAttempt` не создан;
- `SessionState` не изменён;
- Engine не вызван.

---

## N1.2. Backend принял запрос, расчёт ещё выполняется

### Предусловия

- API принял команду;
- в `SessionStore` создан `BuildAttempt(PROCESSING)`;
- расчёт ещё не завершён.

### Шаги

1. API принимает `BuildNatalCommand`.
2. Application-flow создаёт и сохраняет:

   ```text
   BuildAttempt {
       run_id = A
       revision = N
       status = PROCESSING
   }
   ```

3. `BirthDataResolver` разрешает данные рождения.
4. Запускается получение или расчёт `ChartArtifact`.
5. Пользователь закрывает вкладку либо теряет соединение.
6. HTTP/SSE-соединение прекращается.
7. Выполнение расчёта не должно семантически зависеть от жизни вкладки и по возможности продолжается на backend.
8. Пользователь снова открывает страницу.
9. Cookie восстанавливает ту же анонимную сессию.
10. `ContextService` загружает `current_build.status = PROCESSING`.
11. Frontend показывает состояние «Расчёт выполняется».
12. После успешного завершения backend выполняет обычную проверку актуальности и commit.
13. Frontend получает готовую карту при повторном чтении состояния или новом запросе.

### Альтернативная ветка: зависший PROCESSING

Если текущая реализация не гарантирует продолжение после client disconnect:

1. `PROCESSING`, превышающий установленный timeout, признаётся устаревшим.
2. Статус меняется на `INTERRUPTED` либо попытка удаляется.
3. Frontend предлагает повторить построение.
4. Повторный запрос может получить cache hit, если корректный артефакт всё же был рассчитан.

### Инварианты

- закрытие вкладки само по себе не означает отмену пользовательского intent;
- незавершённая попытка не изменяет `SessionState`;
- stale `PROCESSING` не хранится бессрочно.

---

## N1.3. Расчёт успешно завершился после закрытия вкладки

### Шаги

1. Пользователь закрывает страницу после принятия команды backend.
2. Engine успешно возвращает `ChartArtifact`.
3. Handler проверяет, что `BuildAttempt` всё ещё является актуальным.
4. Проверяется `expected_state_version` внутри compare-and-set.
5. Handler формирует `StateDelta`.
6. `ContextService` атомарно сохраняет профиль.
7. `current_build` очищается.
8. Пользователь позднее открывает страницу.
9. Cookie восстанавливает ту же session.
10. `ContextService` загружает обновлённый `SessionState`.
11. По сохранённому `ChartSpec` строится `calculation_key`.
12. `Calculation Cache` возвращает `ChartArtifact`; при eviction карта пересчитывается.
13. Frontend показывает готовую карту.

### Результат

Успешный расчёт не теряется только потому, что пользователь закрыл вкладку.

# N2. Application layer или Orchestrator недоступен

В MVP Orchestrator находится внутри application, а не является отдельным сетевым сервисом. Поэтому сценарий трактуется как отказ application processing.

### Шаги

1. Frontend отправляет команду построения.
2. API выполняет DTO validation, session resolution и rate-limit check.
3. API передаёт команду application-слою.
4. Orchestrator не может принять или обработать запрос из-за внутреннего отказа.
5. `BuildNatalHandler` не запускается либо use case прекращается до предметных операций.
6. `BirthDataResolver` и Engine не вызываются.
7. `SessionState` не изменяется.
8. Если `BuildAttempt` ещё не был зарегистрирован, `revision` не увеличивается.
9. API возвращает один из typed outcomes:

   ```text
   503 SERVICE_UNAVAILABLE
   ```

   или:

   ```text
   500 INTERNAL_ERROR
   ```

10. Frontend показывает retryable error без внутренних деталей.

### Пользовательское сообщение

```text
Не удалось выполнить запрос. Попробуйте ещё раз.
```

### Инварианты

- расчёт не начинается;
- профиль не мутируется;
- raw exception не отдаётся пользователю.

### Будущее remote-размещение

Если Orchestrator будет вынесен в отдельный сервис, сценарий дополнится:

```text
API → Orchestrator Client → timeout / connection refused → Circuit Breaker → 503
```

# N3. Ошибка на этапе разрешения данных рождения

## N3A. Некорректные, неполные или неоднозначные данные пользователя

### Примеры

- дата `31 февраля`;
- обязательное место отсутствует;
- `place_id` не найден;
- найдено несколько кандидатов места;
- локальное время неоднозначно из-за перевода часов.

### Шаги

1. API принимает `BuildNatalCommand`.
2. Создаётся `BuildAttempt(PROCESSING)`.
3. `BuildNatalHandler` вызывает `BirthDataResolver`.
4. Resolver обнаруживает, что вход нельзя однозначно разрешить.
5. Resolver возвращает единый контракт:

   ```text
   InputRequired {
       issues: [{
           field: "birth.place",
           code: AMBIGUOUS,
           candidates: [...]
       }]
   }
   ```

6. Handler поднимает `InputRequired` в Orchestrator без изменения контракта.
7. Engine и `Calculation Cache` не вызываются.
8. Запись состояния не выполняется: compare-and-set не вызывается.
9. Ранее успешный `SessionState`, если он есть, остаётся неизменным.
10. Текущий `BuildAttempt` завершается или удаляется: ожидания фонового результата нет.
11. API возвращает typed response с полями и кандидатами.
12. Frontend подсвечивает соответствующее поле либо показывает dropdown кандидатов.
13. После исправления данных пользователь отправляет новую команду с новой `revision`.

### Результат

Это штатный outcome пользовательского ввода, а не системная ошибка.

---

## N3B. Техническая недоступность resolver-а

### Примеры

- timeout внешнего геокодера;
- локальный place catalog недоступен;
- отсутствует или повреждена `tzdata`;
- unexpected resolver exception.

### Шаги

1. Build-flow начинается штатно.
2. `BirthDataResolver` вызывает локальную или внешнюю зависимость.
3. Зависимость отвечает ошибкой либо превышает timeout.
4. Resolver возвращает typed infrastructure failure:

   ```text
   ResolutionUnavailable
   ```

5. Ошибка не преобразуется в `InputRequired`.
6. Engine не вызывается.
7. `SessionState` не изменяется.
8. `BuildAttempt.status` меняется на `FAILED`.
9. В `BuildAttempt.error_code` сохраняется безопасный технический код.
10. API возвращает retryable `5xx`.
11. Frontend сообщает о временной недоступности разрешения места или времени.

### Пользовательское сообщение

```text
Не удалось определить данные места или времени. Попробуйте повторить позже.
```

### Инвариант

Пользователь не должен получать рекомендацию «исправьте город», если отказала инфраструктура системы.

# N4. Ошибка Calculation Engine

### Возможные причины

- ошибка Swiss Ephemeris;
- отсутствуют или повреждены файлы эфемерид;
- внутренняя ошибка `calculate_natal()`;
- timeout удалённого Calculation Service;
- нарушение контракта результата.

### Шаги

1. `BirthDataResolver` успешно возвращает `ResolvedBirthData`.
2. `CalculationKeyFactory` строит `calculation_key`.
3. `Calculation Cache` возвращает miss.
4. `ChartArtifactResolver` вызывает `CalculationEnginePort`.
5. Engine начинает расчёт.
6. Возникает typed calculation failure.
7. Частичный либо невалидный результат не записывается в `Calculation Cache`.
8. Запись состояния не выполняется: compare-and-set не вызывается.
9. Текущий успешный `SessionState` остаётся прежним.
10. `BuildAttempt.status` меняется с `PROCESSING` на `FAILED`.
11. В сессии сохраняется безопасный `error_code`.
12. Orchestrator формирует:

   ```text
   CalculationFailed {
       run_id
       retryable: true | false
       error_code
   }
   ```

13. API возвращает typed error.
14. Frontend показывает сообщение и действие «Повторить».
15. Повторная команда создаёт новый build attempt.

### Инварианты

- failure не кэшируется как `ChartArtifact`;
- partial artifact не кэшируется;
- только полностью валидная карта может изменить профиль.

# N5. Ошибка расчёта → закрытие вкладки → повторное открытие

> **Что из этого есть в MVP.** Сохранение `current_build.status = FAILED` вместе с `error_code` и `birth_input` — часть `BuildAttempt` (§1.1) и отложено. При синхронном построении ошибка возвращается в том же ответе, и её показывает клиент; после закрытия вкладки сообщение об ошибке теряется, а старая карта остаётся.
>
> **Инвариант, который действует уже сейчас и является главным в этом сценарии:** неуспешная попытка построения **не изменяет состояние**. Старая рабочая карта переживает любое число неудачных замен, потому что CAS выполняется только после полностью валидного `ChartArtifact` (§1.5).

## N5.1. В сессии уже есть старая успешная карта

### Предусловие

```text
SessionState {
    base_chart = OLD
}
```

### Шаги

1. Пользователь вводит новые данные рождения.
2. Создаётся `BuildAttempt B` с новым `revision`.
3. Resolver или Engine завершается технической ошибкой.
4. Сохраняется:

   ```text
   current_build {
       run_id = B
       status = FAILED
       birth_input = NEW
       error_code = ...
   }
   ```

5. Старый `SessionState` не изменяется.
6. Пользователь закрывает вкладку.
7. Позднее открывает страницу снова.
8. Cookie восстанавливает ту же session.
9. `ContextService.load()` возвращает:

   ```text
   SessionState = OLD successful state
   current_build = FAILED
   ```

10. Frontend показывает старую рабочую карту.
11. Frontend дополнительно показывает уведомление об ошибке нового построения.
12. Форма может быть предварительно заполнена из `current_build.birth_input`.
13. Пользователь выбирает одно из действий:
    - повторить расчёт;
    - изменить данные;
    - оставить старую карту без изменений.

### Пользовательское сообщение

```text
Не удалось построить карту для новых данных. Сохранена предыдущая карта.
```

---

## N5.2. Ранее успешной карты не было

### Состояние после ошибки

```text
SessionState = None
current_build = FAILED
```

### Поведение после reopening

1. Frontend показывает форму.
2. Форма заполняется последним `birth_input`, если он сохранён.
3. Отображается безопасное сообщение об ошибке.
4. Пользователь может повторить либо изменить данные.

# N6. Запрос A → закрытие вкладки → повторное открытие → новые данные B

Это основной concurrency case. Применяется правило `latest accepted build wins`.

> **Что из этого есть в MVP.** Проверка `revision` отложена вместе с `BuildAttempt` (§1.1); правило целиком обеспечивается compare-and-set по `state_version`. Исходы веток не меняются — меняется только то, какая проверка их даёт, и то, что «намерение устарело» и «состояние изменилось под тобой» перестают различаться в диагностике.

## Этап 1. Запуск A

1. Пользователь отправляет данные A.
2. Текущее состояние:

   ```text
   state_version = 5
   ```

3. Создаётся:

   ```text
   BuildAttempt A {
       revision = 10
       expected_state_version = 5
       status = PROCESSING
   }
   ```

4. Начинается расчёт A.
5. Пользователь закрывает вкладку.

## Этап 2. Запуск более нового B

6. Пользователь снова открывает страницу.
7. Cookie восстанавливает session.
8. Frontend видит незавершённый A.
9. Пользователь вводит новые данные B и подтверждает построение.
10. Создаётся:

    ```text
    BuildAttempt B {
        revision = 11
        expected_state_version = 5
        status = PROCESSING
    }
    ```

11. `current_build` теперь указывает на B.

## Ветка 1. A заканчивается первым

12. A возвращает полностью валидный `ChartArtifact`.
13. Artifact A можно сохранить в `Calculation Cache`.
14. Перед мутацией профиля проверяется:

    ```text
    A.revision == current_build.revision
    10 == 11 → false
    ```

15. A получает внутренний outcome `STALE_BUILD`.
16. Compare-and-set для A не выполняется.
17. `SessionState` не изменяется.

## Ветка 2. B заканчивается и становится актуальным

18. B возвращает `ChartArtifact`.
19. Проверяется:

    ```text
    B.revision == current_build.revision
    11 == 11 → true
    ```

    Шаг отложен вместе с `BuildAttempt` (§1.1).

20. Проверяется optimistic lock — **внутри** compare-and-set:

    ```text
    expected_state_version == actual_state_version
    5 == 5 → true
    ```

21. Store присваивает новую версию внутри той же операции:

    ```text
    state_version = 6
    birth_input = B
    birth_resolved = B
    base_chart = B
    ```

22. `ContextService` атомарно сохраняет дельту.
23. `current_build` очищается.
24. Пользователь получает карту B.

## Ветка 3. B заканчивается первым, A — позже

1. B успешно сохраняется как новая карта.
2. A позже завершает вычисление.
3. Artifact A можно сохранить в Calculation Cache.
4. CAS для A отказывает: `expected = 5`, актуальная `6`.
5. Намерение A не совпадает с актуальным состоянием → исход `Superseded`,
   без rollback и без ошибки расчёта.

### Инварианты

- более старый запрос никогда не перезаписывает более новый;
- stale-результат не вызывает rollback;
- stale-результат не считается ошибкой новой пользовательской сессии;
- проверка `revision` (шаг 19) отложена вместе с `BuildAttempt` (§1.1);
  в MVP действует только CAS по `state_version`. Разница — в диагностике:
  без `revision` случаи «намерение устарело» и «состояние изменилось под
  тобой» дают один исход `Superseded`.

# N7. Double click, retry или повторная доставка одного запроса

Этот сценарий отличается от N6: данные и пользовательское намерение не изменились.

### Шаги

1. Две доставки одного намерения читают `state_version = 5`.
2. Обе сохраняют original `expected_state_version = 5` отдельно от
   `StateDelta`; expected не является полем дельты.
3. Детерминированный resolver даёт одинаковый `ResolvedBirthData`, а
   `ChartArtifactResolver` — один `calculation_key`.
4. Обе вызывают CAS с одинаковыми delta и original expected.

```text
обе команды читают state_version = 5
обе резолвят birth_input   → одинаковый ResolvedBirthData (детерминизм)
обе зовут ensure_chart     → одинаковый calculation_key
                           → single-flight в ChartArtifactResolver
                           → один вызов движка, вторая ждёт результат
обе готовят одинаковый StateDelta; original expected = 5

первая:  compare_and_set(expected = 5) → успех, версия 6
вторая:  compare_and_set(expected = 5) → отказ, актуальная 6
```

Расчёт не дублируется: `ChartArtifactResolver._ensure_singleflight` схлопывает одинаковые ключи в один вызов движка. Состояние не мутируется дважды: CAS пропускает ровно одну запись.

`idempotency_key` и `build_revision` в MVP не вводятся
(`build_natal_components.md` §12).

### Исход второй команды — `AlreadyApplied`, а не `Superseded`

`Superseded` означает «результат вытеснен более новым», то есть состояние ушло не туда, куда просил пользователь. При двойном клике оно ушло **ровно туда**. Возврат `Superseded` даёт мигание интерфейса на ровном месте и зашумлённую метрику конкурентности.

При конфликте сравнивается намерение отклонённой операции с актуальным состоянием:

| Ситуация | Сравнение | Исход |
|---|---|---|
| Двойной клик, данные X и X | равны | `AlreadyApplied` |
| A(X) и B(Y), победила B | X ≠ Y | `Superseded` |
| A(X), B(Y), A'(X); победила B | X ≠ Y | `Superseded` |

Стоимость нулевая: `compare_and_set` при конфликте возвращает не только факт отказа, но и актуальное состояние.

```text
async def compare_and_set(...) -> int | VersionConflict(actual: SessionState)
```

Дополнительного чтения не требуется, и сравниваемое состояние взято из той же атомарной операции — гонки между отказом и перечитыванием нет.

`matches_intent` сравнивает `birth_resolved` и `base_chart_spec`, но не
текстовую форму `birth_input`. Классифицирует `VersionConflict` только
`ContextService`: совпадение даёт `AlreadyApplied`, различие —
`Superseded`; скрытого retry или rebase в сервисе нет.

Механизм: `sequence_diagrams/session/005-compare-and-set.puml`.

### Разделение механизмов

```text
state_version + сравнение намерения
```

различает повторную доставку одного запроса (`AlreadyApplied`) и конкуренцию разных намерений (`Superseded`).

# N8. Расчёт успешен, но `SessionStore` недоступен при commit

### Шаги

1. `BirthDataResolver` успешно разрешает данные.
2. Engine возвращает полностью валидный `ChartArtifact`.
3. Artifact записывается в `Calculation Cache`.
4. Handler формирует `StateDelta`.
5. `ContextService` выполняет compare-and-set в `SessionStore`.
6. `SessionStore` поднимает `StateWriteError(error_code)` после timeout,
   unavailable либо storage error.
7. Commit пользовательского состояния не подтверждён.
8. Операция не считается успешной, даже если карта рассчитана.
9. `BuildNatalResponse` с success возвращать нельзя.
10. `ContextService` сохраняет безопасный код и возвращает:

    ```text
    StateCommitFailed(error_code)
    ```

11. API возвращает `500` или `503` в зависимости от класса отказа.
12. Frontend предлагает повторить операцию.
13. При retry `Calculation Cache` вероятнее всего возвращает hit.
14. Engine повторно не вызывается.
15. Система повторяет ту же попытку атомарного commit: та же `StateDelta` и
    тот же original `expected_state_version`.

Неизвестен фактический исход предыдущего commit: запись могла пройти, а мог
потеряться только ответ; могла не пройти вовсе. Но original
`expected_state_version` **известен** и при retry не заменяется свежей
версией. Предварительное перечитывание с последующим rebase запрещено: оно
превратило бы старое намерение в новую запись и позволило бы затереть
конкурентное изменение.

Ветки повторного CAS:

- запись прежде не состоялась и версия прежняя → `Committed`;
- запись состоялась → `VersionConflict(actual)`, затем `AlreadyApplied`
  по тому же `matches_intent`, что в N7;
- между попытками победило другое намерение → `Superseded`;
- write снова не подтверждён → `StateCommitFailed` с `error_code`.

`ContextService` использует только `actual` из атомарного
`VersionConflict`, не делает дополнительного чтения и не повторяет CAS
скрыто. Передача original expected между пользовательскими запросами —
acceptance-требование application-задачи; P1 фиксирует типы и семантику,
P3 — классификацию исходов.

### Инвариант

Успех расчёта не равен успеху пользовательской операции. Пользователь должен получить success только после подтверждённого `Committed` или атомарно доказанного `AlreadyApplied`.

# N9. Session TTL истёк во время расчёта

### Шаги

1. Пользователь начинает построение карты.
2. Запрос принимается в существующей session.
3. Resolver успешно разрешает вход.
4. Engine начинает расчёт.
5. До завершения расчёта TTL сессии истекает.
6. Reaper атомарно удаляет агрегат state+dialog через persistence backend.
7. Engine успешно возвращает `ChartArtifact`.
8. Artifact можно сохранить в `Calculation Cache`.
9. Handler пытается применить результат к прежней session.
10. `ContextService` обнаруживает `session not found` или `session expired`.
11. Для старого результата автоматически не создаётся новая session.
12. `StateDelta` не сохраняется.
13. Операция завершается typed outcome:

    ```text
    SESSION_EXPIRED
    ```

14. При следующем открытии страницы browser получает новую session.
15. Frontend показывает форму заново.

### Инварианты

- старый asynchronous run не создаёт профиль в новой сессии;
- Calculation Cache может сохранить артефакт, но пользовательское состояние не восстанавливается без действующей session;
- пользователь получает явное сообщение об истечении сессии.

# N10. Старый расчёт завершается после нового успешного результата

Этот случай не требует отдельной sequence diagram и включается как альтернативная ветка N6.

### Шаги

1. A запущен раньше B.
2. B завершается первым и успешно становится новым `SessionState` (версия 6).
3. A заканчивается позже.
4. Artifact A можно сохранить в Calculation Cache.
5. `compare_and_set(expected = 5)` для A отказывает: актуальная версия 6.
6. Намерение A сравнивается с актуальным состоянием: `birth_resolved` различаются, значит исход `Superseded`, а не `AlreadyApplied` (N7).
7. A не изменяет состояние.
8. A не откатывает B.
9. Пользователь получает явное «результат отброшен», а не молчаливый успех с неактивной картой.

# N11. Отказ хранилища при чтении состояния

N8 описывает отказ при **записи**. Этот случай — отказ при **чтении**, и он опаснее: «не смог ответить» легко перепутать с «пусто», а цена ошибки несимметрична.

### Предусловия

- В сессии лежит успешно построенная карта.
- Cookie жива, TTL не истёк.

### Шаги

1. Пользователь открывает приложение.
2. Frontend отправляет `RestoreSessionQuery` и HttpOnly cookie; API берёт
   `session_id` только из cookie, не из query/body/path.
3. `ContextService` вызывает required
   `SessionPersistence.touch(session_id, now=now)`.
4. Persistence поднимает `StateReadError(error_code)` после timeout,
   connection refused либо storage error.
5. `ContextService` **не трактует отказ как отсутствие сессии**.
6. Возвращается typed outcome:

   ```text
   StateReadFailed(error_code)
   ```

7. API возвращает `503`.
8. Frontend показывает «сервис временно недоступен, обновите страницу».
9. Локальное состояние клиента не очищается, форма ввода не показывается.

### Почему не «показать пустую форму»

Отвергнутая альтернатива — трактовать отказ чтения как отсутствие сессии:

```text
отказ чтения → пустая форма
             → пользователь строит карту заново
             → хранилище оживает
             → в нём лежала целая карта, которую только что перезаписали
```

Данные были в порядке; потеряли их мы. Обратная ошибка — показать `503` там, где сессии действительно нет, — стоит пользователю одного обновления страницы.

### Три исхода чтения, а не два

| Исход | Что произошло | Ответ |
|---|---|---|
| `SessionSnapshot` | aggregate touch подтверждён | карта и диалог восстановлены |
| `SessionAbsent` | записи нет или TTL истёк | погасить cookie; новая форма только с новым server ID |
| `StateReadFailed` | хранилище не ответило | `503` |

`session_expired` и `session_not_found` пользователю даются **одним исходом и одной формулировкой**; различие сохраняется в метриках. Старый ID не используется для create: transport генерирует свежий и обрабатывает коллизию без чтения или перезаписи существующей записи.

### Инварианты

- отказ чтения никогда не приводит к перезаписи целого состояния;
- `StateReadFailed` не маскируется под `SessionAbsent`;
- после failed required touch не возвращается stale snapshot, даже если
  фасетное чтение до отказа когда-либо успело вернуть данные;
- при недоступности хранилища система отказывает **целиком**, а не работает «без памяти»: полудеградация даёт двойные расчёты и гонки без возможности их обнаружить.

Диаграмма: `sequence_diagrams/session/003-session-store-read-failure.puml`.
Требования: `component_responsibilities/exact-orb_session_requirements.md` §8.1.

# N12. Данные рождения меняются во время интерпретации

Пользователь запросил интерпретацию по карте версии 1, и пока текст стримится, исправил время рождения через форму. Построение новой карты и стрим интерпретации идут одновременно.

### Шаги

1. Пользователь выбирает тему и запускает интерпретацию.
2. `InterpretSelectionHandler` читает состояние: `state_version = 1`.
3. Handler **фиксирует `spec` значением** в момент старта запроса.
4. Начинается стрим ответа.
5. Пользователь исправляет время рождения и нажимает «Построить».
6. `BuildNatalCommand` выполняет расчёт и `compare_and_set(expected = 1)` → успех, версия 2.
7. Стрим интерпретации **не прерывается**.
8. Пользователь получает полный ответ по карте версии 1.
9. Завершённый ход дописывается в `DialogStore` со `state_version_at_answer = 1`.

### Решение: стрим не прерывается

Пользователь получает ответ по той карте, которая была в запросе. Прерывание на середине текста выглядит как поломка, а начатая генерация уже оплачена.

Следствия, каждое из которых обязательно:

1. **Событие `superseded` в контракте стрима не вводится** — ADR-0012 не расширяется.
2. **Пометка версии становится обязательной, а не желательной:** на экране карта версии 2, текст про версию 1. Без пометки это выглядит как ошибка расчёта.
3. **`spec` фиксируется значением на старте запроса.** Если `ensure_natal` перечитает состояние позже, он подхватит новую карту, и ответ окажется химерой: половина текста про одну карту, половина про другую. Это единственный способ получить в этом сценарии по-настоящему неверный результат.

### Пометка версии

Первое SSE-событие `status` несёт:

```text
{ state_version, chart_summary }
```

где `chart_summary` — дата, время и место в человекочитаемом виде. Frontend рисует плашку над сообщением.

**Пометка не поручается модели.** Инструкция «верни параметры карты в начале ответа» ненадёжна: модель может её не выполнить, переформулировать или ошибиться в цифрах, и пользователь увидит это как ошибку данных. Версия — факт транспорта. Дублировать её в тексте допустимо как удобство, но не как источник истины.

### Почему здесь нет конкуренции за запись

`InterpretSelectionCommand` состояние **не пишет**: ход диалога дописывается в `DialogStore` отдельной операцией, `state_version` не затрагивается, CAS не выполняется. Поэтому интерпретация не может ни получить `Superseded`, ни вызвать его у параллельного построения карты. Две одновременные интерпретации тоже не конкурируют — ограничением остаётся сессионный лимит стоимости (ADR-0013).

### Прерывание пользователем

Отдельный случай: пользователь сам нажимает «стоп».

- стрим закрывается событием `cancelled`, а не `error`: это не отказ;
- бюджет — `commit` по фактически потраченному. Иначе кнопка «стоп» становится способом получить генерацию бесплатно;
- частичный текст сохраняется со `status = "partial"`. Иначе после обновления страницы ход исчезнет, и пользователь решит, что сломалось.

`partial` не означает storage truncation. Если сохранённый текст пришлось
обрезать до 8 000 символов, отдельно выставляется `truncated = true`, а
`status` остаётся фактическим статусом генерации. Поэтому корректны и
`complete + truncated`, и `partial + truncated`.

### Две вкладки

Не запрещаются. Любой ответ backend несёт актуальный `state_version`; вкладка видит, что отстала, и выполняет `RestoreSessionQuery`. Дополнительной инфраструктуры не требуется.

### Инварианты

- ответ интерпретации всегда соответствует ровно одной версии состояния;
- версия, по которой отвечено, доступна пользователю и сохранена в ходе диалога;
- изменение данных рождения не отменяет и не портит уже идущий ответ;
- прерванный пользователем ответ сохраняется как `partial`, а не исчезает.

Требования: `component_responsibilities/exact-orb_session_requirements.md` §7.1–7.4.

# 2. Набор sequence diagrams

| Код | Диаграмма | Содержание |
|---|---|---|
| `S1` | Позитивный natal build | Валидное время, cache miss, успешный расчёт и commit |
| `S2` | Позитивная cosmogram | Время неизвестно, дома не считаются, успешный commit |

| `N3` | Resolver outcomes | `InputRequired` против infrastructure failure |

| `N5` | Failed build → reopen | Старая карта переживает неуспешную замену; восстановление ввода отложено |
| `N6` | Concurrent A → B | Latest accepted build wins; stale A отбрасывается |
| `N7` | Duplicate request | Single-flight и CAS: один расчёт, одна мутация, исход `AlreadyApplied` |
| `N8` | State commit failure | Расчёт успешен, `SessionStore` недоступен, операция неуспешна |
| `N9` | Session expires | Artifact рассчитан, но commit в истёкшую session запрещён |

# 4. Ключевые проверяемые свойства

Golden/integration-тесты этих сценариев должны подтверждать:

- неуспешный расчёт никогда не изменяет `SessionState`;
- stale run никогда не перезаписывает более новый build;
- duplicate delivery не создаёт второй расчёт и вторую мутацию и возвращает `AlreadyApplied`, а не `Superseded`;
- success возвращается только после подтверждённого сохранения состояния;
- пользовательская неоднозначность возвращается как `InputRequired`, а infrastructure failure — как `5xx`;
- закрытие вкладки не удаляет анонимную сессию до истечения TTL;
- истёкшая session не восстанавливается старым asynchronous run;
- полностью корректный stale artifact может быть сохранён в Calculation Cache, но не в пользовательском состоянии;
- partial и failed artifacts не попадают в Calculation Cache;
- старое успешное состояние сохраняется при неуспешной попытке его заменить;
- отказ чтения хранилища возвращается как `StateReadFailed` и никогда не приводит к показу пустой формы поверх целых данных;
- ответ интерпретации соответствует ровно одной версии состояния, и эта версия доступна пользователю;
- изменение данных рождения во время стрима не прерывает и не искажает идущий ответ;
- прерванный пользователем ответ сохраняется со `status = "partial"`.
