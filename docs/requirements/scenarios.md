# Сквозные сценарии exact-orb

Статус документа: рабочий, версия 2.0 (2026-08-25).
Заменяет версию 1.0, где все сценарии начинались со свободного текста в чате.

Контекст: вход через форму, карта сразу, затем preset-действия и — в подписке —
свободный вопрос. События потока: `status`, `input_required`, `token`, `done`, `error`.
Компоненты — по `overview.md`.

---

## Сценарий 1. Bootstrap: дата, время и место известны

Форма: `2 сентября 1990`, `14:30`, город выбран из подсказок → `place_id`.

1. **Session Middleware**: cookie отсутствует — заводится анонимная сессия.
2. **AdmissionControl**: access и IP rate limit. Класс операции `calculation`,
   interpretation quota не расходуется.
3. **Build Chart API** → **Orchestrator** → **BuildNatalHandler**.
4. **BirthDataResolver** → **PlaceResolverPort** → `LocalPlaceCatalog`:
   `place_id` → канонический город, `lat 55.7558`, `lon 37.6173`,
   `tz_id = Europe/Moscow`.
5. **Historical TZ**: 02.09.1990 в `Europe/Moscow` — летнее время UTC+4,
   отменённое 30.09.1990. Локальные 14:30 = **10:30 UTC**.
   Наивное «GMT+3» дало бы ошибку в час и сдвинутый асцендент.
6. `ResolvedBirthData` возвращается **в handler**; резолвер в состояние не пишет.
7. **BuildNatalHandler** формирует `ChartSpec` натальной карты
   (`chart_kind = natal`, полный `include`) и вызывает **ChartArtifactResolver**.
8. **KeyFactory**: `(ResolvedBirthData, ChartSpec, CalculationVersion) → key`.
   **Calculation Cache** — промах.
9. **EngineService** → `calculate_natal()`: эфемериды, дома и углы, тела,
   производные точки, управители домов и интерцепции, аспекты → конфигурации → сила.
10. Артефакт кладётся в кэш через `put`.
11. **ProfileService**: `birth_input`, `birth_resolved`, `profile_version = 1`,
    `base_chart = {1, spec}`, `active_view = base`. Handler возвращает `ContextDelta`.
12. **Orchestrator** → `ContextService.save()`; ответ JSON, без SSE.
13. **Chart Renderer** рисует колесо. LLM не вызывалась ни разу.

**Проверяет:** ADR-0005 (исторический пояс), ADR-0009 (сессия), ADR-0012
(построение без LLM), ADR-0017 (ключ и `ChartSpec`).

## Сценарий 2. Время неизвестно — космограмма, один ход

Форма: дата и город заполнены, поле времени пустое.

1. Пустое время — **не ошибка валидации**: это явное `time_unknown = true`.
   Уточняющий вопрос не задаётся (ADR-0008).
2. `ChartSpec` содержит `chart_kind = cosmogram`,
   `include = {positions, aspects, configurations}`.
   Не рассчитываются `houses`, `angles`, `house_rulers`, `interceptions`
   и `strength` — последний требует домов.
3. Полдень используется как техническая опорная точка для долгот и не появляется
   ни в одном поле результата как «время рождения».
4. Если в пределах суток меняется знак Луны или знак либо директность быстрого
   объекта — добавляется `warning`.
5. `NatalChart.chart_kind = "cosmogram"` — вид определяется полем, а не отсутствием
   домов (И-8).
6. UI визуально отличает космограмму от натальной карты и **блокирует переход
   к транзитам** с объяснением (ADR-0016).

**Проверяет:** ADR-0008 (движок знает `chart_kind`, `strength` исключён),
ADR-0007 (пустое время не создаёт `input_required`), И-8.

## Сценарий 3. Выбор места, проверка и подстановка

Форма: пользователь набирает название населённого пункта.

### 3а. Обычный путь — город есть в каталоге

1. **Location Dropdown** с задержкой запрашивает подсказки:
   `GET /places?q=Киров` → **PlaceResolverPort** → `LocalPlaceCatalog`.
   Возвращается ограниченный список кандидатов `[{place_id, label}]`.
   У эндпоинта собственный rate limit: он вызывается на каждое нажатие клавиши.
2. Пользователь выбирает вариант. Кнопка отправки разблокируется только после
   выбора: **Build API принимает `place_id` и не принимает свободный текст**,
   поэтому исход `AMBIGUOUS` на пути построения карты не возникает.
3. **BirthDataResolver** проверяет `place_id` по каталогу. Идентификатор пришёл
   от клиента и доверенным не является — он может устареть после обновления
   каталога, быть скопированным из другого окружения или подделанным.
   Если не разрешается:
    InputRequired { issues: [{ field: "birth_place", code: INVALID }] }
4. Успешный резолв даёт канонический город, `lat`, `lon`, `tz_id`,
   `place_substituted = false`. Дальше — по сценарию 1.

### 3б. Города нет в каталоге — подстановка ближайшего

5. Пользователь не находит свой населённый пункт в подсказках. Форма предлагает
   указать ближайший известный ему город.
6. **Подобрать его система не может:** координат исходного места у неё нет —
   в этом и состояла проблема. Ближайший город называет человек. Формулировка
   в UI должна это отражать, иначе пользователь решит, что система что-то
   вычислила за него.
7. Резолв идёт по выбранному городу, но подстановка фиксируется явно:

ResolvedBirthData {
canonical_place выбранный город
place_substituted true
place_input_text что человек написал изначально
warnings[]
}


   Исходный текст сохраняется в `birth_input`, разрешённое место — в
   `birth_resolved`. Это одна из причин хранить оба представления.

8. **Что подстановка портит.** Тела считаются геоцентрически
   (`FLG_SWIEPH` без `FLG_TOPOCTR`), поэтому положения планет от места
   не зависят вообще. Меняются только дома, Ascendant и MC.

   Порядок величины: 1° долготы — четыре минуты звёздного времени, то есть
   в среднем около градуса смещения Ascendant, а в быстровосходящих знаках
   заметно больше. На широте 55° один градус долготы — примерно 64 км.
   Подстановка города в 30 км сопоставима с обычной неточностью записанного
   времени рождения; подстановка за 300 км двигает куспиды ощутимо.

9. При отклонении больше 0.5° по долготе или широте добавляется `warning`.
   По И-7 он обязан дойти до промпта; рецепт смягчает утверждения о куспидах
   и углах. Меньшее отклонение остаётся только в метаданных.

10. Смягчение выражается **флагом в `Evidence`**, а не третьим набором `forbids`.
    Запрет упоминать дома — это про космограмму; здесь дома есть, просто
    посчитаны по подставленному месту. Отдельный набор запретов удвоил бы
    матрицу композиции рецептов, которую мы специально сократили.

### Что остаётся за кадром

Код `AMBIGUOUS` не исчезает из словаря `InputRequired`: его порождает эндпоинт
подсказок, и он вернётся на пути построения вместе со свободным текстом, когда
появится подписка (ADR-0019).

Подстановка — компромисс, продиктованный неполнотой локального каталога.
С появлением `RemoteGeocoder` необходимость в ней сокращается до редких случаев.

**Проверяет:** ADR-0005 (frontend не источник истины, `place_id` проверяется
на сервере, подстановка не молчаливая), ADR-0007 (единый тип `InputRequired`),
И-7 (предупреждение доходит до текста), И-11.

## Сценарий 4. Preset-интерпретация: тема и два фокуса

Пользователь на странице карты нажимает `topic = natal`,
`focus = [career, love]`.

1. **AdmissionControl**: класс `preset_interpretation`, квота расходуется.
2. **CapabilityService** → `CapabilitySet`: в demo preset разрешён.
3. **ActionContractBuilder**: `topic + focus + active_view` → `ContractDraft`.
   Вероятностного шага нет — `IntentService` не вызывается (ADR-0011).
4. **ContractValidator** сверяет черновик с `SessionProfile` → `ResolvedContract`.
5. **Planner** → **ScenarioRegistry**: сценарий `natal`,
   `tools = [natal]`, `topics = [{natal, recipe: natal.focused, mode: full}]`.
   Два фокуса **не** порождают две темы и **не** включают `compact`:
   сжатие определяется количеством техник, а не фокусов.
6. **PolicyService** авторизует план. Пользовательского текста нет,
   `InterpretationQuery` отсутствует.
7. **ToolExecutor** → **Chart Tool** → **ChartArtifactResolver**: попадание в кэш,
   расчёт не повторяется.
8. **InterpretationService** строит ключ кэша интерпретаций
   (`artifact key + recipe version + topic + focus`) — промах.
9. **AdmissionControl** атомарно резервирует бюджет с lease.
10. **DataSelector** — единственное место, где работают фокусы: «карьера» тянет
    X дом и его управителя, MC и аспекты к нему, Сатурн, Солнце; «личная жизнь» —
    VII дом и управителя, Венеру, Луну, Марс и аспекты между ними; плюс общая база.
    Наборы объединяются с дедупликацией. `warnings` переносятся обязательно (И-7).
11. **PromptBuilder** собирает **один** `PromptBundle`; слот под пользовательский
    вопрос присутствует и пуст.
12. **Gateway.complete_stream()**, профиль «интерпретация», потолок `max_tokens`.
    События `token` идут в канал.
13. **OutputGuard** → `done`. Ответ кладётся в кэш интерпретаций,
    **AdmissionControl** коммитит фактический расход.

**Проверяет:** ADR-0003 (один промпт), ADR-0004 (темы против инструментов),
ADR-0013 (класс операции), ADR-0015 (capability), ADR-0017 (два кэша).

## Сценарий 5. Изменение данных рождения и гонка

Пользователь исправляет время в форме на странице карты.

1. `UpdateBirthData` — **явная типизированная команда**, а не побочный эффект
   диалога (И-13).
2. Резолв, новый `ChartSpec`, новый ключ, расчёт.
3. **ProfileService** инкрементирует `profile_version` **compare-and-set**:
   версию присваивает store, иначе два одновременных обновления прочитают 7
   и оба запишут 8.
4. Атомарно обновляются `birth_input`, `birth_resolved`, `base_chart`
   и **сбрасываются производные**: `derived_chart = None`, `active_view = base`.
   Транзит, посчитанный к прежнему наталу, не переносится.
5. Старый кэш не инвалидируется: новые параметры дают другой ключ.

**Гонка.** Запрос A стартовал при версии 7, пользователь успел сделать
изменение B (версия 8), A завершился позже:

6. A не имеет права менять активную карту — инвариант
   `chart.profile_version == profile_version` нарушен.
7. A возвращает клиенту явный `superseded`, а не молчаливый успех с неактивной
   картой: иначе фронт её нарисует.

**Проверяет:** ADR-0014 (явная операция, CAS, `superseded`), ADR-0016 (сброс
производного), И-13.

## Сценарий 6. Транзит как производная карта

Пользователь переключает вид на транзиты и выбирает дату.

1. `SetActiveView` / `BuildDerivedChart` — **отдельная операция состояния**,
   а не побочный эффект интерпретации (ADR-0014).
2. Момент транзита резолвится по `tz_id` **места расчёта** на дату транзита,
   не по поясу пользователя (ADR-0005).
3. `ChartSpec` транзита содержит момент, место и параметры окна.
   Кэш натала переиспользуется: `calculate_transit()` принимает готовый
   `NatalChart` (ADR-0001).
4. `derived_chart = {profile_version, spec}`, `active_view = derived`.
   Базовая карта не мутирует.
5. Дату транзита можно менять многократно без пересчёта натала.

**Если базовая карта — космограмма**, переход недоступен: `calculate_transit()`
требует `natal.cusps` и `natal.angles`, которых у космограммы нет. UI блокирует
действие с объяснением, а не показывает ошибку расчёта.

**Проверяет:** ADR-0016 (базовое и производное), ADR-0008 (ограничение),
ADR-0017 (переиспользование кэша).

## Сценарий 7. Свободный вопрос (подписка)

«Что в моей карте говорит о том, почему я постоянно меняю работу?»

1. **CapabilityService**: `freeform_interpretation` разрешён тарифом.
   В demo на этом шаге операция отклоняется.
2. **InputGuard**: нормализация, **лимит длины**, детект инъекций
   → `GuardVerdict` как отдельный объект.
3. **AdmissionControl**: abuse-сигналы плюс квота.
4. **IntentService** → `UnderstandingResult`:
   `contract_fields = {topic: natal, focus: career}`,
   `interpretation_query = {normalized_text, language}`.
   Данные рождения из текста **не извлекаются** (ADR-0019) — источник один:
   `SessionProfile`.
5. **ContractValidator** → `ResolvedContract`. **Planner** строит план.
   Ни тот, ни другой пользовательского текста не видят (И-1).
6. **PolicyService** → `AuthorizedInterpretationQuery`.
7. **PromptBuilder** кладёт вопрос в **отдельный делимитированный слот**
   рядом с trusted system recipe. Нормализация не делает текст доверенным:
   защиту дают отсутствие инструментов у модели, отсутствие доступа к состоянию
   и изоляция слота.
8. Вход недоверен — значит недоверен и выход: **OutputGuard** обязателен.
9. Кэш интерпретаций для free-form включает `session_id` и хэш вопроса,
   запись живёт не дольше сессии. Попадание случается при двойном клике
   или refresh — это защита от повторного списания, не экономия.

**Проверяет:** ADR-0018 (переформулированный И-1, `GuardVerdict` отдельно),
ADR-0015 (capability), ADR-0013 (admission), ADR-0017 (ключ free-form).

## Сценарий 8. В свободном тексте упомянута дата рождения

«Построй карту мужу, 3 марта 1988, Киров».

1. Rule-based **детектор** замечает дату и топоним. Резолв не выполняется —
   распознавания данных рождения в MVP нет (ADR-0019).
2. Возвращается явный отказ через существующий тип:
InputRequired { issues: [{
field: "subject",
code: UNSUPPORTED,
constraints: "изменение данных рождения — через форму"
}] }
3. Молчаливый ответ про сохранённую карту недопустим: пользователь получил бы
   осмысленный текст и решил, что система его поняла. Это тихая подмена субъекта,
   а не мягкая деградация.

**Проверяет:** ADR-0019 (граница отсрочки честная, а не скрытая),
И-11 (тот же тип для другой категории).

## Сценарий 9. Ошибка после начала потока

1. Ход развивается как сценарий 4 до шага 12.
2. На середине генерации провайдер обрывает соединение или превышает таймаут.
3. Поток открыт и часть `token` отдана — HTTP-код изменить нельзя.
   Ошибка доставляется событием `error` **внутри потока** (И-10).
4. **AdmissionControl** получает `commit` по фактически израсходованному
   либо `cancel`; резервация не остаётся висеть.
5. Финализация по накопленному тексту: частичный ответ и признак неполноты
   пишутся в ходы сессии.
6. **Если процесс погиб между `reserve` и `commit`**, резервацию освобождает
   reaper по истечении lease. Без него краш-луп молча съедает дневной потолок,
   и снаружи это выглядит как «квота кончилась ни с того ни с сего» (ADR-0006).

**Проверяет:** И-10, ADR-0006 (lease), ADR-0013 (жизненный цикл резервации).

## Сценарий 10. Кэш вымыт, карта восстанавливается

Деплой очистил `Calculation Cache`; у пользователя открыта страница
с активным транзитом.

1. `active_view = derived`, `derived_chart.spec` лежит в сессии.
2. **ChartArtifactResolver**: `get` — промах.
3. Ключ выводится заново из `ChartSpec` — **не** берётся из сохранённой ссылки:
   хэш невосстановим, спецификация восстановима.
4. Расчёт повторяется, результат кладётся в кэш. Пользователь видит ту же карту.
5. Если бы сессия хранила только `calculation_key`, транзит был бы утрачен:
   момент и место транзита не входят в профиль и жили только внутри артефакта.

**Проверяет:** ADR-0017 (И-12), ADR-0009 (структура `SessionProfile`).

## Сценарий 11. Истечение сессии

1. TTL истёк, страница карты открыта.
2. Любой запрос возвращает `session_expired`; фронт возвращается к bootstrap.
3. Восстановление карты из данных клиента **запрещено**: frontend не является
   источником истины для расчётных параметров.
4. После истечения TTL или удаления cookie данные рождения не существуют нигде:
   persistent History нет, логи не содержат персональных данных.

**Проверяет:** ADR-0009 (TTL и отказ от восстановления с клиента),
ADR-0010 (И-14), ADR-0005 (frontend не источник истины).
