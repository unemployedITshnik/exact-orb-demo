# exact-orb — блок РЕЗОЛВ: контракт, взаимодействие, сценарии

**Статус:** рабочий документ; описанное поведение реализовано в `birth/`
и покрыто тест-паком
**Дата:** 2026-08-27, синхронизирован с кодом после ревью
**Область:** путь `BuildNatalHandler → BirthDataResolver → PlaceCatalog →
resolve_historical_tz → BirthDataResolver → BuildNatalHandler`.
**Основание:** ADR-0005, 0007, 0008, 0019; инварианты И-5, И-7, И-11.
**Родительский документ:** `exact-orb_build_natal_components.md` §5.

---

## 1. Входной контракт от `BuildNatalHandler`

```text
BirthInput {
    birth_date: date            обязательно
    birth_time: time | None     необязательно; None = time_unknown
    place_id:   str             обязательно; НЕДОВЕРЕННЫЙ
}
```

Три поля. Больше системе для расчёта ничего не нужно, и всё, что нужно,
человек выбрал явно.

```text
class BirthDataResolver:
    def __init__(
        self,
        *,
        places:         PlaceCatalog,
        min_birth_date: date,       из конфигурации, см. §3.3
        max_birth_date: date,
    ) -> None: ...

    async def resolve(
        self,
        birth_input: BirthInput,
    ) -> ResolvedBirthData | InputRequired | ResolutionUnavailable: ...
```

**`place_substituted` отменяется как атрибут** — см. §3.5. Механизм
подстановки ближайшего города остаётся, но целиком на клиенте: это
подсказывающий текст в форме, а не поле контракта.

**Допустимый диапазон дат — параметр конструктора, а не константа модуля.**
Он определяется составом `ephe/*.se1`, то есть конфигурацией развёртывания,
и резолвер не должен знать, откуда взялись границы. Для дат рождения
верхняя граница дополнительно схлопывается с текущим днём:
`effective_max = min(max_birth_date, today_provider())`. Обоснование
значений — §3.3.

**Чего на входе нет.** Координат, `tz_id`, свободного текста места,
пользовательского текста вообще. Резолвер вызывается **до** planning
и calculation (ADR-0005) и является детерминированным компонентом.

## 2. Взаимодействие внутри блока

### 2.1. Алгоритм

```text
1.  Дешёвые проверки без I/O:
       effective_max = min(max_birth_date, today_provider())
       birth_date в [min_birth_date, effective_max]?
    → накопить issues, НЕ возвращать сразу

2.  places.lookup(place_id)
       Resolved  → продолжаем
       NotFound  → issue { birth.place, INVALID }
       отказ     → ResolutionUnavailable, немедленный выход

3.  Если issues непусты → InputRequired(issues)

4.  Сборка локального момента:
       time_unknown = (birth_time is None)
       local_datetime = birth_date + (birth_time или местный полдень)

5.  resolve_historical_tz(local_datetime, tz_id)
       UnknownTimezoneError → ResolutionUnavailable

5a. TzNonexistent И NOT local_date_exists(birth_date, tz_id)
       → InputRequired { birth.date, INVALID }
       проверка идёт ДО разбора time_unknown и действует в обеих ветках:
       если дня не существовало, виновата дата, а не время (§5.3)

5b. TzOk          → продолжаем
    TzNonexistent → §5.3: зависит от time_unknown
    TzAmbiguous   → §5.3: зависит от time_unknown

6.  Сборка ResolvedBirthData + warnings
```

### 2.2. Почему issues накапливаются, а не возвращается первая

`InputRequired.issues` — список (ADR-0007), и это не случайность формы записи.
Если неверны и дата, и место, пользователь должен увидеть подсветку обоих
полей за один заход, а не исправлять их по очереди двумя запросами.

Границу накопления задаёт зависимость данных: время резолвится только после
места, потому что нужен `tz_id`. Поэтому issues собираются в два этапа —
дата и место вместе, время после них.

### 2.3. Порядок владения

| Компонент | Владеет |
|---|---|
| `PlaceCatalog` | «где»: координаты и `tz_id` по `place_id` |
| `resolve_historical_tz` | «когда»: локальное время + `tz_id` → UTC |
| `BirthDataResolver` | склейкой, конвенцией полудня, переводом исходов в `InputRequired` |

Конвенция полудня (ADR-0008) живёт в резолвере, а не во временной функции:
вторая половина того же решения — `time_unknown = true` — устанавливается
здесь же, и разносить половины по модулям нельзя.

## 3. Где проходит граница валидации

Три уровня. Сценарии из §6 распределяются по ним, и это распределение —
главный результат разбора.

### 3.1. Уровень схемы — API, до оркестратора

Отсутствие обязательного поля и синтаксически невозможное значение
(`1990-02-31`, `25:70`) не могут быть представлены в типах `date` и `time`:
запрос не парсится. Резолвер такого входа не видит **никогда**.

ADR-0007 относит это к «валидация формы: обязательность и формат проверяются
до расчёта».

**Но наружу это обязано уйти тем же контрактом.** Если один класс ошибок
приходит как `InputRequired{issues[]}`, а другой — как ошибка схемы pydantic,
у клиента появляются два пути отрисовки одной и той же подсветки поля.
Поэтому API-слой переводит ошибки валидации схемы в `InputRequired`
с кодами `MISSING` и `INVALID`.

### 3.2. Уровень резолва — требует знания, которого нет у формы

Три случая, и каждый требует данных, которых на клиенте нет:

```text
place_id не найден в каталоге       → нужен каталог
локальное время не существует       → нужны правила IANA на эту дату
локальное время удвоено             → то же
```

### 3.3. Уровень допустимого диапазона дат

Замер на текущем составе `ephe/`:

```text
1750  RuntimeError: could not calculate body 'chiron' …
1799  RuntimeError: could not calculate body 'chiron' …
1800  OK, без предупреждений
1900  OK, без предупреждений
2026  OK, без предупреждений
2399  OK, без предупреждений
2400  OK, но ВСЁ посчитано по Moshier — 12 предупреждений
2500  RuntimeError: could not calculate body 'chiron' …
```

Поведение на границе **несогласованное**: часть тел молча деградирует
на Moshier с меньшей точностью, Хирон поднимает исключение. Ни то, ни другое
не является внятным ответом «дата вне поддерживаемого диапазона».

Отсюда: диапазон проверяется **до** расчёта, в резолвере, и выражается как
`InputRequired` с кодом `UNSUPPORTED` — код из ADR-0007, который для этого
и предназначен:

```text
InputRequired {
    issues: [{
        field: "birth.date",
        code: UNSUPPORTED,
        constraints: { min: "1800-01-01", max: "2399-12-31" }
    }]
}
```

Для текущего набора файлов границы — `1800-01-01` и `2399-12-31`.
Они конфигурационные: добавление `sepl_12.se1` и соседних расширит диапазон
без правки кода.

### 3.4. Подстановка ближайшего города — не контракт, а текст в форме

ADR-0005 вводит `place_substituted` и требует `warning` «при отклонении
больше 0.5° по долготе или широте». Это не работает, и по двум независимым
причинам сразу.

**Флаг неоткуда взять.** Человек, не нашедший свой посёлок в подсказках,
выбирает районный центр. Со стороны backend это неотличимо от выбора своего
города: пришёл валидный `place_id`. Чтобы флаг появился, форма должна была бы
отследить состояние «человеку показали пустой список, и он выбрал другое» —
лишняя UI-механика ради поля, которое ниже никем не используется.

**Порог невычислим.** Отклонение считается от координат исходного места,
которых у системы нет — в этом и состояла причина подстановки. Круг
замкнулся: чтобы предупредить о неточности, нужно знать величину,
которая недоступна именно потому, что место неизвестно.

Остаётся то, что реально работает: **строка в форме** — «не нашли свой
населённый пункт? выберите ближайший известный вам город». Ручной ввод
названия при этом по-прежнему запрещён (ADR-0005): свободный текст
Build API не принимает.

Следствия:

* `place_substituted` и `place_input_text` убираются из `BirthInput`
  и `ResolvedBirthData`;
* ADR-0005 требует ревизии в части «Подстановка ближайшего города»:
  решение остаётся, атрибуты и порог отменяются;
* закрывается открытый вопрос №2 родительского документа — он спрашивал,
  где считается порог 0.5°. Ответ: нигде, потому что не из чего.

Отдельная выгода: `place_input_text` не попадёт в `ResolvedBirthData`,
а значит и в `calculation_key` — см. §7.2, где это оказывается важнее,
чем кажется.

---

### 3.5. «Города нет в списке» и «place_id не резолвится» — разные события

Их легко перепутать, а реагировать надо противоположно.

```text
Человек не нашёл свой город в подсказках
    → эндпоинт подсказок вернул пустой список
    → форма показывает «выберите ближайший город»
    → Build API этого НЕ ВИДИТ: кнопка отправки заблокирована
      до выбора из списка

place_id пришёл, но не резолвится
    → идентификатор устарел или подделан
    → InputRequired { birth.place, INVALID }
    → «выберите ближайший» здесь бессмысленно:
      город-то в списке был
```

Первое — контракт эндпоинта подсказок и текст в UI. Второе — контракт
резолвера. Совет «выберите ближайший населённый пункт» относится только
к первому: если `place_id` не разрешился, человек уже выбирал из списка,
и предлагать ему выбрать снова из того же списка — не помощь.

Практический вывод для UI: пустой ответ подсказок — не ошибка ввода,
а точка, где показывается подсказывающий текст.

## 4. Локальное время и UTC: где проходит граница

Вопрос «может, сразу всё переводить в UTC и работать только с ним» —
наполовину уже так и есть, и вторая половина объясняет, почему не до конца.

### 4.1. Ниже резолвера локального времени нет

```text
BirthInput.birth_date/birth_time    локальное — вход и отображение
        ↓ BirthDataResolver
ResolvedBirthData.utc_datetime      UTC — всё, что ниже
        ↓
ChartSpec, calculation_key, EngineService, calculate_natal
```

Это стоит зафиксировать как инвариант блока: **ни один компонент ниже
резолвера не получает локального времени и не выполняет преобразований
часовых поясов.** Проверяется тестом на сигнатуры: `utc_datetime` всегда
tz-aware в UTC, и `calculate_natal` его таким и требует.

Выгода конкретная: правила часовых поясов применяются ровно один раз,
в одном месте, и ошибиться в них можно только там.

### 4.2. Почему локальное всё-таки хранится

Соблазн выбросить `birth_date`/`birth_time` и оставить только `utc_datetime`
разбивается о календарь:

```text
Москва, 2 сентября 1990, 00:30   →   1 сентября 1990, 20:30 UTC
```

Человек родился второго. В паспорте второе. Форма редактирования, собранная
из UTC, покажет первое. Это не теоретическая придирка, а гарантированное
обращение в поддержку от каждого, кто родился между полуночью и рассветом.

Поэтому ADR-0009 и хранит оба представления: `birth_input` — то, что
человек ввёл и увидит снова; `birth_resolved` — то, по чему посчитано.
Второе выводится из первого, обратно — нет.

### 4.3. `tz_id` остаётся и после перевода

`utc_offset_seconds` уже применён, и для натального расчёта `tz_id` больше
не нужен. Хранится он по трём другим причинам: показать человеку, по какому
поясу посчитано; пересчитать при обновлении `tzdata`, не спрашивая заново;
и потому что момент транзита по ADR-0005 резолвится «по `tz_id` **места
расчёта**» — то есть поле работает за пределами натала.

В `calculation_key` он при этом **не входит** — §7.2.

## 5. Найденные пробелы

### 5.1. Ошибка в алгоритме `resolve_historical_tz`

В `exact-orb_build_natal_components.md` §5.2 порядок проверок был записан
неверно: сначала удвоенное время, потом несуществующее. **Так нельзя.**

По PEP 495 для **несуществующего** времени `fold=0` и `fold=1` тоже дают
разные `utcoffset()` — ровно как для удвоенного. Проверка «смещения
различаются» ловит оба случая и классифицирует несуществующее время
как удвоенное.

Проверено:

```text
Москва 2011-03-27 02:30   старый порядок → AMBIGUOUS (неверно)
                          новый порядок  → NONEXISTENT (верно)
```

Правильный порядок — несуществующее **первым**, через round-trip:

```python
tz = ZoneInfo(tz_id)
dt = local_datetime.replace(tzinfo=tz)

# 1. несуществующее
back = dt.astimezone(timezone.utc).astimezone(tz).replace(tzinfo=None)
if back != local_datetime:
    return TzNonexistent(local_datetime, tz_id, normalized=back)

# 2. удвоенное
o0 = dt.replace(fold=0).utcoffset()
o1 = dt.replace(fold=1).utcoffset()
if o0 != o1:
    return TzAmbiguous(
        local_datetime=local_datetime,
        tz_id=tz_id,
        offsets=(int(o0.total_seconds()), int(o1.total_seconds())),
    )

return TzOk(...)
```

Тест, закрывающий именно эту ошибку: `2011-03-27 02:30 Europe/Moscow`
даёт `TzNonexistent`, а не `TzAmbiguous`.

### 5.2. `AMBIGUOUS` на build-пути всё-таки возникает

ADR-0005 и ADR-0007 утверждают: «исход `AMBIGUOUS` на пути построения карты
не возникает — его порождает эндпоинт подсказок». Это верно **для места**:
форма выбирающая, Build API принимает только `place_id`.

Для **времени** это неверно. Удвоенный час осеннего перехода — ровно
`AMBIGUOUS`, и другого кода для него в ADR-0007 нет:

```text
Москва 2014-10-26 01:30 → два смещения: UTC+4 и UTC+3
```

Здесь `candidates` осмысленны и отличаются от кандидатов места: это два
варианта смещения, между которыми выбирает человек («до перевода стрелок»
или «после»).

Формулировку в обоих ADR стоит сузить до места, иначе она читается как
запрет на корректное поведение.

### 5.3. Аномалия часового пояса: виновато время или дата

**Неизвестное время + дата, на которой подставленный полдень
не существует или удвоен.**

Выглядит выдуманным, но это реальные даты:

```text
Africa/Casablanca  1967-06-03 12:00 → NONEXISTENT (нормализуется в 13:00)
Pacific/Apia       2011-12-30 12:00 → NONEXISTENT (нормализуется в 2011-12-31 12:00)
```

Полный перебор всех зон IANA по точкам переходов TZif за 1900–2030 даёт
семнадцать случаев несуществующего полудня. Они **неоднородны**, и это
определяет поведение.

```text
дата сохраняется, пропущен только час — 12 зон
  Africa/Casablanca 1967-06-03 → 13:00
  America/Havana    1925-07-19 → 12:29

дата не существовала вовсе — 5 зон
  Pacific/Apia       2011-12-30 → 2011-12-31
  Pacific/Fakaofo    2011-12-30 → 2011-12-31
  Pacific/Kiritimati 1994-12-31 → 1995-01-01
  Pacific/Kanton     1994-12-31 → 1995-01-01
  Pacific/Kwajalein  1993-08-21 → 1993-08-22
```

Самоа и Токелау в 2011 году перешли через линию перемены дат, Кирибати
сделало это в 1994-м: **дня не существовало целиком**.

### Случай первый: пропущен час, дата цела

Здесь подставленный полдень — техническая опорная точка, а не утверждение
пользователя. Вернув `InputRequired { birth.time }`, мы попросили бы
человека исправить поле, которое он намеренно оставил пустым и исправить
не может, — и нарушили бы ADR-0008 («вопрос о времени не задаётся»).

```text
time_unknown = false → TzNonexistent / TzAmbiguous → InputRequired
time_unknown = true  → детерминированное разрешение + warning
                       несуществующее → нормализованный момент,
                                        код noon_anchor_adjusted
                       удвоенное      → fold = 0,
                                        код noon_anchor_ambiguous
```

**Два кода, а не один.** Причины разные, и рецепту нужно различать:
сдвиг якоря на минуты внутри тех же суток — мелочь, а неоднозначность
может разнести кандидатов почти на сутки. `Pacific/Kwajalein 1969-09-30`:
смещения `+11:00` и `−12:00`, и Луна между вариантами уходит из Тельца
в Близнецы. Предупреждение несёт оба смещения, чтобы рецепт смягчил
утверждения о Луне; полноценная защита — проверка смены знака Луны
в движке (ADR-0008), она пока не реализована.

Выбор `fold = 0` зафиксирован, чтобы результат не зависел от версии
реализации; конкретный вариант не важен, важна его неизменность.

### Случай второй: дня не существовало — виновата дата

Дата рождения — **ввод пользователя**, а не подставленное системой
значение, и правило «не спрашивать о том, что подставил сам» на неё
не распространяется.

Что было бы, прими мы нормализацию молча:

```text
Самоа, названо 2011-12-30 → посчитано 2011-12-31
  Луна 354.031° Pisces  →  6.115° Aries      ЗНАК МЕНЯЕТСЯ
```

Космограмма состоит из положений, аспектов и конфигураций; Луна в ней —
главное быстрое тело. Мы отдали бы интерпретацию по знаку, которого
у человека нет.

Исход — `InputRequired { birth.date, INVALID }`, **и при неизвестном
времени, и при явно указанном**. «Родилась 30 декабря 2011 года в Апиа
в 14:00» — здесь неверна не величина времени, а сам день: ни одно время
на нём не существовало, и отправлять человека подбирать время бессмысленно.

### Детекция: не «дата сдвинулась»

Наивная проверка `normalized.date() != local_datetime.date()` **неверна**.
Переходы в 23:00 с переводом на 00:00 следующих суток обычны, и тогда
несуществующее локальное время нормализуется за полночь, хотя день
существует целиком:

```text
Africa/Algiers 1920-02-14 23:00 → 1920-02-15 00:00   день существует
Africa/Ceuta   1927-04-09 23:00 → 1927-04-10 00:00   день существует
```

Перебор за 1900–2030 даёт **1135 таких случаев**. Наивное правило
обвинило бы дату в каждом.

Правильный критерий — ненулевая длительность суток:

```python
def local_date_exists(local_date: date, tz_id: str) -> bool:
    start = _utc_of_local_midnight(local_date, tz_id)
    end   = _utc_of_local_midnight(local_date + timedelta(days=1), tz_id)
    return end > start
```

O(1), без перебора часов. Для пропущенного дня обе локальные полуночи
отображаются в один момент UTC.

### Общее правило

**Система не спрашивает пользователя о значении, которое подставила сама,
и не переписывает значение, которое пользователь назвал.** Первая половина
покрывает полдень, вторая — дату.

### 5.4. Устаревший `place_id` у пользователя с уже построенной картой

ADR-0005 отмечает, что `place_id` «может устареть после обновления каталога».
Как сценарий это нигде не разобрано, а бьёт по худшему случаю: у человека
карта уже построена, он открывает форму редактирования, меняет **время**,
отправляет — и получает `InputRequired` на **место**, которого не трогал,
потому что каталог обновился и geonameid слился с другим.

Механически поведение верное. Продуктово — тупик: в форме стоит название
города, который «не существует».

Смягчение стоит дёшево: `SessionProfile.birth_resolved` уже хранит
`canonical_place`, координаты и `tz_id`. При `NotFound` по `place_id`,
который совпадает с сохранённым в профиле, резолвер может использовать
сохранённый резолв, добавив warning. Но это делает резолвер зависимым
от сессии, а ADR-0005 говорит: «в состояние не пишет» и не читает.

Поэтому решение принадлежит handler'у, а не резолверу.

**Статус: зафиксировано и отложено.** В MVP поведение остаётся механически
верным — `InputRequired { birth.place, INVALID }`. Условие возврата:
первое реальное обновление каталога на работающем сервисе, потому что
до него сценарий не воспроизводится вовсе.

## 6. Сценарии для тест-пака

Колонка «ваш №» — нумерация из постановки. `R-*` — сквозные идентификаторы
для тестов.

### 6.1. Успешные

| R | ваш № | Вход | Уровень | Исход |
|---|---|---|---|---|
| R-1 | 3.1 | дата + время + валидный `place_id` | резолв | `ResolvedBirthData`, `time_unknown = false` |
| R-2 | 3.2 | дата + валидный `place_id`, время пусто | резолв | `ResolvedBirthData`, `time_unknown = true`, момент от полудня |
| R-3 | 3.4 | дата + **явные 12:00** + `place_id` | резолв | `ResolvedBirthData`, `time_unknown = **false**` |
| R-4 | — | дата раньше 1970-01-01 | резолв | `ResolvedBirthData` + warning `pre_1970_offset_unverified` |
| R-5 | — | дата в интервале 1991-09-29 … 1992-01-18 | резолв | `ResolvedBirthData`, `utc_offset_seconds = 7200` |

**R-3 — не косметика.** Явные 12:00 и подставленный полдень дают одинаковый
`utc_datetime`, но разный `time_unknown`, а значит разный `chart_kind`
(`natal` против `cosmogram`), разный `include` и **разный `calculation_key`**.
Тест обязан проверять, что две эти карты не схлопываются в одну запись кэша.

### 6.2. Пользовательский ввод — `InputRequired`

| R | ваш № | Вход | Уровень | Исход |
|---|---|---|---|---|
| R-6 | 3.3 | `place_id` отсутствует в каталоге | резолв | `{ birth.place, INVALID }` |
| R-7 | 3.5 | дата календарно невозможна (`1990-02-31`) | схема | `{ birth.date, INVALID }`, резолвер не вызван |
| R-8 | 3.5 | дата в будущем | резолв | `{ birth.date, UNSUPPORTED }` |
| R-9 | 3.5 | дата вне диапазона эфемерид | резолв | `{ birth.date, UNSUPPORTED, constraints }` |
| R-10 | 3.6 | время невозможно (`25:70`) | схема | `{ birth.time, INVALID }`, резолвер не вызван |
| R-11 | 3.6 | локальное время не существует, время **указано** | резолв | `{ birth.time, INVALID }` |
| R-12 | 3.6 | локальное время удвоено, время **указано** | резолв | `{ birth.time, AMBIGUOUS, candidates: два смещения }` |
| R-13 | 3.7-1 | нет `birth_date` | схема | `{ birth.date, MISSING }` |
| R-14 | — | нет `place_id` | схема | `{ birth.place, MISSING }` |
| R-15 | — | неверны дата **и** место одновременно | схема + резолв | **два** issue в одном ответе |

**3.7 сценарий 2 (нет времени) — это R-2, а не ошибка.** Отсутствие времени
штатно и порождает космограмму (ADR-0008). Отдельного негативного сценария
здесь нет, и его отсутствие стоит зафиксировать явно, иначе кто-нибудь
добавит проверку.

### 6.3. Аномалии при неизвестном времени — §5.3

| R | ваш № | Вход | Исход |
|---|---|---|---|
| R-16 | — | время пусто, полдень не существует, **дата цела** (`Africa/Casablanca 1967-06-03`) | `ResolvedBirthData` + warning `noon_anchor_adjusted`, **не** `InputRequired` |
| R-16b | — | то же место и дата, но время указано явно | `InputRequired { birth.time, INVALID }` |
| R-17 | — | время пусто, полдень удвоен (`Pacific/Kwajalein 1969-09-30`) | `ResolvedBirthData` + warning `noon_anchor_ambiguous`, `fold = 0`, `utc_offset_seconds = 39600` |
| R-17b | — | то же, но время указано явно | `InputRequired { birth.time, AMBIGUOUS }` |
| R-21 | — | **дня не существовало**, время пусто (`Pacific/Apia 2011-12-30`) | `InputRequired { birth.date, INVALID }` |
| R-22 | — | то же, но время указано `14:00` | `InputRequired { birth.date, INVALID }` — именно дата, а не время |
| R-23 | — | `Pacific/Kiritimati 1994-12-31`, время пусто | `InputRequired { birth.date, INVALID }` |

Пары `a`/`b` и пара R-16 / R-21 — суть раздела. Первая различает
«назвал человек» и «подставила система», вторая — «часа не было»
и «дня не было». Ни одну из пар нельзя объединять параметризацией:
они утверждают противоположное поведение, и при рефакторинге правило
ломается молча.

### 6.4. Технические отказы

| R | ваш № | Вход | Исход |
|---|---|---|---|
| R-18 | — | каталог недоступен | `ResolutionUnavailable(retryable = true)`, **не** `InputRequired` |
| R-19 | — | `tz_id` из каталога неизвестен `zoneinfo` | `ResolutionUnavailable` — каталог повреждён или `tzdata` устарела |
| R-20 | — | `place_id` устарел после обновления каталога (§5.4) | `{ birth.place, INVALID }` — механически верно, продуктово тупик |

**R-19 — не выдуманный.** Каталог собирается один раз скриптом, `tzdata`
обновляется с зависимостями. Переименование зоны в IANA при неизменном
каталоге даёт ровно это. Отдавать `InputRequired` нельзя: пользователь
не виноват и исправить не может.

### 6.5. Контрольные значения

Все значения ниже прогнаны на `zoneinfo` с текущей `tzdata`.

```text
Europe/Moscow      1990-09-02 14:30 → OK, UTC+4, 10:30 UTC   контроль ADR-0005
Europe/Moscow      1985-06-14 04:25 → OK, UTC+4
Europe/Moscow      1987-01-06 16:25 → OK, UTC+3, 13:25 UTC   зима, декретное
Europe/Moscow      1987-07-15 16:25 → OK, UTC+4, 12:25 UTC   лето, MSD
Europe/Moscow      1991-12-20 16:25 → OK, UTC+2, 14:25 UTC   ← окно UTC+2
Europe/Moscow      2013-12-20 16:25 → OK, UTC+4, 12:25 UTC   ← зима на UTC+4
Europe/Moscow      2016-12-20 16:25 → OK, UTC+3, 13:25 UTC
Europe/Moscow      2011-03-27 02:30 → NONEXISTENT → 03:30    отмена перевода
Europe/Moscow      2014-10-26 01:30 → AMBIGUOUS, UTC+4 / +3  возврат зимнего
Europe/Moscow      1955-03-10 12:00 → OK, UTC+3 + warning pre_1970
Europe/Moscow      1970-01-01 02:00 → OK, UTC+3, warning ЕСТЬ   ← в UTC это 1969
Europe/Moscow      1970-01-01 04:00 → OK, UTC+3, warning НЕТ
Pacific/Apia       2011-12-30 12:00 → NONEXISTENT → 2011-12-31 12:00
Pacific/Kiritimati 1994-12-31 12:00 → NONEXISTENT → 1995-01-01 12:00
Pacific/Apia       2011-12-29 12:00 → OK, UTC-10
Africa/Algiers     1920-02-14 23:00 → NONEXISTENT, но день существует
```

**`pre_1970_offset_unverified` считается по UTC, а не по локальному
времени.** Гарантия IANA сформулирована относительно POSIX epoch,
то есть 1970-01-01 00:00 UTC. Локальные 02:00 первого января 1970 года
в Москве — это 23:00 предыдущего дня по UTC, и предупреждение там нужно.
Окно расхождения равно смещению зоны и случается один раз в её истории.

**Две московские аномалии, ради которых стоит держать эти строки в тестах.**
Наивное «Москва — это UTC+3 зимой и UTC+4 летом» ломается дважды:

```text
1991-09-29 … 1992-01-18   UTC+2   отмена декретного времени
                                  единственное окно UTC+2 в истории Москвы,
                                  111 дней, зима — люди в нём родились

2011-03-27 … 2014-10-25   UTC+4   постоянное «летнее» время
                                  три зимы подряд на UTC+4
```

Границы получены перебором по дням на `zoneinfo`, а не из памяти.

`2016-12-20` даёт **UTC+3, не UTC+4**: с 26 октября 2014 года Москва
вернулась на UTC+3 постоянно. Зимняя дата на UTC+4 — это 2011, 2012
или 2013 год, и именно её стоит держать в тест-паке: она ловит реализацию,
которая считает, что зимой в Москве всегда UTC+3.

## 7. Выходной состав `ResolvedBirthData`

### 7.1. Состав и назначение каждого поля

```text
ResolvedBirthData {
    utc_datetime:       datetime   tz-aware UTC     ← расчёт
    latitude:           float                       ← расчёт
    longitude:          float                       ← расчёт

    tz_id:              str                         ← форма, транзиты
    utc_offset_seconds: int                         ← объяснение
    canonical_place:    str                         ← форма

    time_unknown:       bool                        ← chart_kind
    warnings:           tuple[ResolutionWarning, …] ← промпт (И-7)
}
```

Три группы, и различие между ними существеннее, чем кажется:

| Группа | Поля | Влияет на числа расчёта |
|---|---|---|
| Расчётные | `utc_datetime`, `latitude`, `longitude` | да |
| Восстановительные | `tz_id`, `utc_offset_seconds`, `canonical_place` | нет |
| Пояснительные | `time_unknown`, `warnings` | нет напрямую |

`time_unknown` не меняет ни одного числа, но определяет `chart_kind`,
а тот живёт в `ChartSpec` и попадает в ключ оттуда.

**Смещение хранится в секундах.** До введения стандартного времени зоны
жили по местному солнечному, и смещения не кратны минуте: `Europe/Moscow`
на 1800 год даёт `+02:30:17`, `Europe/Paris` — `+00:09:21`, `Asia/Tokyo`
на 1880 — `+09:18:59`. Проверено перебором: **399 зон из 498** имеют
нецелые минуты на 1800-01-01, а нижняя граница поддерживаемого диапазона
как раз 1800 год.

В минутах поле «применённое смещение» врало бы для большей части старого
диапазона — `utc_datetime` считался бы верно, а соседнее поле нет.
Единица вынесена в имя, чтобы убрать класс ошибок при чтении кода.

### 7.2. Ключ строится из подмножества, а не из всего объекта

**Это то место, где вопрос о выходном составе перестаёт быть косметикой.**

`calculation_key(resolved, spec, version)` при наивной реализации
сериализует `ResolvedBirthData` целиком. Тогда в ключ попадают
`canonical_place` и `warnings`, и появляются два разрушительных эффекта:

```text
GeoNames переименовал «Москва» → «Moscow» при пересборке каталога
    → canonical_place изменился
    → ключ изменился
    → весь кэш этих карт промахивается
    → CalculationVersion при этом НЕ менялся: расчёт тот же самый

обновление tzdata добавило warning pre_1970_offset_unverified
    → warnings изменились
    → та же карта получает вторую запись в кэше
```

Ни один из этих случаев не означает, что числа изменились. Кэш
инвалидируется зря, а `CalculationVersion` — единственный законный
механизм инвалидации — оказывается обойдён сбоку.

Поэтому вводится явная проекция:

```text
CalculationInput {
    utc_datetime: datetime   UTC, секунды, микросекунды отброшены
    latitude:     float      квантование до 6 знаков
    longitude:    float      квантование до 6 знаков
}

ResolvedBirthData.to_calculation_input() -> CalculationInput   чистая функция

calculation_key(CalculationInput, ChartSpec, CalculationVersion) -> str
```

Квантование координат и отбрасывание микросекунд нужны не для красоты:
без них ключ зависит от того, как конкретная реализация сериализует
`float`, а это меняется между версиями и точно изменится при выносе
расчёта в отдельный сервис.

`tz_id` в ключ **не входит**: смещение уже применено, а два разных места
не могут дать одинаковые координаты. Дублировать его — значит связать
ключ с версией `tzdata` через чёрный ход.

**Тест инварианта:** изменение `canonical_place` или `warnings`
при неизменных `utc_datetime`, координатах и спеке даёт **тот же** ключ.

### 7.3. Форматировать под движок — не задача handler'а

Ответ на прямой вопрос: **ни резолвер, ни handler под движок не форматируют.**

```text
BirthDataResolver  → факты резолва, в форме, удобной домену
BuildNatalHandler  → выбирает ChartSpec, ничего не преобразует
EngineService      → ЕДИНСТВЕННОЕ место, знающее сигнатуру calculate_natal
```

`EngineService` уже определён родительским документом §4.4 как «единственное
место в системе, знающее сигнатуру `calculate_natal()`». Если бы handler
раскладывал `ResolvedBirthData` в аргументы движка, это утверждение
перестало бы быть правдой, и добавление параметра техники потребовало бы
правки handler'а — то есть application-слоя.

При этом один формат резолвер обязан гарантировать: **`utc_datetime`
tz-aware и в UTC.** Это не «форматирование под движок», а инвариант типа:
`NatalToolArgs._require_timezone` в существующем коде отвергает naive
datetime, и правильно делает — naive-время здесь означает потерянную
информацию, а не значение по умолчанию.

## 9. Открытые вопросы

1. **Нижняя граница диапазона дат.** Технически 1800 — предел файлов.
   Продуктово осмысленнее 1900: рождения XIX века для сервиса интерпретаций
   означают скорее опечатку, чем реального пользователя. Разница видна
   пользователю сообщением, поэтому решать до реализации.

2. **Верхняя граница.** «Не в будущем» и «не позже 2399» — разные проверки
   с разными кодами. Нужна ли вторая, если первая строже? Нужна: она
   защищает не пользователя, а расчёт транзитов, где дата не ограничена
   сегодняшним днём.

3. **Квантование координат в ключе** (§7.2). Шесть знаков — примерно
   11 сантиметров на экваторе, заведомо избыточно для каталога городов.
   Меньшее число знаков экономнее и устойчивее, но требует решения,
   какая точность места считается значимой для карты.

**Закрыт:** вопрос о пороге `place_substituted` — порог невычислим,
атрибут отменён (§3.4).

**Отложен:** R-20, устаревший `place_id` у пользователя с построенной
картой (§5.4).
