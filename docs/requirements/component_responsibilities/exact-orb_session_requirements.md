# exact-orb — требования к блоку сессии

Документ описывает блок B дорожной карты: пакет `session/`, жизненный цикл
анонимной сессии, операции над её состоянием и хранилища исследовательских
данных.

Это основной контракт блока сессий. Общая граница с application-слоем
кратко отражена в `exact-orb_build_natal_components.md` §3.5 и §6; при
расхождении имён или сигнатур для session-портов нормативен настоящий
документ и действующие ADR.

Согласовано 2026-09-03 и 2026-09-04.

---

## 1. Область

### 1.1. Что входит

- жизненный цикл анонимной сессии: TTL, восстановление, сброс, удаление;
- состав `SessionState` и отдельное хранилище ходов диалога;
- операции над состоянием: построение, изменение данных, восстановление,
  сброс, удаление;
- правила конкурентности за пределами «два одновременных построения»;
- поведение при отказе хранилища на чтении;
- лимиты на построение карты внутри сессии;
- исследовательские хранилища и контур согласия;
- выбор реализации хранилищ и замеры пропускной способности.

### 1.2. Что не входит

- `derived_chart`, `active_view` и команда `SetActiveView` — сужение MVP,
  см. §9;
- свободный чат и связанный с ним сбор сырого текста — контракт зафиксирован
  в §6.3, реализация отложена;
- HTTP-транспорт, cookie middleware и SSE — блок F;
- переход на PostgreSQL и многопроцессный деплой — §12.4;
- репликация и отказоустойчивость хранилища — блок I.

### 1.3. Решения, принятые до этого документа

1. Анонимная сессия с TTL на устойчивой cookie; долговременных профилей нет
   (ADR-0009).
2. Состояние меняют только явные типизированные команды (ADR-0014).
3. Версию присваивает store атомарно при compare-and-set (ADR-0014,
   `build_natal_components.md` §6.1).
4. **`BuildAttempt` не реализуется.** Актуальность результата обеспечивается
   CAS по версии состояния. Обоснование замером — `build_natal_components.md`
   §1.4: полный натал median 18.9 мс, p95 20.3 мс. Условие возврата к решению
   там же: расчёт устойчиво дороже нескольких сотен миллисекунд либо появление
   асинхронного build. См. §13.4 — транзиты это условие выполняют.
5. Расчёт и интерпретация имеют разный transport: request/response и SSE
   (ADR-0012).
6. Ходы диалога умирают вместе с сессией; отдельного persistent-хранилища
   `History` нет (ADR-0010). Настоящий документ **уточняет** это решение
   дважды: диалог хранится отдельной записью с тем же TTL (§3.1), а
   исследовательский корпус без персональных данных живёт бессрочно (§6).
7. `session_id` генерируется доверенным серверным транспортом. Значение из
   cookie используется только как непрозрачный ключ поиска; идентификатор
   нельзя принимать из тела, query/path-параметра или переиспользовать для
   создания сессии после `SessionAbsent`.

## 2. Термины

### 2.1. Compare-and-set (CAS)

CAS — «сравни и запиши»: операция «применить `StateDelta` **только если**
текущая версия равна ожидаемой», выполняемая хранилищем **атомарно**. Между
сравнением, применением дельты, назначением новой версии и записью никто
вклиниться не может.

Зачем она нужна, видно на конкурентной записи:

```text
A читает state_version = 5, готовит новое состояние
B читает state_version = 5, готовит своё

без CAS:  A пишет версию 6
          B пишет версию 6 поверх
          результат A потерян молча — lost update

с CAS:    A: compare_and_set(expected=5) → успех, версия 6
          B: compare_and_set(expected=5) → отказ, актуальная 6
```

Три свойства, без которых это не CAS:

1. **Атомарность обеспечивает хранилище, а не приложение.** Проверка
   `if version == expected: write` в коде приложения — не CAS: между
   проверкой и записью есть окно, в которое попадёт конкурент.
2. **Store получает дельту, а не готового кандидата.** Он применяет её к
   текущему состоянию и присваивает версию `actual + 1` внутри той же
   атомарной операции. Вызывающий новую версию не вычисляет (ADR-0014).
3. **Отказ — это нормальный исход, а не исключение.** Проигравший получает
   типизированный результат с атомарным `actual`; `ContextService`
   классифицирует его без дополнительного чтения.

В терминах баз данных это оптимистическая блокировка: конфликт не
предотвращается блокировкой заранее, а обнаруживается при записи.

CAS — единственный механизм защиты состояния от конкурентных изменений.
`BuildAttempt` со счётчиком попыток не реализуется именно потому, что CAS
покрывает все ветки «кто закончил первым».

Механизм и три исхода записи — `sequence_diagrams/session/005-compare-and-set.puml`.

Отдельный случай — полный reset. `RESET_DELTA` является обычной валидной
дельтой со всеми тремя nullable-полями, равными `None`. Агрегатный
`SessionPersistence.reset(...)` не вводит второй алгоритм: его семантика
тождественна
`sessions.compare_and_set(session_id, expected_state_version, RESET_DELTA,
now=now)`. Агрегат только делегирует; RESET_DELTA-aware реализация фасетного
CAS сама очищает диалог в той же backend-секции или транзакции.

### 2.2. Переименование

Оформляется ревизиями ADR-0009 и ADR-0014.

| Было | Стало |
|---|---|
| `SessionProfile` + `SessionContext` | `SessionState` |
| `profile_version` | `state_version` |
| `ContextDelta` | `StateDelta` |
| `ChartRef.profile_version` | `ChartRef.state_version` |

Смысл контрактов не меняется. Инвариант
`chart.state_version == state.state_version` сохраняется как единственная
проверка валидности ссылки на карту.

## 3. Состояние сессии

```text
SessionState {
    session_id:      str
    birth_input:     BirthInput | None
    birth_resolved:  ResolvedBirthData | None
    state_version:   int
    base_chart:      ChartRef | None
    created_at:      datetime
    expires_at:      datetime
    hard_expires_at: datetime
}

ChartRef {
    state_version: int          # >= 1
    spec:          ChartSpec
}

StateDelta {
    birth_input:     BirthInput | None
    birth_resolved:  ResolvedBirthData | None
    base_chart_spec: ChartSpec | None
}

RESET_DELTA = StateDelta(None, None, None)

DialogTurn {
    turn_id:                 str
    created_at:              datetime
    selection:               Selection
    state_version_at_answer: int
    status:                  Literal["complete", "partial"]
    truncated:               bool = False
    text:                    str
}

Selection {
    topic: str
    focus: str
}

SessionCreated   { state: SessionState }
SessionIdConflict { session_id: str }
VersionConflict { actual: SessionState }
Committed       { state_version: int }
AlreadyApplied  { state_version: int }
Superseded      { actual: SessionState }
SessionAbsent   { reason: Literal["expired", "not_found"] }
StateReadFailed { error_code: str }
StateCommitFailed { error_code: str }
```

Все модели контракта frozen. У `SessionState` тройка `birth_input`,
`birth_resolved`, `base_chart` либо целиком пуста, либо целиком заполнена;
то же правило действует для тройки полей `StateDelta`. `session_id` непуст,
`state_version >= 0`, `ChartRef.state_version >= 1`, а при наличии ссылки
`base_chart.state_version == state_version`. Времена — timezone-aware UTC,
и выполняется `created_at <= expires_at <= hard_expires_at`.

Равенство `hard_expires_at == created_at + 30 дней` — postcondition
`new_session`, а не инвариант чтения persisted-записи: контракт обязан уметь
прочитать историческую валидную запись с более ранним абсолютным сроком.

`apply_delta` и `touched` не переходят из уже истёкшего состояния и в этом
случае поднимают `ExpiredSessionTransitionError` с безопасным
`error_code="SESSION_EXPIRED"`. Продление вычисляется как
`min(hard_expires_at, max(expires_at, now + 7 дней))`: срок не укорачивается
при передаче более раннего `now` и не проходит абсолютный потолок.

`derived_chart` и `active_view` в MVP отсутствуют, см. §9.

`state_version_at_answer` фиксирует, по какой карте сгенерирован ответ. Это
не диагностика: после смены данных рождения диалог остаётся, и без этого поля
старые ответы становятся неотличимы от новых.

### 3.1. Диалог хранится отдельной записью

Внутри `SessionState` он давал два дефекта:

1. **Каждая запись карты переписывала весь диалог.** CAS заменяет запись
   целиком, поэтому изменение трёх полей влекло перезапись до 240 КБ текста,
   к карте отношения не имеющего.
2. **Добавление хода конкурировало с изменением карты за одну версию.** Две
   операции разного смысла боролись за один `state_version`: пользователь
   меняет данные рождения, в этот момент дописывается ход интерпретации —
   одна из них получает конфликт на ровном месте.

Вынесение снимает оба: `SessionState` остаётся маленьким и читается при
каждой операции дёшево, а добавление хода вообще не участвует в CAS.

### 3.2. `DialogStore` — `session/dialog.py`

```text
@runtime_checkable
class DialogStore(Protocol):
    async def append(
        self, session_id: str, turn: DialogTurn, *, now: datetime
    ) -> None | SessionAbsent: ...
    async def read(
        self, session_id: str, *, now: datetime
    ) -> tuple[DialogTurn, ...] | SessionAbsent: ...
    async def clear(
        self, session_id: str, *, now: datetime
    ) -> None | SessionAbsent: ...
```

**Атомарность.** `append` выполняется хранилищем как одна операция вместе с
вытеснением по числу ходов и продлением parent state. Реализация через
чтение, изменение и запись в коде приложения недопустима: две вкладки,
дописывающие ходы одновременно, потеряют один. CAS здесь не нужен —
добавление хода ни с чем не конфликтует по смыслу, нужна только атомарность
самого добавления и write-and-renew обеих записей.

**Пределы диалога**, действующие одновременно:

| Предел | Значение | Что защищает |
|---|---|---|
| Ходов в диалоге | 50 | глубина истории |
| Символов в одном ходе | 8 000 | аномально длинный ответ |
| Символов во всём диалоге | 120 000 | размер записи |

Вытеснение идёт с самых старых ходов, пока не выполнены все три условия.
Ход длиннее 8 000 символов обрезается при `append`, получает
`truncated=True` и не отбрасывается целиком. `status` означает только
завершённость генерации: `partial` используется для прерванного ответа и не
подменяет признак усечения. Поэтому сочетания `complete + truncated` и
`partial + truncated` корректны.

`append` не идемпотентен: повторный `turn_id` сохраняется ещё одним ходом и
остаётся correlation/UI metadata, а не ключом хранения. Поле
`state_version_at_answer` — историческая метка, не CAS-предикат: store не
сверяет его с текущей версией и сохраняет без изменения как меньший, так и
больший marker. Порядок ходов определяется успешными append, а не
`created_at`.

Обоснование чисел: ответ preset-интерпретации ограничен сверху `max_tokens`
(ADR-0013), кириллица занимает два-три символа на токен, поэтому типичный
ход укладывается в три-четыре тысячи символов. Предел 8 000 даёт двукратный
запас. Потолок 120 000 символов — около 240 КБ в UTF-8.

**TTL синхронизирован с сессией.** Фасетные `SessionStore.get` и
`DialogStore.read` ничего не продлевают. `SessionPersistence.touch` —
единственный read-and-renew. Успешные CAS, append и clear являются
write-and-renew: append продлевает parent state и dialog одним deadline;
clear продлевает state, удаляет dialog и не меняет предметные поля или
`state_version`. Расхождение допустимо только в одну сторону: сессия есть,
диалога нет — это пустой диалог, не ошибка. Обратное — осиротевшие
персональные данные, и оно исключается порядком удаления (§5.3).

Private `_DialogRecord.expires_at` в InMemory хранится для изоморфизма с
SQLite и будущего reaper, но не читается публичными операциями и не является
вторым источником liveness: live/missing/expired всегда определяется только
по parent `SessionState`.

### 3.3. `SessionStore` — `session/store.py`

```text
@runtime_checkable
class SessionStore(Protocol):
    async def create(
        self, session_id: str, *, now: datetime
    ) -> SessionCreated | SessionIdConflict: ...
    async def get(
        self, session_id: str, *, now: datetime
    ) -> SessionState | SessionAbsent: ...
    async def compare_and_set(
        self,
        session_id: str,
        expected_state_version: int,
        delta: StateDelta,
        *,
        now: datetime,
    ) -> int | VersionConflict | SessionAbsent: ...
```

`create` сам строит начальное состояние через `new_session`; готовый
`SessionState` с произвольной версией или сроками наружу порта не передаётся.
Идентификатор поступает от доверенного серверного генератора. При коллизии
с любой существующей, в том числе истёкшей, строкой возвращается
`SessionIdConflict`; запись не читается и не перезаписывается, транспорт
генерирует другой свежий идентификатор.

`get` — read-only: учитывает `now` при классификации отсутствующей или
истёкшей записи, но не продлевает TTL. Отсутствие — `SessionAbsent`, а не
`None`; инфраструктурный отказ поднимает типизированный `StateReadError`.

`compare_and_set` принимает `StateDelta`, применяет её и назначает новую
версию внутри атомарной операции. Конфликт возвращает
`VersionConflict(actual=...)`, а отсутствие/истечение — `SessionAbsent`.
Инфраструктурный отказ записи поднимает `StateWriteError`.

Публичная база инфраструктурных ошибок —
`SessionPersistenceError(error_code)`; `StateReadError` и `StateWriteError`
наследуют её и несут безопасный строковый `error_code`. Сырые
`sqlite3.Error`, `OSError` и тексты исключений не пересекают границу порта.
`ContextService` в P3 переводит read-ошибки в
`StateReadFailed(error_code)`, а write-ошибки — в
`StateCommitFailed(error_code)`.

### 3.4. Агрегат persistence — `session/persistence.py`

`SessionStore` и `DialogStore` остаются узкими фасетами для CAS и диалога.
Операции, которым нужна атомарность между обеими записями, принадлежат
агрегату:

```text
SessionSnapshot {
    state:  SessionState
    dialog: tuple[DialogTurn, ...]
}

@runtime_checkable
class SessionPersistence(Protocol):
    sessions: SessionStore
    dialogs:  DialogStore

    async def touch(
        self, session_id: str, *, now: datetime
    ) -> SessionSnapshot | SessionAbsent: ...
    async def reset(
        self, session_id: str, expected_state_version: int, *, now: datetime
    ) -> int | VersionConflict | SessionAbsent: ...
    async def delete(self, session_id: str) -> None: ...
```

`SessionSnapshot` frozen и является persistence-снимком согласованного
состояния и диалога, а не новой доменной сущностью. `touch` — единственный
публичный read-and-renew путь: в одной критической секции продлевает TTL
состояния и существующей записи диалога одним значением и возвращает снимок.
Фасетные `get` и `read` остаются read-only.

`reset` и `delete` также агрегатные. Полный reset только делегирует
фасетному CAS ровно `RESET_DELTA`; RESET_DELTA-aware CAS применяет переход и
очищает диалог в одной backend-секции. `delete` атомарно
удаляет обе записи; порядок двух отдельных вызовов не считается реализацией
контракта.

### 3.5. Правило перехода отделено от записи

Правилом перехода состояния владеют чистые функции `session/state.py`;
отдельный `ProfileService` не вводится. Фактическое применение дельты и
присвоение версии выполняются атомарно в store.

`apply_delta` задаёт детерминированное правило формирования следующего
состояния, но вызывается реализацией store внутри CAS. Это не переносит
владение новой версией вызывающему: наружная сторона передаёт только дельту
и исходную `expected_state_version`.

Разделение проходит по границе тестируемости: правило — чистая функция без
I/O, хранилища и `asyncio`; атомарность инкремента проверяется отдельным
тестом на конкурентность. Слитые в handler, они проверяются только вместе, и
каждый тест правила тянет фикстуру хранилища.

Правило нетривиально: к «обновить три поля и сбросить производные»
добавились инкремент версии при сбросе вместо обнуления (§5.2), два объёма
сброса и вытеснение диалога по трём пределам (§3.2).

## 4. Жизненный цикл

### 4.1. TTL

- **sliding TTL — 7 дней.** Продлевается агрегатным `touch` при согласованном
  чтении и write-and-renew операциями: успешными CAS, append и clear.
- **абсолютный потолок — 30 дней** от `created_at`, независимо от
  активности. По его достижении сессия удаляется, продление невозможно.

Read-and-renew применяется **к обеим записям** — состоянию и диалогу — одной
операцией `SessionPersistence.touch`. `SessionStore.get` и
`DialogStore.read` read-only и сами TTL не меняют. Write-and-renew CAS и
append синхронизируют deadlines существующих state/dialog, а clear продлевает
state и удаляет dialog. Любое продление ограничено `hard_expires_at`.

Каждый port-параметр `now` обязан быть timezone-aware с UTC offset `0`.
Предусловие выражено публичной контрактной функцией `require_utc`, доступной
из `exact_orb.session`. Внутренний wrapper
`exact_orb.session.adapters._time.validate_now` фиксирует port-specific имя
`now` для InMemory и SQLite; adapter-слой не импортирует приватные имена
контрактных модулей. Невалидное время даёт обычный `ValueError` до storage
lookup и до любой мутации. `delete` времени не принимает.

Абсолютный потолок нужен затем, что бесконечно продлеваемое окно
противоречит privacy-модели ADR-0010: данные рождения не должны жить в
хранилище неограниченно долго только потому, что человек раз в неделю
открывает вкладку.

### 4.2. Отсутствие сессии

| Случай | Причина |
|---|---|
| `session_expired` | запись была, TTL истёк или достигнут потолок |
| `session_not_found` | по ключу из cookie записи нет |

Оба случая представлены `SessionAbsent(reason=...)` и пользователю даются
одной формулировкой. Различие сохраняется в метриках и логах. Ни один из них
не разрешает создать новую запись под прежним ключом: transport гасит
непригодную cookie, генерирует свежий серверный `session_id` и вызывает
`SessionStore.create`. Коллизия даёт `SessionIdConflict` и требует ещё одного
свежего идентификатора, а не чтения или перезаписи чужой записи.

Истечение на границе порта логическое: `now >= expires_at` или
`now >= hard_expires_at` немедленно даёт `SessionAbsent("expired")`, и
`ExpiredSessionTransitionError` из чистых функций наружу persistence не
выходит. InMemory P2 физически запись не удаляет; SQLite P4 удалит её reaper.
После purge тот же ID наблюдается как `not_found`, поскольку tombstone не
хранится.

### 4.3. Восстановление при возврате

Операция чтения состояния. Без неё ветка «вернулся, карта уже есть» не
существует, а после первого дня это основной вход в приложение.

```text
RestoreSessionQuery
    → SessionSnapshot
    | SessionAbsent
    | StateReadFailed { error_code: str }
```

`session_id` не является полем query. API получает его только из защищённой
cookie и передаёт `ContextService` как доверенный контекст вызова. Restore
выполняется одним `SessionPersistence.touch`, а не последовательностью
`get` → `read` → два `touch`.

Диаграмма: `sequence_diagrams/session/002-session-restore-on-return.puml`.

## 5. Операции

| Команда | Меняет состояние | Расходует бюджет LLM |
|---|---|---|
| `BuildNatalCommand` | да | нет |
| `UpdateBirthDataCommand` | да | нет |
| `InterpretSelectionCommand` | **нет** | да |
| `RestoreSessionQuery` | нет | нет |
| `ResetSessionCommand` | да | нет |
| `DeleteMyDataCommand` | да | нет |

### 5.1. Интерпретация не пишет состояние

`InterpretSelectionHandler` читает состояние и не сохраняет его. Две
одновременные интерпретации не конкурируют за запись и дополнительной
сериализации не требуют — ограничением остаётся общий сессионный лимит
стоимости (ADR-0013).

Завершённый ход дописывается через `DialogStore.append` — отдельное
хранилище, отдельная операция, `state_version` не затрагивается и CAS не
выполняется. Поэтому интерпретация не может ни получить `Superseded`, ни
вызвать его у параллельного построения карты.

### 5.2. `ResetSessionCommand`

```text
ResetSessionCommand { scope: Literal["dialog", "all"] }
```

- `scope="dialog"` — `DialogStore.clear`; карта, данные рождения и
  `state_version` не меняются, но успешный clear считается активностью и
  может продлить `expires_at` state;
- `scope="all"` — только `SessionPersistence.reset(session_id,
  expected_state_version, now=now)`: агрегат делегирует `RESET_DELTA` тому же
  фасетному CAS, который атомарно меняет state и очищает dialog; сессия и её
  лимиты сохраняются.

**`state_version` инкрементируется, а не сбрасывается в ноль.** Иначе
незавершённая операция с `expected_state_version = 0` пройдёт CAS и запишет
старую карту в только что очищенную сессию. Reset — такая же мутация, как
любая другая.

### 5.3. `DeleteMyDataCommand`

`ContextService` вызывает только агрегатный `SessionPersistence.delete`,
который атомарно удаляет обе записи. После подтверждения transport
**гасит cookie** — `Set-Cookie` с истёкшим сроком. Следующий запрос получает
свежий серверный идентификатор и новую сессию.

Два последовательных вызова `DialogStore.clear` и `SessionStore.delete` не
реализуют этот контракт: при сбое между ними останется частично удалённый
агрегат. In-memory реализация выполняет delete под одним lock, SQLite — в
одной транзакции (§12).

Лимиты сессии сбрасываются, и это допустимо: ADR-0009 фиксирует, что
сессионный лимит не является защитой от злоупотребления, ею остаются
IP-лимит и дневной потолок (ADR-0013).

Формулировка для пользователя обязана быть точной:

> Данные рождения и переписка удалены. Обезличенная статистика качества
> ответов — без даты, времени и места рождения — сохраняется для улучшения
> сервиса.

Диаграмма: `sequence_diagrams/session/004-session-reset-and-delete.puml`.

## 6. Исследовательские хранилища

### 6.1. Разделение

| Хранилище | Содержит ПДн | Срок | Удаляется кнопкой |
|---|---|---|---|
| Session Store | да | TTL | да |
| Dialog Store | да | тот же TTL | да |
| Research Corpus | нет | бессрочно | нечего удалять |
| Raw Query Corpus | да | отдельный | да, по `consent_id` |

### 6.2. `Research Corpus`

```text
ResearchRecord {
    research_id      случайный, не производный ни от чего
    created_at       округлён до часа
    chart_features   категориальные признаки
    selection        topic, focus
    recipe_version, model
    response_text
    quality          rating | regenerate | copy | время чтения
    tokens, cost, latency
}
```

**`chart_features` — только категориальные признаки:** знак и дом каждого
тела, тип аспекта и его категория (`exact` / `working` / `background`),
конфигурации, достоинства, баланс стихий и крестов, `chart_kind`.

**Запрещено хранить:** `birth_input`, `place_id`, координаты, точное время,
`julian_day_ut`, градусы и минуты, `calculation_key`, `session_id`, cookie, IP.

Про `calculation_key` отдельно: он строится из точного UTC-времени и
координат. Хэш не спасает — при известном каталоге мест перебор по минутам
восстанавливает вход за секунды.

Полностью обезличить натальную карту нельзя: она по построению есть функция
от времени и места. Необратимость даёт именно огрубление до знака и дома —
сочетание «Солнце в Деве, 4 дом» описывает миллионы людей. Для улучшения
рецептов интерпретации градусы не нужны, а группировать по категориям
удобнее.

### 6.3. `Raw Query Corpus` — контракт без реализации

В первом срезе свободного чата нет: `selection` — пара enum-значений, сырого
пользовательского текста не существует. Собирать нечего, поэтому реализация
откладывается вместе с freeform-режимом (ADR-0013, класс
`freeform_interpretation`).

Контракт фиксируется сейчас, чтобы согласие не пришлось изобретать задним
числом:

```text
RawQueryRecord {
    record_id
    consent_id           по нему выполняется удаление
    created_at
    query_text           сырой текст пользователя
    selection_resolved   что извлёк intent-слой
    recipe_version, model
}

Consent {
    consent_id
    granted_at
    consent_text_version   на что именно человек согласился
    scope
    revoked_at | None
}
```

Требования к контуру согласия:

1. opt-in, по умолчанию выключено;
2. `consent_text_version` обязателен: без него через полгода нельзя
   установить, на что человек соглашался;
3. отзыв согласия — отдельное действие, не равное удалению сессии;
4. `DeleteMyDataCommand` доходит до `Raw Query Corpus` по `consent_id`;
5. **между `Research Corpus` и `Raw Query Corpus` нет общего
   идентификатора.** Иначе удаление сырого текста оставит связанную с ним
   карту, и обезличенность первого превратится в фикцию.

**Сырой текст остаётся недоверенными данными (ADR-0018).** Когда из корпуса
собирается eval-набор, текст не должен попадать в позицию инструкции.
Инвариант И-1 действует и на исследовательском пути — там его нарушить проще
всего, потому что соблазн подставить реальный запрос прямо в шаблон.

### 6.4. Отношение к ADR-0010

ADR-0010 утверждает, что после истечения сессии персональных данных не
остаётся нигде. `Research Corpus` этому не противоречит — персональных
данных там нет по построению. `Raw Query Corpus` противоречит и допускается
только под явным согласием.

Оформлено **ADR-0023, заменяющим ADR-0010**, а не правкой на месте: изменилось
само решение, а не его границы.

## 7. Конкурентность

### 7.1. Изменение данных во время интерпретации

**Стрим не прерывается.** Пользователь получает ответ по той карте, которая
была в состоянии на момент запроса.

Следствия:

1. Событие `superseded` в контракте стрима **не вводится**; ADR-0012 не
   расширяется.
2. Пометка версии становится обязательной, а не желательной: на экране карта
   версии 2, текст про версию 1.
3. `InterpretSelectionHandler` обязан зафиксировать `spec` **в момент старта
   запроса** и передавать его дальше значением. Если `ensure_natal` перечитает
   состояние позже, он подхватит новую карту и ответ окажется химерой.

### 7.2. Пометка версии ответа

Первое SSE-событие `status` несёт `{ state_version, chart_summary }`, где
`chart_summary` — дата, время и место в человекочитаемом виде. Фронтенд
рисует плашку над сообщением.

**Пометка не поручается модели.** Инструкция «верни параметры карты в начале
ответа» ненадёжна: модель может её не выполнить, переформулировать или
ошибиться в цифрах, и пользователь увидит это как ошибку данных. Версия —
факт транспорта. Дублировать её в тексте допустимо как удобство, но не как
источник истины.

### 7.3. Две вкладки

Не запрещаются. Любой ответ backend несёт актуальный `state_version`; вкладка
видит, что отстала, и выполняет `RestoreSessionQuery`. Дополнительной
инфраструктуры не требуется.

`BroadcastChannel` между вкладками одного origin — необязательное улучшение
фронтенда, к backend-контракту отношения не имеет.

### 7.4. Прерывание пользователем

- стрим закрывается событием `cancelled`, не `error`: это не отказ;
- бюджет — `commit` по фактически потраченному. Иначе кнопка «стоп»
  становится способом получить генерацию бесплатно;
- частичный текст сохраняется со `status="partial"`. Иначе после обновления
  страницы ход исчезнет и пользователь решит, что сломалось.

### 7.5. Повторная доставка одного запроса (N7)

Случай: двойной клик по «Построить карту», повтор после сетевого таймаута,
ретрай прокси. На backend приходят две **идентичные** команды.

```text
обе читают state_version = 5
обе резолвят birth_input       → одинаковый ResolvedBirthData (детерминизм)
обе зовут ensure_chart         → одинаковый calculation_key
                               → single-flight в ChartArtifactResolver
                               → один вызов движка, второй ждёт результат
обе готовят одинаковый StateDelta; обе сохраняют original expected = 5

первая:  compare_and_set(expected=5) → успех, версия 6
вторая:  compare_and_set(expected=5) → отказ, актуальная 6
```

**Дорогая часть уже идемпотентна.** Расчёт не дублируется: single-flight в
`ChartArtifactResolver._ensure_singleflight` схлопывает одинаковые ключи в
один вызов движка. Состояние не мутируется дважды: CAS пропускает ровно одну
запись. `idempotency_key` не защищает ничего, что не защищено уже, — и это
ровно та машинерия, от которой отказался `build_natal_components.md` §1.4.

**Неточным было только имя исхода.** `Superseded` означает «результат
вытеснен более новым», то есть состояние ушло не туда, куда просил
пользователь. При двойном клике оно ушло ровно туда. Отсюда мигание
интерфейса на ровном месте и зашумлённая метрика конкурентности.

**Решение — отдельный исход `AlreadyApplied`.** При конфликте сравнивается
намерение отклонённой операции с актуальным состоянием:

| Ситуация | Сравнение | Исход |
|---|---|---|
| Двойной клик, данные X и X | равны | `AlreadyApplied` |
| A(X) и B(Y), победила B | X ≠ Y | `Superseded` |
| A(X), B(Y), A'(X); победила B | X ≠ Y | `Superseded` |

Стоимость нулевая: `compare_and_set` при конфликте возвращает не только факт
отказа, но и актуальное состояние.

```text
async def compare_and_set(...) -> int | VersionConflict(actual: SessionState)
```

Дополнительного чтения не требуется, и сравниваемое состояние взято из той же
атомарной операции — гонки между отказом и перечитыванием нет. Это изменение
контракта `SessionStore` в `build_natal_components.md` §6.1.

`matches_intent` сравнивает `birth_resolved` и `base_chart_spec`.
`birth_input` намеренно исключён: две текстовые формы ввода, разрешившиеся в
одни данные и одну спецификацию карты, означают одно расчётное намерение.

**Acceptance-семантика P3 фиксирована:** `ContextService` передаёт store
ровно полученные `delta` и original `expected_state_version`; `int` переводит
в `Committed`, `VersionConflict(actual)` — в `AlreadyApplied`, если
`matches_intent(actual, delta)`, иначе в `Superseded(actual)`,
`SessionAbsent` сохраняет как штатный исход, а `StateWriteError` переводит в
`StateCommitFailed` с тем же безопасным `error_code`. Сервис не перечитывает
состояние после конфликта, не подменяет expected свежей версией и не повторяет
CAS автоматически.

Store вправе вернуть `VersionConflict(actual)` с `actual.state_version == 0`,
например если вызывающий передал expected `1` для свежей сессии. Поскольку
`AlreadyApplied.state_version >= 1`, P3 обязан классифицировать этот случай
тотально и не конструировать `AlreadyApplied(0)` автоматически.

## 8. Отказы хранилища

### 8.1. Отказ на чтении

`SessionStore.get` может ответить не «пусто», а «не смог ответить» — timeout,
connection refused, storage error. Эти два ответа легко перепутать, и цена
ошибки несимметрична:

- трактовать отказ как отсутствие сессии → показать пустую форму →
  пользователь строит карту заново → хранилище оживает, а в нём лежала целая
  карта, которую только что перезаписали. Данные были в порядке, потеряли их
  мы;
- отдать `503` → карта не тронута, пользователь ждёт.

**Решение: `StateReadFailed(error_code)` → `503`.** N8 покрывает только отказ при записи;
этот случай добавляется в `build_chart/exact_orb_negative_corner_scenarios.md`.

Диаграмма: `sequence_diagrams/session/003-session-store-read-failure.puml`.

### 8.2. Недоступность хранилища целиком

Система **отказывает целиком**, а не работает «без памяти». Полудеградация
даёт двойные расчёты и гонки без возможности их обнаружить.

Резервная копия задачу не решает: она защищает от потери данных, но не от
недоступности в моменте. Отказоустойчивость — это репликация с автоматическим
переключением, и это блок I.

### 8.3. Повторная попытка после неуспешного commit

Неизвестен **фактический исход commit**, но original
`expected_state_version` известен и не меняется. Повтор отправляет ту же
дельту с тем же original expected; перечитывать состояние и «перебазировать»
операцию на свежую версию запрещено, потому что это превратит старое
намерение в новое и позволит ему затереть конкурентное изменение.

Повтор того же CAS даёт исчерпывающие ветки:

- прошлый commit не состоялся, версия не изменилась — `Committed`;
- прошлый commit состоялся — `VersionConflict(actual)`, затем
  `AlreadyApplied` по `matches_intent`;
- победило другое намерение — `VersionConflict(actual)`, затем
  `Superseded`;
- хранилище снова не подтвердило запись — `StateCommitFailed` с
  `error_code`.

Так N8 использует тот же механизм, что N7. Отдельного blind retry,
повторного чтения между CAS и классификацией и автоматического rebase нет.

### 8.4. Acceptance-набор P3

P3 обязан закрепить одним явным набором следующие десять свойств:

1. Каждый публичный вызов `ContextService` получает `now` один раз и
   передаёт это же значение без повторного чтения часов во все persistence-
   операции данного вызова.
2. Restore/load вызывает ровно один required
   `SessionPersistence.touch(session_id, now=now)` и при успехе возвращает
   полученный `SessionSnapshot`, не собирая снимок отдельными `get`/`read`.
3. `StateReadError(error_code)` из required touch превращается только в
   `StateReadFailed` с тем же `error_code`, никогда не в `SessionAbsent`.
4. Если required touch завершился ошибкой, ранее прочитанный или
   закэшированный snapshot не возвращается как успех: итог только
   `StateReadFailed`.
5. Save вызывает CAS ровно один раз с исходными `delta`, original
   `expected_state_version` и единым `now`; `int` превращается в
   `Committed(state_version)`.
6. `StateWriteError(error_code)` превращается только в
   `StateCommitFailed` с тем же `error_code`, никогда не в
   `VersionConflict`, `Superseded` или `AlreadyApplied`.
7. `VersionConflict(actual)` классифицируется без дополнительного `get`:
   совпадение `birth_resolved + base_chart_spec` даёт
   `AlreadyApplied(actual.state_version)`, различие — `Superseded(actual)`;
   различие только в `birth_input` намерение не меняет.
8. N7: два конкурентных save с одинаковыми delta и original expected дают
   один `Committed` и один `AlreadyApplied`; итоговая версия увеличивается
   ровно на единицу.
9. N8: последовательный retry после неподтверждённого commit повторяет те же
   delta и original expected без load/rebase; если первый commit состоялся,
   retry даёт `AlreadyApplied`, а версия за обе попытки растёт только на
   единицу.
10. `scope="all"` вызывает ровно `SessionPersistence.reset`, а не
    `DialogStore.clear` плюс отдельный CAS. Успех инкрементирует версию и
    очищает диалог атомарно; `VersionConflict` не очищает диалог, а
    `StateWriteError` не может дать наблюдаемое частично сброшенное состояние
    и переводится в `StateCommitFailed(error_code)`.

## 9. Сужение MVP: одна базовая карта

`derived_chart`, `active_view` и команда `SetActiveView` в MVP отсутствуют.

`SetActiveView` нужна не для натала, а для транзитов: по ADR-0016 в сессии
живут две ссылки, и `active_view` определяет не только что рисовать, а **по
какой карте отвечает интерпретация**. Без неё вопрос «расскажи про Марс»
неоднозначен. Отдельной командой она сделана намеренно: ADR-0014 отверг
`ChartStateIntent` как побочный эффект интерпретации, чтобы у мутации
состояния был один владелец.

Транзиты в первый срез не входят, поэтому `active_view` всегда `base`.
Сужение временное и снимается вместе с транзитами; оформляется ревизией
ADR-0016.

## 10. Лимиты

| Лимит | Значение | Назначение |
|---|---|---|
| Построений карты на сессию | 20 в час, 100 в сутки | честный перебор |
| Построений карты на IP | значение — блок F | защита от скрипта |
| Одновременных расчётов | потолок с быстрым `503` | блок F/I |

Обоснование сессионного лимита: живой пользователь строит от одной до пяти
карт — себе, партнёру, ребёнку, родителю. Показ демо компании из десяти
человек укладывается в 20 за час с запасом.

Обоснование необходимости IP-лимита: класс `calculation` по ADR-0013 бюджет
не расходует и доступен всем без подписки, а расчёт CPU-bound и сериализован
процессным `RLock` в `ephemeris_runtime.py` — параллелизма нет by design,
слот один на процесс (§13.2). Скрипт, перебирающий даты, занимает этот слот, и
интерпретации встают вместе с ним: им нужен `ensure_natal`. Стоимость атаки
нулевая — ни LLM, ни капчи, ни авторизации.

Сессионный лимит защитой не является: сессия сбрасывается вместе с cookie
(ADR-0009). Он нужен, чтобы честному пользователю объяснить, почему его
притормозили. Прежняя редакция ADR-0013 упоминала IP-лимит только
на транспорте, без привязки к классу операций; исправлено ревизией
от 2026-09-04.

## 11. Кэш интерпретаций

ADR-0013 называл кэш интерпретаций вторым уровнем защиты бюджета, но
сущности не было ни в одном ADR и ни в одной диаграмме. Ключ и место жизни
зафиксированы ревизией ADR-0013 от 2026-09-04.

**Хранилище глобальное, не сессионное.** В сессии кэш умрёт вместе с TTL и не
спасёт от повторов между сессиями.

**Ключ:** `calculation_key + topic + focus + recipe_version + model`.

`recipe_version` и `model` обязательны: изменение формулировки рецепта или
модели даёт другой ответ, и старый кэш к нему не относится. Логика та же, что
у `CalculationVersion` для расчётного кэша.

## 12. Реализация хранилищ

### 12.1. Требования различаются

| Хранилище | Что нужно | Профиль нагрузки |
|---|---|---|
| `SessionStore` | атомарный CAS, TTL | чтение при каждой операции, запись редко |
| `DialogStore` | атомарный append с вытеснением, TTL | запись после каждой интерпретации |
| `SessionPersistence` | атомарные touch/reset/delete двух записей | lifecycle сессии |
| `CalculationCache` | opaque bytes, TTL | чтение часто, запись при промахе |
| Кэш интерпретаций | ключ → текст, TTL | то же |
| `ResearchCorpus` | группировка и агрегирование, бессрочно | запись всегда, чтение вручную |

Последняя строка отличается принципиально: на вопрос «какие формулировки по
теме отношений получали низкую оценку» нельзя ответить обходом ключей, нужны
индексы и агрегаты.

### 12.2. Три ступени

| Ступень | Где применяется | Что даёт |
|---|---|---|
| `InMemory*` | тесты | быстро, без I/O и файлов |
| `Sqlite*` | демо и стенд | переживает рестарт, ноль зависимостей в деплое |
| `Postgres*` | когда перерастём одну машину | несколько процессов, аналитика параллельно с обслуживанием |

Контракты при переходе не меняются: `SessionStore`, `DialogStore`,
`SessionPersistence` и `CalculationCache` остаются теми же `Protocol`. Это и
есть то, ради чего порт вводился (`build_natal_components.md` §1.3.3).

Поддерживаемая composition root процессной ступени —
`InMemorySessionPersistence()`. Aggregate создаёт один private backend с
одним `asyncio.Lock` и отдаёт стабильные facets `.sessions` и `.dialogs` над
ним; zero-argument создание отдельных facet не поддерживается. Два aggregate
полностью изолированы. Все now-bearing методы InMemory, а в P4 и SQLite,
используют публичный контракт `exact_orb.session.require_utc` через внутренний
wrapper `session/adapters/_time.py`; импорт приватных имён контрактных модулей
для adapter-слоя запрещён.

### 12.3. SQLite закрывает все хранилища

**CAS.** Запись выполняется внутри `BEGIN IMMEDIATE`. Precheck читает
актуальный snapshot и до UPDATE возвращает `SessionAbsent` для
отсутствующей/истёкшей строки либо `VersionConflict(actual)` при несовпадении
версии. Только после совпавшего precheck реализация применяет `StateDelta` и
делает guarded `UPDATE ... WHERE session_id = ? AND state_version = ?`.
Version predicate в UPDATE обязателен: ранний write lock его не заменяет.
После совпавшего precheck `rowcount` обязан быть ровно 1; иное значение —
`StateWriteError`/нарушение persistence-инварианта с rollback, а не normal
conflict и не повод для второго чтения.

**Агрегатные операции.** `touch`, полный `reset` и `delete` выполняются через
`BEGIN IMMEDIATE … COMMIT`. `touch` обновляет обе даты одним значением и
возвращает согласованный `SessionSnapshot`. `reset` только делегирует тому же
guarded CAS с `RESET_DELTA`; RESET_DELTA-aware CAS очищает диалог только при
`rowcount == 1` и в той же транзакции. Неединичный `rowcount` откатывает всю
операцию как `StateWriteError`. `delete` удаляет обе строки атомарно
(§5.3).

**Dialog write-and-renew.** `append` и `clear` каждый выполняются в одной
`BEGIN IMMEDIATE … COMMIT` вместе с продлением parent state. Append сохраняет
dialog с тем же deadline; clear продлевает state и удаляет dialog, не меняя
предметные поля или `state_version`. Частичное изменение state/dialog
недопустимо; liveness определяется только parent state, а persisted dialog
deadline нужен reaper.

**TTL.** Колонка `expires_at`, проверка при чтении и периодическая чистка.
Встроенного TTL у SQLite нет, reaper писать придётся.

**`ResearchCorpus`.** Группировка и агрегаты по миллионам строк — нормальная
для SQLite работа; в режиме WAL читатели не блокируют писателей, поэтому
исследовательский запрос не мешает обслуживанию.

**Ноль зависимостей в деплое:** `sqlite3` входит в стандартную библиотеку.

Три оговорки, которые надо учесть при реализации:

1. **`synchronous=NORMAL` в режиме WAL** переживает падение процесса и
   рестарт — то есть ровно тот случай, ради которого всё затевается, — но при
   потере питания может потерять последние транзакции. `FULL` безопаснее и
   заметно медленнее из-за fsync на каждый коммит. Для демо берём `NORMAL`.
2. **`sqlite3` блокирующий.** Выполнять в том же `ThreadPoolExecutor`, что
   уже используется в `EngineService`, либо добавить `aiosqlite`. Первое не
   добавляет зависимостей и повторяет принятый в проекте приём.
3. **Одна машина, один файл.** Несколько процессов на одном файле в WAL
   работают, но с оговорками; несколько машин — нет.

### 12.4. Когда PostgreSQL

Когда деплой перестанет быть одномашинным либо когда исследовательские
запросы начнут мешать обслуживанию. До этого PostgreSQL — вторая система в
деплое без выигрыша: один бэкап, один мониторинг и один способ восстановления
для соло-разработчика дешевле.

Redis не нужен ни на одной ступени: он выигрывает микросекунды доступа там,
где экономятся миллисекунды расчёта (§13.2).

### 12.5. Что нельзя откладывать

`ResearchCorpus` должен писаться **с первого дня работы стенда**. Данные, не
записанные тогда, не восстанавливаются никогда, а именно они определяют
качество рецептов интерпретации.

## 13. Замеры

Первый срез блока E дорожной карты. Стенд: 2 vCPU Intel Xeon 2.80 ГГц,
Python 3.11, `pysweph` 2.10.3.6, прогретый кэш эфемерид. Замер автора на его
машине (`build_natal_components.md` §1.4) дал median 18.9 мс — машины
сопоставимы.

### 13.1. Расчёт натальной карты

```text
40 прогонов с разными датами, однопоточно:
  min 10.5   median 16.3   p95 18.2   max 20.7 мс
  → потолок последовательного расчёта 62 карты/с
```

### 13.2. Конкурентность

```text
60 расчётов через EngineService:

 одновременных  воркеров   карт/с   p50 мс   p95 мс
             1         1     62.1       17       18
             2         2     59.9       33       46
             5         5     59.2       85       97
            10        10     60.5      159      180
            10         4     57.0      172      202
```

**Пропускная способность не растёт от конкурентности** — подпись глобального
`RLock` в `ephemeris_runtime.py`. Задержка растёт линейно: десять
одновременных запросов дают десять последовательных расчётов. Размер пула
воркеров не влияет ни на что: они стоят в очереди за одним замком.

Попадание в кэш:

```text
  median 4.28 мс   p95 6.53 мс   → 234 отдачи/с однопоточно
  при 10 / 50 / 200 одновременных: 139 / 189 / 171 отдач/с
  внутри: decode_chart_artifact 1.22 мс + model_copy(deep=True) 2.49 мс
  размер артефакта: 46 КБ JSON, 7 КБ gzip
```

Больше половины стоимости попадания — глубокая копия модели. Она нужна для
изоляции вызывающих и закреплена тестами; трогать её сейчас незачем, но здесь
лежит двукратное ускорение горячего пути, если оно понадобится.

### 13.3. SQLite

```text
CAS-запись (UPDATE ... WHERE version + commit), WAL, synchronous=NORMAL:
  median 0.016 мс   p95 0.084 мс   → 61 000 записей/с
  raw UPDATE с устаревшей версией: rowcount = 0
  чтение по первичному ключу: 0.002 мс → 520 000 чтений/с
```

Это микрозамер SQL-примитива на машине автора, а не benchmark будущего
`SqliteSessionPersistence`. В него не входили сериализация моделей,
`BEGIN IMMEDIATE`, возврат `VersionConflict(actual)`, агрегатные
touch/reset/delete, передача работы в executor, реальный профиль диска и
конкуренция писателей. Поэтому числа `61 000` и `520 000` нельзя выдавать за
пропускную способность адаптера или доказательство production-capacity.

P4 повторяет замер через публичный порт на file-backed базе с фактическими
`journal_mode`/`synchronous`, сериализацией, commit и тем же executor, что
используется приложением. Отдельно измеряются p50/p95 для CAS success,
VersionConflict, aggregate touch/reset/delete и конкурирующих писателей.
До этого допустим только вывод, что голый SQL-примитив не выглядит очевидным
узким местом при ожидаемых десятках записей в секунду.

### 13.4. Что из этого следует

**Расчёт для демо не узкое место.** При 50% загрузки движка — около 30 карт/с
и p95 порядка 35 мс — это примерно 20 новых сессий в секунду, то есть десятки
тысяч в час. Интерпретации процессор почти не нагружают: вызов LLM это
ожидание ввода-вывода. Тысячи одновременных соединений упрутся в `ulimit` и
настройки ASGI-сервера, а не в приложение.

**Узкое место — бюджет LLM.** Дневной потолок ADR-0013 финансовый, а не
технический, и считать его надо от стоимости одной интерпретации.

**По памяти запас большой.** Тысяча активных сессий с типичными диалогами —
около 20 МБ; кэш расчётов на 10 000 карт — 70 МБ.

**Транзиты меняют картину полностью.** Окно ±12 месяцев — 0.51 с, в тридцать
раз дороже натала; потолок падает с 62 до примерно двух операций в секунду.
`overview.md` §4.10 называет транзит самой дорогой операцией системы, а
условие возврата к `BuildAttempt` из `build_natal_components.md` §1.4 —
«расчёт, устойчиво превышающий несколько сотен миллисекунд». Транзиты это
условие выполняют: вместе с ними придётся вернуться и к фоновому выполнению,
и к отброшенной машинерии попыток.

## 14. Проверяемые свойства

Дополняют список в `exact-orb_negative_corner_scenarios.md` §4.

**Состояние и версии**

- сброс `scope="dialog"` не трогает карту и данные рождения;
- сброс `scope="all"` применяет `RESET_DELTA` тем же CAS-путём,
  инкрементирует `state_version`, а не обнуляет его, и очищает диалог только
  вместе с успешным commit;
- операция, начатая до сброса, после него получает `Superseded`;
- интерпретация не изменяет `state_version`;
- двойная отправка идентичной команды даёт один `Committed` и один
  `AlreadyApplied`; движок вызывается один раз, `state_version` растёт на
  единицу;
- при конфликте с другим намерением исход — `Superseded`, а не
  `AlreadyApplied`.
- retry после неподтверждённого commit использует ту же дельту и original
  expected без rebase: в зависимости от фактического исхода первой записи
  получает `Committed`, `AlreadyApplied` или `Superseded`;

**Диалог**

- добавление хода не меняет `state_version` и не вызывает CAS;
- append продлевает state и dialog одним deadline, а clear продлевает state
  и очищает dialog; оба сохраняют предметное state и `state_version`;
- два одновременных `append` сохраняют оба хода;
- повторный `turn_id` сохраняется вторым ходом, а
  `state_version_at_answer` не валидируется относительно текущей версии;
- построение карты не переписывает диалог;
- диалог не превышает 50 ходов, 8 000 символов на ход и 120 000 символов
  суммарно; вытеснение идёт с самых старых;
- усечение выставляет `truncated=True` и не меняет `status`; варианты
  `complete + truncated` и `partial + truncated` покрыты отдельно;
- прерывание пользователем сохраняет ход со `status="partial"`;
- ответ интерпретации несёт `state_version`, при котором стартовал запрос,
  даже если состояние изменилось во время генерации.

**Жизненный цикл**

- фасетные `get` и `read` read-only;
- агрегатный `touch` одним `now` продлевает обе записи и возвращает
  согласованный frozen `SessionSnapshot`;
- CAS, append, clear и touch не укорачивают TTL и не проходят
  `hard_expires_at`;
- достижение `hard_expires_at` делает сессию логически недоступной независимо
  от активности; физическую очистку выполняет SQLite reaper;
- невалидный port-параметр `now` даёт `ValueError` до lookup/mutation;
- `ExpiredSessionTransitionError` не пересекает persistence boundary;
- `session_expired` и `session_not_found` различимы в метриках и
  неразличимы в ответе пользователю;
- `DeleteMyDataCommand` гасит cookie и удаляет обе записи; последующий
  запрос получает сессию с новым серверным идентификатором;
- агрегатный delete не оставляет частично удалённую пару записей;
- `session_id` из тела/query/path не принимается, а absent/stale cookie не
  используется для создания новой записи; коллизия create не перезаписывает
  существующую сессию.

**Отказы и хранилище**

- отказ чтения даёт `StateReadFailed`, а не пустое состояние;
- публичная ошибка хранилища и соответствующий failure-outcome сохраняют
  один безопасный `error_code`, не выпуская raw exception;
- превышение лимита построений даёт типизированный отказ, а не расчёт;
- состояние и диалог переживают рестарт процесса на реализации `Sqlite*`;
- обе реализации, `InMemory*` и `Sqlite*`, проходят один conformance-набор
  фасетных портов и `SessionPersistence` через обязательный factory seam
  (тесты параметризованы реализацией).

**Приватность**

- в `ResearchRecord` отсутствуют `birth_input`, координаты, точное время,
  градусы и `calculation_key`.

## 16. Открытые вопросы

1. **IP-лимит для класса `calculation`** — конкретное значение. Требует
   HTTP-транспорта, которого до блока F не существует, поэтому блок B не
   задерживает.
2. **Режим `synchronous` для SQLite на стенде.** `NORMAL` предполагается
   по умолчанию (§12.3); подтвердить при настройке деплоя, когда станет
   известно, на каком диске и в какой виртуализации живёт стенд.
