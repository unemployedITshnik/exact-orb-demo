# ADR-0018. `InterpretationQuery` — недоверенные данные в отдельном слоте

Дата: 2026-08-25. Статус: принято. Переформулирует инвариант И-1.

## Контекст

Прежний инвариант И-1 звучал так: `Planner` и всё ниже никогда не видят
пользовательский текст. Он был безупречен, пока продукт сводился к перечню
интентов и фокусов.

Но полноценный диалог требует, чтобы модель знала конкретный вопрос:

```
«Что в моей карте говорит о том, почему я постоянно меняю работу?»
```

Пары `topic = natal, focus = career` для этого недостаточно. Буквальное прочтение
И-1 делает subscription-режим архитектурно невозможным.

## Решение

Понимание запроса даёт **два независимых результата**:

```
UnderstandingResult {
    contract_fields          → ContractValidator → ResolvedContract → Planner
    interpretation_query     → PolicyService → PromptBuilder
}

InterpretationQuery { normalized_text, language }
```

`GuardVerdict` от `InputGuard` — **отдельный объект**, не поле запроса: иначе
у типа два производителя, а `PromptBuilder` начинает принимать policy-решения
по флагам. Verdict идёт в `AdmissionControl` и `PolicyService`.

`PolicyService` превращает запрос в `AuthorizedInterpretationQuery` либо
отказывает. `PromptBuilder` принимает только авторизованный тип и помещает его
в отдельный делимитированный слот рецепта.

**Переформулированный инвариант И-1:**

> Детерминированный planning и execution path никогда не получает
> пользовательский текст. В разрешённом режиме нормализованный
> `InterpretationQuery` передаётся исключительно в `InterpretationService`
> как недоверенные данные; он не влияет на выбор инструментов, параметры
> расчёта и policy-решения.

**Обработка текста не делает его доверенным.** `normalized_text` ограничен
по длине, приведён к единой кодировке и очищен от управляющих символов — это
нужно для предсказуемости и стоимости, а не для безопасности. Обезвредить текст,
адресованный языковой модели, невозможно в принципе: для неё инструкция
и данные — один поток слов, и отделить одно от другого нечем. Фильтрация
по списку фраз бесполезна в обе стороны: перефразирование её обходит,
а нормальные вопросы она блокирует.

Защиту даёт не обработка текста, а отсутствие у интерпретационной модели
возможностей: инструментов, доступа к секретам и чужому состоянию, влияния
на расчёт. Вопрос попадает к ней отдельным полем, а не подмешивается в системную
инструкцию. Худший исход успешной инъекции — неуместный текст в ответе.
Подписка решает экономическую сторону проблемы, но средством безопасности
не является.

Раз вход недоверенный, недоверенным считается и выход: `OutputGuard`
в free-form режиме обязателен.

Слот под запрос присутствует в рецептах с первого дня и в demo пуст (ADR-0020).

## Альтернативы

Сохранить буквальный И-1 — отвергнуто: закрывает subscription. Передавать текст
в `Planner` как подсказку — отвергнуто: делает выбор инструментов управляемым
пользователем. Считать нормализацию достаточной защитой — отвергнуто.

## Последствия

- `PromptBuilder` явно различает trusted system recipe и untrusted user query.
- `InputGuard` обязан ограничивать длину входа, иначе стоимость промпта
  неограниченна (ADR-0013).
- Рецепты, написанные без слота, потребовали бы полного переписывания при
  включении free-form.
- Free-form ответы кэшируются с `session_id` в ключе (ADR-0017).
