# ADR-0014. Изменение базовых данных и вида карты — явные операции состояния

Дата: 2026-08-25. Ревизия: 2026-08-25 — добавлена операция `SetActiveView`;
`ChartStateIntent` как побочный эффект интерпретации отвергнут.
Ревизия: 2026-09-04 — `profile_version` переименован в `state_version`,
`ContextDelta` в `StateDelta`; зафиксирован контракт `compare_and_set`
и третий исход `AlreadyApplied`; `SetActiveView` в MVP отсутствует
(ревизия ADR-0016); **отменено** следствие «Frontend после мутации получает
новую карту и сброшенный производный вид» в части производного вида.
Ревизия: 2026-09-05 — уточнено, что store принимает и применяет
`StateDelta`, а не готовый state-кандидат; полный reset использует
`RESET_DELTA` через тот же CAS-путь; retry после неподтверждённого commit
повторяет original expected без rebase.
Статус: принято.

## Контекст

После bootstrap в сессии есть базовый набор данных, относительно которого
рассчитана карта. В диалоге пользователь упоминает даты и места по разным
причинам — исправляет, спрашивает гипотетически, говорит о другом человеке,
называет дату события. Автоматическая перезапись сделала бы состояние
нестабильным:

```
Базовое время: 00:45
«А что изменилось бы, если бы я родилась в 01:15?»
```

не означает `base_birth_time = 01:15`.

## Решение

**Состояние меняют только явные типизированные команды.**

`UpdateBirthData` — источник: редактирование полей формы. Изменение через чат
относится к отложенной функции (ADR-0019) и в MVP отсутствует.

`SetActiveView` — переключение `base | derived` и построение производной карты.
В MVP отсутствует: транзитов в первом срезе нет, `active_view` всегда `base`
(ревизия ADR-0016). Решение сохраняется на будущее, потому что определяет не
только что рисовать, а **по какой карте отвечает интерпретация**: без него
вопрос «расскажи про Марс» при двух картах в сессии неоднозначен.
Это отдельная операция состояния, **не побочный эффект интерпретации**:
`ChartStateIntent`, применяемый после успешного tool-flow, отвергнут, потому что
делает оркестратор вторым владельцем мутации и порождает вопросы порядка
применения.

```
UpdateBirthData → BirthDataResolver → ResolvedBirthData
                → ChartArtifactResolver → атомарное обновление сессии
```

После успешного расчёта обновляются `birth_input`, `birth_resolved`,
`state_version`, `base_chart`. Производные (`derived_chart`, `active_view`)
в MVP отсутствуют вместе с транзитами; когда они появятся, обновление
базы сбрасывает их: `derived_chart = None`, `active_view = base`.

**Переименование.** `profile_version` → `state_version`,
`ContextDelta` → `StateDelta`, `ChartRef.profile_version` →
`ChartRef.state_version`. Смысл контрактов не меняется; имя `profile`
осталось от `SessionProfile`, которого больше нет (ревизия ADR-0009).

**`state_version` защищает от stale-записи**, а не участвует в calculation key
— ключ и так различает данные (ADR-0017).

```
state_version = 7 → запрос A
state_version = 8 → запрос B
A завершается позже B → не имеет права менять активную карту
```

Инкремент выполняется **compare-and-set** на записи сессии: иначе два
одновременных обновления прочитают версию 7 и оба запишут 8. Версию присваивает
store, не handler. Store получает `StateDelta`, применяет её к актуальному
состоянию и строит новую версию внутри той же атомарной операции; готовый
кандидат с вычисленной вызывающим версией порт не принимает.

**Контракт CAS:**

```
async def compare_and_set(
    session_id, expected_state_version, delta, *, now
) -> int | VersionConflict(actual: SessionState) | SessionAbsent
```

Возврат актуального состояния в конфликте обязателен: без него вызывающий
обязан сделать второе чтение, между чтением и записью снова случится гонка,
и `Superseded` станет вероятностным. С ним решение принимается по данным,
которые база уже прочитала внутри той же операции.

Отклонение возвращается **результатом, а не исключением**: устаревшая версия
— штатный исход конкурентной работы, а не ошибка.

**Три исхода записи, а не два:**

| Исход | Когда | Что видит пользователь |
|---|---|---|
| `Committed` | версия совпала | новая карта |
| `Superseded` | версия устарела, намерение **другое** | явное «результат отброшен» |
| `AlreadyApplied` | версия устарела, но текущее состояние **уже равно** намерению | успех |

`AlreadyApplied` нужен для повторной доставки одного и того же запроса:
пользователь нажал «Построить» дважды, или клиент повторил запрос после
неподтверждённого commit. Без третьего исхода второй запрос получил бы
`Superseded` — «ваш результат отброшен» на карту, которая на экране и есть
результат этого самого запроса. Сравнивается намерение (`birth_resolved`
и `ChartSpec`), а не версия и не текстовая форма `birth_input`.

При неподтверждённом commit неизвестен его фактический исход, но original
`expected_state_version` известен. Retry повторяет ту же дельту с этим же
expected: если первая запись не состоялась, CAS коммитит её; если состоялась,
конфликт несёт уже применённое состояние и превращается в `AlreadyApplied`;
если победило другое намерение — в `Superseded`. Перечитать состояние и
подменить expected свежей версией означало бы rebase старого намерения и
могло бы затереть конкурентное изменение, поэтому такой retry запрещён.

Классификация принадлежит `ContextService`: он использует только `actual`
из атомарного `VersionConflict`, возвращает `AlreadyApplied` при совпадении
намерения и `Superseded` при различии. Дополнительного `get`, скрытого retry
или изменения expected в этой ветке нет.

Каждая ссылка на карту несёт версию, при которой она получена; инвариант
`chart.state_version == state.state_version` — единственная проверка
валидности ссылки.

## Альтернативы

Считать любую упомянутую дату исправлением — отвергнуто как опасная неявная
мутация. Запретить изменение через чат навсегда — не требуется: достаточно
отличать mutation intent от обычного вопроса; в MVP запрет действует по причине
ADR-0019.

## Последствия

- Гипотетические вопросы безопасны.
- Старый кэш не инвалидируется: новые параметры дают другой ключ.
- Frontend после мутации получает новую карту; прежнее следствие про
  сброшенный производный вид отложено вместе с транзитами.
- `InterpretSelectionCommand` состояние не пишет и CAS не выполняет: ход
  диалога дописывается в `DialogStore` отдельной операцией, поэтому
  интерпретация не может ни получить `Superseded`, ни вызвать его
  у параллельного построения карты.
- `ResetSessionCommand(scope="all")` — такая же мутация: агрегатный
  `SessionPersistence.reset` только делегирует `RESET_DELTA` тому же
  фасетному CAS; RESET_DELTA-aware CAS атомарно очищает диалог при успехе, а `state_version`
  инкрементируется, не сбрасываясь в ноль. Иначе незавершённая операция с
  `expected_state_version = 0` прошла бы CAS и записала старую карту в
  только что очищенную сессию.
- Для нескольких субъектов потребуется явная идентификация роли данных.
- Механизм: `sequence_diagrams/session/005-compare-and-set.puml`.
