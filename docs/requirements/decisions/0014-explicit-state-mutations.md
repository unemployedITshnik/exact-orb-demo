# ADR-0014. Изменение базовых данных и вида карты — явные операции состояния

Дата: 2026-08-25. Ревизия: 2026-08-25 — добавлена операция `SetActiveView`;
`ChartStateIntent` как побочный эффект интерпретации отвергнут.
Статус: принято.

## Контекст

После bootstrap в сессии есть базовый набор данных, относительно которого
рассчитана карта. В диалоге пользователь упоминает даты и места по разным
причинам — исправляет, спрашивает гипотетически, говорит о другом человеке,
называет дату события. Автоматическая перезапись сделала бы состояние
нестабильным:

```
Базовое время: 00:45
«А что изменилось бы, если бы я родилась в 01:15?»
```

не означает `base_birth_time = 01:15`.

## Решение

**Состояние меняют только явные типизированные команды.**

`UpdateBirthData` — источник: редактирование полей формы. Изменение через чат
относится к отложенной функции (ADR-0019) и в MVP отсутствует.

`SetActiveView` — переключение `base | derived` и построение производной карты.
Это отдельная операция состояния, **не побочный эффект интерпретации**:
`ChartStateIntent`, применяемый после успешного tool-flow, отвергнут, потому что
делает оркестратор вторым владельцем мутации и порождает вопросы порядка
применения.

```
UpdateBirthData → BirthDataResolver → ResolvedBirthData
                → ChartArtifactResolver → атомарное обновление сессии
```

После успешного расчёта обновляются `birth_input`, `birth_resolved`,
`profile_version`, `base_chart`, и **сбрасываются производные**:
`derived_chart = None`, `active_view = base`.

**`profile_version` защищает от stale-записи**, а не участвует в calculation key
— ключ и так различает данные (ADR-0017).

```
profile_version = 7 → запрос A
profile_version = 8 → запрос B
A завершается позже B → не имеет права менять активную карту
```

Инкремент выполняется **compare-and-set** на записи сессии: иначе два
одновременных обновления прочитают версию 7 и оба запишут 8. Версию присваивает
store, не handler.

Отброшенный результат возвращается клиенту явно (`superseded`), а не молчаливым
успехом с неактивной картой.

Каждая ссылка на карту несёт версию, при которой она получена; инвариант
`chart.profile_version == profile_version` — единственная проверка валидности
ссылки.

## Альтернативы

Считать любую упомянутую дату исправлением — отвергнуто как опасная неявная
мутация. Запретить изменение через чат навсегда — не требуется: достаточно
отличать mutation intent от обычного вопроса; в MVP запрет действует по причине
ADR-0019.

## Последствия

- Гипотетические вопросы безопасны.
- Старый кэш не инвалидируется: новые параметры дают другой ключ.
- Frontend после мутации получает новую карту и сброшенный производный вид.
- Для нескольких субъектов потребуется явная идентификация роли данных.
