# ADR-0006. Оркестратор — координатор flow; stateless между запросами

Дата: 2026-08-21. Ревизия: 2026-08-25 — область сужена до потоков
с интерпретацией; уточнено значение слова stateless; интерпретационный конвейер
передан `InterpretationService`; **прежнее обоснование отказа от чистой функции
признано недействительным**.
Статус: принято.

## Контекст

Исходная формулировка «единственная точка координации» относилась ко всей
системе, когда система была чистым чатом. После ADR-0012 детерминированное
построение карты имеет собственный путь.

Слово «stateless» в прежней редакции означало «в `self` только зависимости».
Это верно буквально, но описывает не то свойство: внутри одного прогона
оркестратор удерживает `CapabilitySet`, `InterpretationPlan`, `ToolResults`,
`PromptBundle`, открытый SSE-поток и **незакоммиченную резервацию бюджета**.

## Решение

**Граница.** Оркестратор координирует потоки, включающие интерпретацию.
Детерминированное построение и перестроение карты координируется application
service расчёта и через оркестратор не проходит.

**Значение stateless.** Оркестратор не хранит состояния **между запросами**:
реплики взаимозаменяемы, следующий ход диалога может обработать другой процесс.
**Внутри прогона** он является stateful координирующим фреймом, и это его
нормальный режим, а не дефект.

Из этого следуют требования:

* резервация бюджета (`reserve → commit | cancel`) — распределённая транзакция;
  запись обязана иметь lease с TTL и reaper, иначе падение процесса протекает
  резервацией и молча съедает дневной потолок;
* `run_id` — корреляционный идентификатор для наблюдаемости, **не** хэндл
  возобновления; обрыв SSE означает потерю прогона, переподключение
  к идущему прогону не поддерживается;
* внутри хода клиент привязан к реплике.

**Владение конвейером.** Связка `interpretation cache get → reserve budget →
LLM → OutputGuard → cache put → commit` принадлежит `InterpretationService`,
а не оркестратору. Оркестратор выполняет последовательность: загрузить контекст
→ выбрать handler → план → policy → tools → интерпретация → сохранить дельту
→ стримить.

**Мутации состояния** выполняет handler через `ProfileService` и возвращает
`ContextDelta`; оркестратор её сохраняет и сам предметных решений о состоянии
не принимает.

## Альтернативы

Оркестратор как чистая функция `(контракт, контекст) → (ответ, дельта)`.
**Прежнее обоснование отказа недействительно:** оно опиралось на необходимость
сохранить незакрытое уточнение в момент решения спросить, а
`pending_clarification` отменён (ADR-0007). Вариант остаётся жизнеспособным,
и текущая конструкция к нему близка. Полный переход отложен, а не отвергнут.

## Последствия

- Риск god-object реален: противоядие «нет предметных знаний» не работает само
  по себе, его обеспечивает вынос конвейера в `InterpretationService`.
- Ожидание чужого I/O асинхронно.
- Число исходящих зависимостей оркестратора — метрика, за которой нужно следить.
