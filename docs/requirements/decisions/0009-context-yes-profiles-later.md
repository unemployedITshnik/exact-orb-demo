# ADR-0009. Анонимная сессия переживает закрытие страницы, но не становится профилем

Дата: 2026-08-21. Ревизия: 2026-08-25 — введена cookie-идентификация и структура
`SessionProfile`; **отменено** следствие «каждый новый диалог начинается
с запроса данных рождения»; зафиксирован отказ от `Profile DB`.
Ревизия: 2026-09-04 — `SessionProfile` переименован в `SessionState`, ходы
диалога вынесены в отдельную запись `DialogStore`, введён абсолютный потолок
TTL, `DeleteMyDataCommand` гасит cookie, `ProfileService` как отдельный
компонент не вводится; **отменено** следствие «Session TTL продлевается
любой операцией» в части безусловности.
Ревизия: 2026-09-05 — уточнена граница persistence: фасетные чтения
read-only, согласованный read-and-renew выполняет агрегатный `touch` с
`SessionSnapshot`; reset/delete атомарны между состоянием и диалогом;
`session_id` создаётся только доверенным серверным генератором, а cookie
используется только для поиска.
Статус: принято.

## Контекст

Исходно предполагалось, что диалог начинается без данных рождения. После
появления стартовой страницы пользователь приходит к экрану карты с уже
разрешёнными данными. Долговременное хранение профилей для demo не требуется
и открывает контур персональных данных, consent, lifecycle и deletion.

## Решение

Аккаунтов и долговременных профилей нет. Данные рождения и ссылки на карты живут
в **анонимной сессии с TTL**, идентифицируемой устойчивой `HttpOnly` cookie
(`Secure`, `SameSite`), и восстанавливаются в том же браузере до истечения TTL.
После удаления cookie или истечения TTL данные считаются утраченными.

`session_id` генерирует доверенный серверный transport. Клиент не может
передать его в теле, query/path-параметре или выбрать значение для новой
сессии; cookie служит только непрозрачным ключом поиска. Если запись по cookie
отсутствует или истекла, прежний ключ не «оживляется»: cookie гасится, для
новой сессии генерируется свежий идентификатор. Коллизия create возвращается
типизированным `SessionIdConflict` и не раскрывает и не перезаписывает
существующую, в том числе истёкшую, запись.

```
SessionState {
    session_id
    birth_input       что ввёл пользователь — для формы
    birth_resolved    ResolvedBirthData — для расчёта и ключа
    state_version
    base_chart:       { state_version, spec: ChartSpec } | None
    created_at, expires_at, hard_expires_at
}
```

Имя `SessionState` заменяет и `SessionProfile`, и `SessionContext`: сущность
одна, а два имени порождали вопрос, чем `ContextService` отличается от
`ProfileService`. Переименование `profile_version` → `state_version`
оформлено ревизией ADR-0014.

`derived_chart` и `active_view` в MVP отсутствуют — они нужны транзитам,
которых в первом срезе нет (ревизия ADR-0016).

**Ходы диалога — отдельная запись**, `DialogStore`, а не поле состояния.
Иначе каждая запись карты через CAS переписывала бы весь диалог, а
добавление хода конкурировало бы с изменением карты за одну версию.
Хранилища живут по одному TTL. Фасетные `SessionStore.get` и
`DialogStore.read` read-only; согласованный read-and-renew выполняет только
`SessionPersistence.touch`, который продлевает обе записи одним моментом и
возвращает frozen `SessionSnapshot { state, dialog }`.

Хранятся оба представления данных рождения: только `birth_input` означал бы,
что обновление `tzdata` молча сдвинет карту; только `birth_resolved` — что нечего
показать в форме редактирования. Подстановка ближайшего города (ADR-0005) делает
это различие ещё нужнее: `birth_input` хранит то, что человек написал,
`birth_resolved` — то, по чему посчитано.

**Владение persistence одно.** `ContextService` работает с агрегатом
`SessionPersistence`, открывающим узкие фасеты `sessions: SessionStore` и
`dialogs: DialogStore`. Межзаписные touch, reset и delete принадлежат
агрегату и выполняются атомарно. Отдельный компонент `ProfileService`
**не вводится**: его
единственной обязанностью было правило отказа stale-записи, а правило —
чистая функция от текущего состояния и дельты, и живёт оно в
`session/state.py` рядом с моделью. Версию присваивает store при CAS
(ADR-0014); отдельный владелец инкремента не нужен. Handler получает дельту
и возвращает её оркестратору.

**TTL двухуровневый.** Скользящий — 7 дней; при входе в пользовательскую
операцию обе записи продлеваются агрегатным `touch`, а успешный переход
состояния применяет то же правило с переданным `now`.
Абсолютный потолок — 30 дней от `created_at`, независимо от активности; по
его достижении сессия удаляется, продление невозможно. Потолок нужен
затем, что бесконечно продлеваемое окно противоречит privacy-модели
(ADR-0023): данные рождения не должны жить в хранилище неограниченно долго
только потому, что человек раз в неделю открывает вкладку.

Тридцать дней — текущая creation policy `new_session`, а не инвариант
десериализации. Persisted `hard_expires_at` является lifecycle-данными;
модель проверяет только `created_at <= expires_at <= hard_expires_at` и не
требует равенства `hard_expires_at == created_at + текущая константа`.
Иначе изменение policy сделало бы старые корректные строки нечитаемыми.

**Удаление по требованию.** `DeleteMyDataCommand` через агрегатный `delete`
атомарно удаляет обе записи и
**гасит cookie** — `Set-Cookie` с истёкшим сроком; следующий запрос
получает сессию с новым серверным идентификатором. Без гашения пользователь остался бы с cookie,
указывающей в пустоту, и различие «удалил» / «истекло» стало бы неразличимо
в метриках. Два последовательных вызова фасетов не являются реализацией:
сбой между ними оставил бы частично удалённый агрегат.

**Истечение TTL при открытой странице** даёт клиенту `session_expired` и возврат
к bootstrap. Восстановление карты из данных клиента запрещено: frontend
не источник истины (ADR-0005). Если это понадобится продуктово — вводится
отдельным решением через подписанный серверный токен.

Долговременный профиль не создаётся. Появление регистрации и подписки —
основание пересмотреть решение.

## Альтернативы

Передавать карту с frontend в каждом запросе — отвергнуто. Сразу создать
постоянный профиль — отложено: отдельный контур персональных данных.

## Последствия

- Прежнее следствие «каждый новый диалог спрашивает данные рождения» отменено.
- В пределах сессии пользователь не повторяет исходные данные.
- Read-only фасеты не продлевают TTL скрыто; агрегатный `touch` продлевает
  состояние и диалог вместе **в пределах абсолютного потолка**.
- Межзаписные reset/delete являются атомарными операциями
  `SessionPersistence`, а не координацией двух независимых портов в
  application-коде.
- Идентификатор сессии всегда свежий и серверный; значение cookie никогда не
  становится идентификатором для вновь создаваемой записи.
- Лимит расхода в сессии сбрасывается вместе с cookie и потому **не является
  средством защиты от злоупотребления** — им остаются IP-лимит и дневной
  потолок (ADR-0013).
- Session и History — разные понятия; правила исследовательских хранилищ
  задаёт ADR-0023.
- Реализация хранилищ сессии и диалога — ADR-0024.
- Требования к блоку целиком:
  `component_responsibilities/exact-orb_session_requirements.md`;
  диаграммы — `sequence_diagrams/session/`.
