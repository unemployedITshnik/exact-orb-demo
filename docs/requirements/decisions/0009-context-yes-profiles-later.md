# ADR-0009. Анонимная сессия переживает закрытие страницы, но не становится профилем

Дата: 2026-08-21. Ревизия: 2026-08-25 — введена cookie-идентификация и структура
`SessionProfile`; **отменено** следствие «каждый новый диалог начинается
с запроса данных рождения»; зафиксирован отказ от `Profile DB`.
Статус: принято.

## Контекст

Исходно предполагалось, что диалог начинается без данных рождения. После
появления стартовой страницы пользователь приходит к экрану карты с уже
разрешёнными данными. Долговременное хранение профилей для demo не требуется
и открывает контур персональных данных, consent, lifecycle и deletion.

## Решение

Аккаунтов и долговременных профилей нет. Данные рождения и ссылки на карты живут
в **анонимной сессии с TTL**, идентифицируемой устойчивой `HttpOnly` cookie
(`Secure`, `SameSite`), и восстанавливаются в том же браузере до истечения TTL.
После удаления cookie или истечения TTL данные считаются утраченными.

```
SessionProfile {
    birth_input       что ввёл пользователь — для формы
    birth_resolved    ResolvedBirthData — для расчёта и ключа
    profile_version
    base_chart:    { profile_version, spec: ChartSpec }
    derived_chart: { profile_version, spec: ChartSpec } | None
    active_view:   base | derived
}
```

Хранятся оба представления данных рождения: только `birth_input` означал бы,
что обновление `tzdata` молча сдвинет карту; только `birth_resolved` — что нечего
показать в форме редактирования. Подстановка ближайшего города (ADR-0005) делает
это различие ещё нужнее: `birth_input` хранит то, что человек написал,
`birth_resolved` — то, по чему посчитано.

**Владение persistence одно.** `ContextService` читает и пишет `Session Store`.
`ProfileService` выполняет чистые мутации `SessionProfile`, владеет инкрементом
`profile_version` и правилом отказа stale-записи (ADR-0014), но собственного
хранилища не имеет. Handler вызывает `ProfileService`, получает дельту
и возвращает её оркестратору.

**Истечение TTL при открытой странице** даёт клиенту `session_expired` и возврат
к bootstrap. Восстановление карты из данных клиента запрещено: frontend
не источник истины (ADR-0005). Если это понадобится продуктово — вводится
отдельным решением через подписанный серверный токен.

Долговременный профиль не создаётся. Появление регистрации и подписки —
основание пересмотреть решение.

## Альтернативы

Передавать карту с frontend в каждом запросе — отвергнуто. Сразу создать
постоянный профиль — отложено: отдельный контур персональных данных.

## Последствия

- Прежнее следствие «каждый новый диалог спрашивает данные рождения» отменено.
- В пределах сессии пользователь не повторяет исходные данные.
- Session TTL продлевается любой операцией.
- Лимит расхода в сессии сбрасывается вместе с cookie и потому **не является
  средством защиты от злоупотребления** — им остаются IP-лимит и дневной
  потолок (ADR-0013).
- Session и History — разные понятия (ADR-0010).
