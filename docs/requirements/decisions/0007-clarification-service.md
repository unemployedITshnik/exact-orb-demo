# ADR-0007. Единый `InputRequired` вместо `ClarificationService`

Дата: 2026-08-21. Ревизия: 2026-08-25 — **заменяет** конструкцию
`ClarificationService` + `ClarificationRegistry` + `pending_clarification`
типизированным исходом.
Статус: принято.

## Контекст

Прежнее решение вводило отдельный сервис без LLM, собирающий пробелы в один
вопрос, и многоходовое состояние «система спросила и ждёт ответа на конкретный
слот».

После появления формы это перестало окупаться: незаполненное поле формы —
не диалоговая неоднозначность, а сама форма и есть состояние ожидания.
Одновременно появился третий исход — неоднозначное место, — который не является
ни ошибкой валидации, ни conversational gap.

## Решение

Три категории, три механизма.

**1. Валидация формы.** Обязательность и формат проверяются до расчёта.
`birth_date` и `birth_place` обязательны, `birth_time` — нет.

**2. Единый типизированный исход `InputRequired`.**

```
InputRequired {
    issues: [{
        field: contract.path
        code: MISSING | AMBIGUOUS | INVALID | UNSUPPORTED
        candidates?   constraints?
    }]
}
```

Один тип возвращают `BirthDataResolver`, `ContractValidator` и `Planner`.
`missing_slots` как отдельное понятие упраздняется. Исход поднимается через
вызвавший handler к оркестратору и доходит до клиента событием `input_required`.

**3. Многоходового состояния нет.** `ClarificationService`,
`ClarificationRegistry` и `pending_clarification` из архитектуры удаляются.
Клиент, получив `InputRequired`, повторяет запрос с дополненными данными.

## Альтернативы

Сохранить `ClarificationService`. Отвергнуто: для формы он лишний, а для чата
в MVP нечего уточнять (ADR-0019). Формулировать уточнения через LLM — отвергнуто
ранее, остаётся отвергнутым.

## Последствия

- Один тип и одно место его определения; `field` — путь в контракт.
- В MVP `AMBIGUOUS` порождается эндпоинтом подсказок, а не путём построения
  карты: форма выбирающая, Build API принимает только `place_id` (ADR-0005).
- **Известная цена:** отсутствие pending-состояния означает, что повторный ответ
  требует повторного извлечения. Для rule-based экстрактора это идемпотентно,
  для вероятностного — нет. Возврат к вероятностному экстрактору (ADR-0011)
  потребует кэширования результата извлечения по `message_id` или возврата
  pending-состояния.
- Уточнение не расходует interpretation quota.
