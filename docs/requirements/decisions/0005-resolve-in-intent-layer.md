# ADR-0005. Резолв места и исторического времени — детерминированный компонент до planning и calculation

Дата: 2026-08-21. Ревизия: 2026-08-25 — резолвер вынесен из intent-слоя; введён
единый исход; **отменено** правило «момент транзита резолвится по поясу
пользователя»; NL-путь через резолвер отложен (ADR-0019); добавлена подстановка
ближайшего города.
Статус: принято.

## Контекст

Для расчёта нужны `lat/lon`, `tz_id` и историческое смещение на конкретную дату:
для 02.09.1990 в Москве действовало UTC+4. Наивное «GMT+3» даёт ошибку в час
и сдвинутый асцендент.

Прежняя редакция помещала резолвер внутрь intent-слоя, зная единственный путь
из свободного текста. После появления формы структурированный ввод не проходит
через intent-слой и потерял бы доступ к резолву.

## Решение

`BirthDataResolver` — самостоятельный детерминированный компонент, обязательно
вызываемый **до planning и calculation**. `IntentService` его использует,
но не владеет им.

**Вход** — примитивная структура (`place_id | place_text`, `local_date`,
`local_time?`), не типы intent-слоя.

**Выход** — `ResolvedBirthData` либо `InputRequired` (ADR-0007):

```
ResolvedBirthData {
    canonical_place, lat, lon, tz_id
    utc_datetime, utc_offset_applied
    time_unknown: bool
    place_substituted: bool
    place_input_text: str | None
    warnings[]
}
```

`ResolvedContract` **содержит** `ResolvedBirthData` полем, а не дублирует его.

### Место

Резолвится через `PlaceResolverPort` с адаптерами `LocalPlaceCatalog`
и `RemoteGeocoder`; только адаптер знает про сеть (И-5). Порт возвращает исход
`Resolved | Candidates | NotFound` с ограниченным числом кандидатов, чтобы
контракт UI не зависел от реализации.

**Build API принимает `place_id` и не принимает свободный текст.** Форма
выбирающая: отправка разблокируется после выбора из подсказок. Поэтому исход
`AMBIGUOUS` на пути построения карты не возникает — его порождает эндпоинт
подсказок и, позже, свободный текст (ADR-0019).

`place_id` приходит от клиента и доверенным не является: он может устареть после
обновления каталога или быть подделанным. Backend проверяет его по каталогу
и при неудаче возвращает `InputRequired` с кодом `INVALID`.

### Подстановка ближайшего города

Если населённого пункта нет в каталоге, форма предлагает указать ближайший
известный пользователю город. **Подобрать его система не может** — координат
исходного места у неё нет, в этом и состояла проблема. Выбор делает человек,
и формулировка в UI должна это отражать.

Подстановка фиксируется явно: `place_substituted = true`, исходный текст
сохраняется в `birth_input`, `birth_resolved` содержит выбранный город.

Тела считаются геоцентрически (`FLG_SWIEPH` без `FLG_TOPOCTR`), поэтому
подстановка не влияет на положения планет — страдают только дома, Ascendant и MC.
Один градус долготы — четыре минуты звёздного времени, то есть в среднем около
градуса смещения Ascendant, а в быстровосходящих знаках больше; на широте 55°
это примерно 64 км. При отклонении больше 0.5° по долготе или широте добавляется
`warning`, и рецепт смягчает утверждения о куспидах и углах. Меньшее отклонение
сопоставимо с обычной неточностью времени рождения и остаётся в метаданных.

Смягчение выражается флагом в `Evidence`, а не третьим набором `forbids`:
запрет упоминать дома относится к космограмме, здесь дома есть, просто посчитаны
по подставленному месту.

Подстановка — компромисс, продиктованный неполнотой локального каталога.
С появлением `RemoteGeocoder` необходимость в ней сокращается.

### Время

Момент рождения — по историческим правилам `tz_id` места рождения. Момент
транзита — по `tz_id` **места расчёта** на дату транзита; прежнее «по поясу
пользователя» отменяется. Несуществующее и удвоенное локальное время не
исправляется молча.

### Резолвер не пишет в состояние

Результат обрабатывает вызвавший handler.

## Альтернативы

Считать координаты и tz на frontend — отвергнуто: детерминированный расчёт
требует серверного источника истины. Принимать готовые `lat/lon` как доверенные —
отвергнуто; допустим `place_id`, но с проверкой. Резолв внутри `Tool` —
отвергнуто: аргументы должны быть нормализованы раньше. Оставить резолвер
в intent-слое — отвергнуто в этой ревизии. Ручной ввод координат вместо
подстановки города — отвергнуто как источник ошибок у неподготовленного
пользователя.

## Последствия

- Один компонент обслуживает оба пути ввода; в MVP фактически вызывается
  только форма (ADR-0019).
- `ResolvedContract` не содержит сырого текста (И-1 в редакции ADR-0018).
- `Planner.plan(contract: ResolvedContract)` сохраняется.
- Эндпоинт подсказок вызывается на каждое нажатие клавиши: нужен debounce
  на клиенте и собственный rate limit на сервере.
- Сетевой геокодер требует timeout и кэша.
- Стартовое построение карты не требует `IntentService`.
