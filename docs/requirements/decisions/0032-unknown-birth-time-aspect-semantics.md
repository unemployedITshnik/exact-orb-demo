# ADR-0032. Устойчивые аспекты космограммы при неизвестном времени

Дата: 2026-09-12.
**Статус: принято и реализовано 2026-09-12.**

Частично заменяет ADR-0008 только в части представления аспектов и
конфигураций при неизвестном времени. Выбор вида карты, техническое полуденное
положение, запрет домов и правило обработки календарных аномалий из ADR-0008
остаются в силе.

## Контекст

При пустом `BirthInput.birth_time` резолвер устанавливает
`time_unknown=true` и использует местное полуденное положение как
детерминированный технический якорь. Текущий движок рассчитывает по этому
единственному моменту обычные `Aspect` и `Configuration`. Поэтому отношение,
которое существует только около полудня, либо меняет тип или категорию в
течение даты, выглядит как факт момента рождения.

Предупреждение ADR-0008 о смене знака Луны не решает проблему: точка может
пересечь границу орбиса или категории без смены знака. Проверка только начала,
полудня и конца даты также не доказывает устойчивость внутри промежутков.

## Решение

### Вид карты определяется пользовательским вводом

```text
BirthInput.birth_time is None     → time_unknown=true  → cosmogram
BirthInput.birth_time is not None → time_unknown=false → natal
```

Любое явно указанное допустимое время означает `natal`, включая `12:00`.
Технически подставленное полуденное значение не является пользовательским
временем и не превращает космограмму в натал.

### Допустимое время космограммы

Возможное время рождения — конечное множество всех поддерживаемых минут
локальной календарной даты. Секунды и микросекунды равны нулю в локальном
представлении, как и для явно введённого времени продукта.

Каждая локальная минута разрешается по IANA-зоне:

- существующая однозначная минута даёт один UTC-момент;
- несуществующая минута пропускается;
- неоднозначная минута даёт оба UTC-момента;
- полностью несуществующая локальная дата остаётся
  `InputRequired { birth.date, INVALID }`.

Домен не равен `00:00Z…24:00Z` и не строится как техническое полуденное
`utc_datetime ± 12 часов`. Его крайние значения выводятся из соседних местных
полуночей с учётом IANA-переходов. При обычном сезонном переводе UTC-проекция
даты длится 23 или 25 часов вместо 24; историческое изменение смещения может
быть не кратно часу.

Каноническое семантическое представление домена — упорядоченное множество
уникальных aware UTC-моментов. Транспорт хранит его без потерь как
`BirthTimeDomain`: упорядоченный кортеж непересекающихся
`UtcMinuteRange(first_utc, count)`. Один диапазон разворачивается в
`first_utc + n * 60 секунд`, `0 <= n < count`; соседние элементы с тем же
шагом обязаны быть слиты. Разрыв или смена секундной фазы создаёт следующий
диапазон. Такое представление сохраняет исторические смещения с секундами,
пропущенные и повторённые часы без передачи timezone policy в движок.

Для `time_unknown=true` домен непуст и содержит технический
`ResolvedBirthData.utc_datetime`; для `time_unknown=false` он отсутствует.
Нарушение этого соответствия является validation error resolved input.

### Владение доменом

- `birth/tz.py` разрешает локальные минуты и формирует канонический
  `BirthTimeDomain`;
- `BirthDataResolver` связывает его с исходной датой, техническим якорем и
  `time_unknown`;
- `ResolvedBirthData` переносит домен как уже разрешённый факт;
- `CalculationInput` переносит его канонический digest в ключ;
- `EngineService` передаёт готовый домен натальной технике;
- движок потребляет UTC-диапазоны и не восстанавливает локальную дату, не
  открывает `ZoneInfo` и не применяет timezone policy;
- `BuildNatalHandler` только выбирает `chart_kind` и ничего не вычисляет.

Digest домена — SHA-256 канонического JSON с маркером
`utc-minute-domain-v1` и нормализованными `first_utc`/`count` всех диапазонов.
Он служит компактной идентичностью множества; сам `ResolvedBirthData` хранит
диапазоны, необходимые расчёту.

### Устойчивый аспект

Правило применяется ко всем существующим точкам активной аспектной сетки
космограммы, а не только к Луне.

Для каждой неупорядоченной пары на каждом UTC-моменте домена применяется
обычный finder с действующими типами, приоритетами, орбисами и порогами
категорий. Пара публикуется в `NatalChart.aspects` только если:

1. аспект существует на каждом моменте домена;
2. на каждом моменте выбран один и тот же `aspect_type`;
3. категория `exact` / `working` / `background` одинакова на всём домене.

Опубликованный `Aspect.exact_angle` следует типу, `applying` остаётся `None`,
а `Aspect.orb` равен **максимальному** орбису этой пары на всём домене. Для
космограммы это консервативная верхняя граница, а не полуденный орбис и не
утверждение о точном моменте рождения. Для натала `orb` сохраняет прежнюю
моментальную семантику.

Если аспект отсутствует на всём домене, отношения и диагностической записи
нет. Если он существует хотя бы в одном моменте, но не удовлетворяет трём
условиям, он не публикуется и получает запись неопределённости. Аспект,
отсутствующий в полдень, но появляющийся в другое время, поэтому также виден
как исключённый кандидат. При одновременной допустимости типов действует
существующий детерминированный приоритет finder; нового tie-breaker нет.

ADR фиксирует этот математический предикат, но не численный алгоритм его
доказательства. Проверка только начала, полудня и конца даты недостаточна.

### Машиночитаемая неопределённость

Существующий `CalculationWarning { source, message, retflags }` не
расширяется аспектными строковыми соглашениями. `NatalChart` получает
отдельный типизированный блок `time_uncertainty`:

```text
CosmogramTimeUncertainty {
    domain: BirthTimeDomain
    excluded_aspects: tuple[UnstableAspect, ...] | None
}

UnstableAspect {
    from_point:             AspectPointRef
    to_point:               AspectPointRef
    reasons:                tuple[UnstableAspectReason, ...]
    includes_no_aspect:     bool
    possible_aspect_types:  tuple[AspectType, ...]
    possible_categories:    tuple[AspectCategory, ...]
}
```

`UnstableAspectReason` — закрытое множество:

```text
not_present_for_all_times
aspect_type_changed
category_changed
```

Причины и возможные значения дедуплицируются и сортируются канонически;
ссылки пары ориентируются тем же детерминированным порядком, что и обычные
аспекты. Текст сообщения не является частью машинного контракта.

Наличие `time_uncertainty` у космограммы означает, что интервальная проверка
применена. Для натала поле обязательно `None`. Если блок `aspects` не
запрошен, `excluded_aspects=None` означает «не проверяли»; если блок рассчитан,
кортеж присутствует и может быть пустым. Это сохраняет различие «не считали»
и «посчитали, исключений нет».

Блок не является вторым списком опубликованных отношений: в нём нет обычных
`Aspect`, и потребитель не может восстановить из него точный аспект. Единственный
источник интерпретационных отношений — `NatalChart.aspects`.

### Конфигурации

ADR-0031 остаётся в силе. Finder конфигураций получает только устойчивые
аспекты из `NatalChart.aspects`; исключённое ребро не может вернуться через
верхнеуровневую или вложенную конфигурацию.

Отдельный сканер устойчивости конфигураций не вводится. Одинаковый тип и
категория каждого канонического ребра на всём домене гарантируют неизменную
топологию и роли. `Configuration.max_orb` равен максимуму консервативных
`Aspect.orb`, то есть худшему орбису среди всех рёбер и всех допустимых минут;
категория конфигурации выводится из этого значения действующим правилом.

Консервативное следствие принято намеренно: фигура, которая существует весь
день только за счёт сменяющих друг друга неустойчивых рёбер, не публикуется.

### Позиции и прочие блоки

`NatalChart.bodies` космограммы остаются положениями технического полудня.
Интервальная семантика относится к аспектам и производным конфигурациям, а не
подменяет отображаемые координаты тел.

Не меняются отсутствие домов, углов, управителей и силы, `applying=None`,
аспектные профили, ось лунных узлов, materialized-инварианты ADR-0031 и
`house_system="P"`. Транзиты поверх космограммы остаются отдельным открытым
решением. Предупреждения ADR-0008 о смене знака и направления также остаются
отдельным невыполненным обязательством и не подменяются аспектным блоком.

## Идентичность, артефакт и сессия

Решение реализовано одновременным изменением:

- `ENGINE_VERSION`: `"3"` → `"4"`, потому что меняется методика результата;
- schema расчётного ключа: `SCHEMA_VERSION="v1"` → `"v2"` и префикс
  `eo:calc:v2:`, потому что `CalculationInput` получает
  `birth_time_domain_digest: str | None`;
- state payload version: `1` → `2`, потому что persisted
  `ResolvedBirthData` получает `birth_time_domain`.

`profiles_digest` не меняется: профили аспектов и конфигураций прежние.
`CALCULATION_VERSION_SCHEMA` остаётся `v1`, потому что форма
`CalculationVersionRecord` не меняется. `ChartSpec` не получает домен:
это разрешённый входной факт, а не пользовательский выбор техники. Отдельная
`artifact_schema_version` не вводится; строгий artifact validator требует
`time_uncertainty` у новой космограммы, а новый calculation key делает старые
cache entries недостижимыми.

`CalculationInput.birth_time_domain_digest` равен `None` для натала и digest
домена для космограммы. `calculation_input_from_chart()` восстанавливает его
из `chart.time_uncertainty.domain`, поэтому сквозная проверка ключа остаётся
самодостаточной.

Session payload v2 хранит новый resolved-домен. Чтение v1 сохраняется:

- известное время мигрирует с `birth_time_domain=None`;
- для `time_unknown=true` домен детерминированно строится migration-helper'ом
  birth-слоя из сохранённых `birth_input.birth_date` и
  `birth_resolved.tz_id`; session adapter координирует версию, но сам не
  реализует timezone policy;
- результат миграции записывается как v2 при следующей мутации;
- если дата или зона больше не разрешаются, чтение даёт существующий
  типизированный persistence failure, а не использует старый полуденный
  расчёт под ключом v2.

Миграция применяет текущую IANA-базу намеренно: v1 не содержал суточного
домена, поэтому восстановить исторически несуществующий набор невозможно.
Полученный digest входит в новый ключ и не позволяет смешать результаты.

## Альтернативы

**Удалить все аспекты Луны** — отвергнуто: теряются доказуемо устойчивые
отношения, а переменность других быстрых пар остаётся.

**Оставить полуденные аспекты с общей строкой-warning** — отвергнуто:
обычный DTO остаётся ложным фактом, а потребители вынуждены независимо
угадывать риск.

**Хранить все отношения с диапазоном орба** — отвергнуто для текущего
продукта: `NatalChart.aspects` и конфигурации являются интерпретационным
набором фактов, а не перечнем всех возможных гипотез. Неустойчивые кандидаты
остаются в типизированной диагностике без превращения в аспекты.

**Проверить только границы даты** — отвергнуто: пересечение орбиса, категории
или ближайшего типа возможно внутри домена.

**Строить домен в движке из `tz_id`** — отвергнуто: timezone policy
дублировалась бы ниже birth-границы и могла разойтись с резолвером.

## Последствия и статус реализации

- космограмма публикует только отношения, истинные для любой поддерживаемой
  минуты локальной даты;
- одиночный `orb` космограммы является консервативным максимумом;
- неустойчивые пары доступны как закрытая машинная диагностика, но не как
  интерпретационные аспекты;
- конфигурации остаются строго производными от канонических аспектов;
- изменение затронуло resolved input, key identity, artifact и session
  payload в одном implementation-этапе;
- движок исчерпывающе проверяет каждый UTC-момент канонического minute-domain,
  не передавая timezone policy ниже birth-слоя;
- state payload v2 пишется актуальной моделью, frozen v1 читается через
  внедряемый birth-owned migration seam;
- актуальные диаграммы синхронизированы с фактическими моделями и потоком;
- finding `002` остаётся открытым до отдельной сквозной проверки полного
  DEBUG-payload и ручной приёмки.
