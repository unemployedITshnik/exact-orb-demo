# ADR-0021. Модульный монолит со служебными швами; распределённую систему не строим

Дата: 2026-08-30. Статус: принято.

## Контекст

Компоненты проекта неоднородны по природе. Движок — native-биндинг с процессным
локом и CPU-профилем нагрузки. Интерпретация — внешняя latency, стоимость
и стриминг. Calculation Cache уже физически живёт в другом процессе (Redis).
Возникает вопрос, строить ли распределённую систему сразу.

ADR-0017 сделал этот вопрос практическим: ключ кэша обязан строиться чистой
функцией без движка, иначе слой, решающий «идти ли считать», сам обязан поднять
native-биндинг. Это первый случай, когда граница между компонентами перестала
быть вопросом вкуса.

Одновременно нужен ответ на противоположный риск. Заявленная готовность
к сервисам без ограничителя превращается в ритуал: аргумент «а это
service-ready?» начинает оправдывать прослойки, сериализацию и версионирование
там, где хватало вызова функции.

## Решение

**Остаёмся модульным монолитом.** Сеть, очереди, retry/idempotency, деплой-матрица
и distributed tracing между внутренними компонентами не вводятся.

**Границы проектируются разрезаемыми.** Компонент не полагается на то, что он
живёт в одном процессе с соседями: данные приходят аргументами, результат
уходит значением, скрытого доступа к глобальному состоянию нет.

**Компоненты делятся на три категории**, и категории не смешиваются:
shared contracts (копируются на обе стороны шва), logical services (становятся
сетевым вызовом), ports/adapters (меняется реализация, не контракт).
`Calculation Key / Spec` — shared kernel, а не сервис. `Tool` — порт (ADR-0002),
а не сервис.

**Правила выносятся в `docs/architecture/service_ready_architecture.md`** —
это постоянная рамка, а не точечное решение, и жанр ADR ей не подходит.
На каждое правило рамки наложены два ограничения:

* правило обязано оправдываться **сегодняшней** выгодой; обоснование
  «понадобится при разрезе» недостаточно;
* правило без автоматической проверки называется соглашением ревью,
  а не инвариантом.

**Разрез выполняется по наблюдаемому триггеру**, а не по готовности. Триггеры
перечислены в рамочном документе.

## Альтернативы

**Строить распределённую систему сейчас** — отвергнуто. Приносит сетевые
отказы, версионирование API, деплой-матрицу и распределённые блокировки
до того, как появится нагрузка, которая их оправдывает. Ни один из триггеров
разреза сегодня не наблюдается.

**Не фиксировать границы вовсе** — отвергнуто. ADR-0017 уже опирается
на границу «ключ строится без движка»; без записанного правила она держится
на памяти автора и разрушается первым удобным импортом.

**Записать намерение без проверок** — отвергнуто. Непроверяемая рамка
не ограничивает код, зато ограничивает обсуждение: превращается в аргумент,
которым удобно обосновать любую прослойку.

**Оформить рамку как ADR** — отвергнуто. Записи в этом каталоге — точечные
решения с альтернативами и последствиями; постоянный список правил с колонкой
«как проверяется» — другой жанр, и он будет переписываться чаще, чем допускает
формат ревизий (`decisions/README.md`).

## Последствия

- Появляется `docs/architecture/service_ready_architecture.md`; спецификации
  компонентов ссылаются на него, а не переписывают правила.
- Появляется `tests/test_module_boundaries.py`: контрактный слой проверяется
  на отсутствие native, runtime и edge импортов, `swisseph` — на единственную
  точку входа в процесс.
- Добавление поля в модель, участвующую в ключе, становится явным событием
  инвалидации кэша, а не рядовой правкой (следствие ADR-0017).
- Зафиксирован долг: движок читает `exact_orb.config`; `selena_method` влияет
  на результат, но не входит ни в `ChartSpec`, ни в `CalculationVersion`.
  Второй пункт требуется закрыть до реализации `CalculationVersion`.
- Появление сети, очередей или отдельной деплой-единицы между внутренними
  компонентами требует нового ADR, а не решения в рамках задачи.
