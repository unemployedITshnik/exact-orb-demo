# ADR-0002. `Tool` как порт с адаптерами `Local` / `Remote`

Дата: 2026-08-21. Статус: принято, не реализовано.

## Контекст

Требуется гибкая расширяемая конфигурация и возможность вынести расчётное ядро
в отдельный сервис, не переписывая агентский слой. Сегодня `cli.py` вызывает
`get_natal()` напрямую, а пакет `tools/` существует как неподключённый скелет.

## Решение

`Tool.run(ToolRequest) -> ToolResult` — порт, о котором знают Orchestrator и Planner
и который ничего не сообщает о месте исполнения расчёта. Реализации:

- `LocalTool` — валидация аргументов, вызов функции движка в процессе;
- `RemoteTool` — тот же контракт через HTTP.

Конфигурация вида `natal = local | http://...` читается фабрикой на старте,
адаптеры регистрируются в `ToolRegistry`. Интерфейс асинхронный.

Обобщённые адаптеры вместо класса-обёртки на каждую технику: `ToolRequest`
и `ToolResult` уже транспортно-нейтральны (pydantic + dict). Отдельный класс
пишется только там, где нетривиален маппинг аргументов и результата.

## Альтернативы

Класс-обёртка на каждую технику. Отвергнуто как бойлерплейт: для типового случая
«запрос → расчёт → результат» достаточно двух обобщённых адаптеров.

## Последствия

- Добавление техники: файл в `engine/charts` плюс строка конфигурации.
- Перенос техники в микросервис: строка конфигурации, без правок в остальном стеке.
- Адаптер — единственное место в системе, знающее про сеть (инвариант И-5).
