# Промт: перенос расчётного ядра в exact_orb.engine

Ты работаешь над проектом exact-orb. Задача этого промта — чисто
механический перенос путей, без единого изменения расчётной логики или
поведения. Пять пакетов, которые сейчас лежат прямо в `src/exact_orb/`
как отдельные сиблинги — `ephemeris/`, `charts/`, `aspects/`,
`configurations/`, `strength/` — являются детерминированным расчётным
ядром проекта: они не знают ни про LLM, ни про промпты, ни про
пользовательский ввод. Сейчас это разделение видно только по факту (эти
пять пакетов случайно не импортируют ничего интерпретирующего), а не по
структуре. Нужно сделать его явным: собрать все пять под одним новым
пакетом `src/exact_orb/engine/`, сохранив их содержимое и внутреннюю
структуру один в один — просто на уровень глубже.

Мотивация (контекст, не часть проверки): в перспективе это ядро может
быть выделено в отдельный сервис. Сама эта задача НЕ проектирует границу
сервиса, HTTP/gRPC-контракты или что-либо подобное — только чистит
структуру пакетов внутри монолита. Не делай ничего сверх переноса путей
под этим предлогом.

ЗАДАЧА
1. Перенеси каталоги `ephemeris/`, `charts/`, `aspects/`,
   `configurations/` (вместе с вложенным `configurations/patterns/`) и
   `strength/` из `src/exact_orb/` в `src/exact_orb/engine/`. Это
   обычный перенос каталогов внутри рабочего дерева, без требований к
   системе контроля версий. Не пересоздавай файлы вручную, не меняй их
   имена и не удаляй содержимое поддеревьев.
2. Заведи `src/exact_orb/engine/__init__.py`, если его там ещё нет
   (сам `engine/` — новый пакет уровня, отдельного `__init__.py` для
   него раньше не существовало). Открой существующий
   `src/exact_orb/__init__.py` и `__init__.py` каждого из пяти
   перенесённых пакетов, чтобы понять, какой в проекте принят стиль
   реэкспорта публичных имён — и реши по аналогии, нужно ли
   `engine/__init__.py` что-то реэкспортировать сам, или ему достаточно
   быть пустым (с докстрингом, что это единая точка входа в расчётное
   ядро). Не изобретай новый стиль реэкспорта, если в проекте уже есть
   свой.
3. Найди и поправь абсолютно все импорты в репозитории, ссылающиеся на
   старые пути (`exact_orb.ephemeris`, `exact_orb.charts`,
   `exact_orb.aspects`, `exact_orb.configurations` — включая
   `exact_orb.configurations.patterns.*` — и `exact_orb.strength`),
   заменив префикс на `exact_orb.engine.*`. Также найди относительные
   импорты из верхнего пакета `exact_orb`, например `from .aspects ...`
   в `src/exact_orb/cli.py`, и переведи их на `.engine.*`. Ищи через
   полнотекстовый поиск по `src/`, `tests/` и `scripts/` (`rg` или
   аналог), а не по памяти о том, что где импортируется — среди прочего
   это точно затронет:
   - внутренние cross-imports между самими этими пятью пакетами
     (например, `configurations` может импортировать типы из `aspects`,
     `strength` — из `configurations`/`ephemeris`, `charts/transit.py`
     — из `ephemeris`/`aspects`; проверь фактически, не считай на
     слово, что где используется);
   - `cli.py` — крупный файл, наверняка импортирует из всех пяти
     пакетов;
   - весь `tests/`: каждый тестовый файл, `tests/fixtures/*`,
     `tests/helpers.py`, если там есть такие импорты;
   - `scripts/`, если там есть smoke-тесты или служебные скрипты,
     импортирующие расчётное ядро;
   - `src/exact_orb/__init__.py` и `__main__.py`, если они что-то
     реэкспортируют из перенесённых пакетов.
4. Чистый cutover: никаких временных re-export/alias на старых путях не
   оставляй. После этой задачи `import exact_orb.aspects` (и аналогично
   для остальных четырёх) должен просто не работать.

ОСОБОЕ ВНИМАНИЕ
1. Внутри самих перемещаемых пакетов могли использоваться как
   абсолютные импорты (`from exact_orb.aspects.types import ...`), так
   и относительные (`from . import types`, `from .. import ...`).
   Относительные импорты **внутри** одного и того же перемещаемого
   поддерева (например, внутри `configurations/` между `finder.py` и
   `configurations/patterns/*`) при переносе всего поддерева на уровень
   глубже обычно продолжают работать без изменений — а вот абсолютные
   импорты (`from exact_orb....`), включая те, что смотрят из одного из
   пяти пакетов в другой (например, `configurations` -> `aspects`), не
   исправятся сами. Проверь оба вида явно, не только абсолютные.
2. `config.py` и `logging_setup.py` остаются на прежнем месте,
   `src/exact_orb/`, — **не переноси их в `engine/`.** Они
   инфраструктурные и не принадлежат исключительно расчётному ядру:
   `config.py` уже используется (или должен использоваться, по промту
   `2026-08-17/02-llm-gateway.md`) слоем LLM, а не только ephemeris.
3. `cli.py` тоже остаётся на прежнем месте — это точка входа приложения
   (`exact-orb = "exact_orb.cli:main"` в `pyproject.toml`), а не часть
   расчётного ядра. У него просто поправляются импорты, как у любого
   другого потребителя `engine/`.
4. Если в проекте к этому моменту уже существуют `intent/`, `tools/`,
   `interpretation/`, `orchestration/` и/или `llm/` — не трогай их.
   Проверь (через тот же поиск), что ни один из них не импортирует
   что-либо из `ephemeris/aspects/charts/configurations/strength`
   напрямую; если вдруг импортирует — это отдельная находка, сообщи о
   ней, но не переделывай архитектуру агентных слоёв в рамках этого
   промта, только поправь путь импорта на `exact_orb.engine.*`.
5. `pyproject.toml` менять не нужно: `[tool.setuptools.packages.find]
   where = ["src"]` работает через автообнаружение и подхватит
   `engine/` и всё вложенное само — но не считай это на слово, а
   подтверди это в ПРОВЕРКЕ ниже.

ЧТО ВЕРНУТЬ

```
src/exact_orb/
  engine/
    __init__.py
    ephemeris/            # без изменений внутри, кроме импортов
    charts/
    aspects/
    configurations/
      patterns/
    strength/
  cli.py                  # импорты поправлены
  config.py               # без изменений
  logging_setup.py        # без изменений
  __init__.py
  __main__.py
```

Ни один файл внутри перенесённых пакетов не переименовывается — `finder.py`
остаётся `finder.py`, `types.py` остаётся `types.py` и т.д. Меняется
только их родительский пакет.

ПРОВЕРКА
1. На диске существует структура `src/exact_orb/engine/{ephemeris,charts,
   aspects,configurations,strength}`, а старых каталогов
   `src/exact_orb/{ephemeris,charts,aspects,configurations,strength}` уже
   нет. `src/exact_orb/config.py`, `src/exact_orb/logging_setup.py`,
   `src/exact_orb/cli.py`, `src/exact_orb/__init__.py` и
   `src/exact_orb/__main__.py` остаются на прежних местах.
2. Полнотекстовый поиск по рабочим исходникам и проверкам, исключая
   исторические промты, кэши, `.venv`, `logs` и прочий generated output,
   после переноса не находит старых импортов. Используй поиск, который
   ловит и абсолютные, и относительные формы, например:
   `rg -n --glob '!prompts/**' --glob '!**/__pycache__/**' --glob '!logs/**'
   --glob '!pytest-cache-files-*' "from \.(ephemeris|charts|aspects|configurations|strength)|exact_orb\.(ephemeris|charts|aspects|configurations|strength)" src tests scripts README.md pyproject.toml`.
   Допустимы только исторические упоминания в `prompts/**`, если они не
   обновляются в рамках этой задачи.
3. `python -c "import exact_orb.ephemeris"` (и аналогично для `charts`,
   `aspects`, `configurations`, `strength` без префикса `engine`)
   кидает `ModuleNotFoundError` — подтверждает отсутствие старых путей
   и alias'ов.
4. `PYTHONPATH=src python -c "from exact_orb.engine import ephemeris, charts,
   aspects, configurations, strength"` отрабатывает без ошибок (это
   работает, даже если `engine/__init__.py` пустой — импорт подпакетов не
   требует реэкспорта в `__init__.py` родителя).
5. Весь существующий `pytest` зелёный, без единого свежего
   `xfail`/`skip`/`mark`, добавленного, чтобы обойти проблему с
   импортом, — это подтверждает, что перенос не задел ни один расчёт.
   Отдельно убедись, что golden-тест на основе
   `tests/golden/natal_1985_human.txt` (через `test_cli_render.py`)
   по-прежнему проходит побайтово.

ОГРАНИЧЕНИЯ
Не меняй ни одной строчки расчётной логики — только пути импорта и
расположение файлов на диске. Не переименовывай сами пакеты или файлы
внутри перенесённого поддерева. Не трогай `intent/`, `tools/`,
`interpretation/`, `orchestration/`, `llm/`, если они уже существуют —
кроме точечного исправления путей импорта, если они там всё же
используются. Не оставляй нигде временных re-export/alias на старых
путях `exact_orb.aspects` и т.п. — cutover должен быть полным сразу. Не
трогай `pyproject.toml`, пока фактическая проверка (пункт 4 в ПРОВЕРКЕ)
не покажет, что без правок не обойтись — тогда останови работу и
сообщи, что понадобилось изменить и почему, а не молча правь конфиг. Не
проектируй под эту задачу ничего про будущий микросервис (HTTP-контракты,
сериализация через границу процесса и т.п.) — это отдельная, гораздо
более поздняя задача.
