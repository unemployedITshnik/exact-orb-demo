# Prompt: ограничить натальный расчёт системой домов Плацидуса

Работай в ветке `fix/house-system-validation`.

## Цель

В текущей версии продукта поддерживается только система домов Плацидуса:

```text
P — Placidus
```

Другие системы домов пока не поддерживаются. Их поддержку нужно зафиксировать
как будущую функциональность, связанную с выбором системы в UI.

Сейчас `normalize_house_system_code()` принимает любой одиночный
ASCII-символ. Swiss Ephemeris для неизвестных кодов вроде `Z` и `?` молча
рассчитывает Плацидус, а `NatalChart` сохраняет исходный неизвестный код.
Получается численно карта Плацидуса, маркированная другой системой.

## Обязательное поведение

### Поддерживаемый код

Для натального расчёта разрешён только `P`.

Допустимая нормализация:

```text
"P"   → "P"
"p"   → "P"
b"P"  → "P"
b"p"  → "P"
```

Все остальные значения должны отклоняться: известные Swiss-коды `K`, `O`,
`R`, `C`, `E`, `W`, неизвестные `Z` и `?`, многосимвольные, не-ASCII и
нестроковые значения.

### Не выполнять молчаливую подмену

Запрещено всегда присваивать `house_system = "P"` независимо от входа. Если
вызывающий передал неподдерживаемый код, должна возникать явная ошибка. Нельзя
рассчитывать Плацидус и возвращать результат, маркированный переданным кодом.

### Сохранить поле в контракте

Не удаляй `house_system` из `NatalChartSpec`, аргументов натального движка,
`NatalChart`, сериализации и ключа расчёта. Сейчас все поддерживаемые запросы
будут иметь значение `P`. Поле сохраняется как точка расширения для будущего
выбора системы домов через UI.

## Границы валидации

### `NatalChartSpec`

Обычное создание `NatalChartSpec` с неподдерживаемым кодом должно завершаться
Pydantic validation error. Нижний регистр и bytes для `P` должны
канонизироваться в строку `"P"`.

### `EngineService`

Защитная предпроверка подделанной через `model_construct()` спеки с
неподдерживаемой системой должна возвращать
`ChartCalculationError(code="SPEC_INVALID", run_id=<исходный run_id>)` до
executor, эфемеридного лока и вызова адаптера. Не используй `model_construct()`
в тестах обычного публичного контракта: он допустим только для защитной границы
`EngineService`.

### Прямой натальный движок

Прямой вызов `calculate_natal(..., house_system=<неподдерживаемый код>)`
должен завершаться `ValueError` до вызова `swe.houses_ex()`. Неизвестный код
не должен доходить до Swiss Ephemeris.

## Изоляция от транзитов

Эта ветка относится только к натальному расчёту.

Текущий `normalize_house_system_code()` используется также транзитами, где
существуют тесты с кодом `K`. Не вводи глобальное ограничение `{"P"}` в общий
нормализатор, если это изменит транзитное поведение.

Выдели натальный контракт отдельно, например:

```text
normalize_house_system_code()        — общая ASCII-нормализация
normalize_natal_house_system_code()  — нормализация и проверка, разрешает только P
```

Точное имя выбери в соответствии со стилем проекта. Натальную проверку должны
использовать `NatalChartSpec`, `EngineService._prevalidate()`, натальный
адаптер и прямой путь `calculate_natal()`.

Не меняй `transit.py`, транзитные модели, поиск точных дат, станции или
транзитные алгоритмы. Существующие транзитные тесты должны продолжать
проходить без изменения ожиданий.

## Тесты

Добавь детерминированные regression-тесты:

1. `P`, `p`, `b"P"` и `b"p"` принимаются и дают `"P"`.
2. `K`, `Z`, `?` и остальные неподдерживаемые значения отклоняются натальным
   валидатором.
3. Обычный `NatalChartSpec(house_system="K")` не создаётся.
4. Подделанный `NatalChartSpec` с `K` или `Z` даёт `SPEC_INVALID` на границе
   `EngineService`.
5. При таком отказе сохраняется `run_id`, не вызываются executor и адаптер.
6. Прямой `calculate_natal()` не передаёт неподдерживаемый код в
   `swe.houses_ex()`.
7. Валидный расчёт с `P` сохраняет `chart.house_system == "P"`, существующие
   числовые результаты и golden-файлы.
8. Существующее транзитное поведение не изменилось.

Найди существующие тесты, использующие `K` только как способ получить другой
натальный ключ или другой single-flight key. После ограничения системы домов
такие натальные спеки становятся невалидными. Замени технический способ
различить спеки другим поддерживаемым полем, не ослабляя исходный проверяемый
инвариант. Не создавай ключи из заведомо невалидных натальных спецификаций.

## Документация

Синхронизируй актуальную документацию.

### Текущее ограничение

В README и calculation requirements явно укажи:

- текущая версия натального расчёта поддерживает только `P` — Плацидус;
- параметр `house_system` сохранён для будущего расширения;
- другие коды отклоняются, а не подменяются на Плацидус;
- CLI-флаг `--house-system` сейчас принимает только `P`.

Исправь Т-ЭФ-10: формулировка «любой одиночный ASCII-символ» больше не
является действующим контрактом. Проверь связанные требования `ChartSpec` и
предпроверки `EngineService`: вместо «известный код» должно быть явно указано
«поддерживаемый натальный код `P`».

### Будущая функциональность

В разделе известных ограничений и дорожной карте добавь отдельную будущую
задачу «Поддержка нескольких систем домов».

Зафиксируй, что её реализация потребует:

- выбора системы домов в UI;
- явного backend-allowlist поддерживаемых кодов;
- передачи выбранного значения из UI в `NatalChartSpec`;
- сохранения backend-валидации — UI не является доверенной границей;
- числовых и golden-тестов для каждой поддерживаемой системы;
- проверки поведения на высоких широтах;
- пользовательских названий систем;
- проверки влияния системы на ключ и версию расчёта.

Коды `K`, `O`, `R`, `C`, `E`, `W` можно перечислить как кандидатов будущей
функциональности, но не объявлять поддерживаемыми сейчас.

Не создавай новый ADR, если действующие архитектурные решения не требуют его.
Не редактируй исторические промты.
