# Промт: правки блока `birth/` по итогам ревью

**Контекст.**

Блок `birth/` реализован промтами `01-birth-data-resolution.md`
и `02-birth-data-resolution-tests.md`. Тест-пак из 73 тестов проходит.
Ревью нашло дефекты, которых тесты не ловят; ниже — их исправление.

Две находки одного класса и наиболее серьёзные: **детерминированное
разрешение аномалии часового пояса молча меняет ответ на другой знак
Луны.** Остальное — устойчивость загрузки каталога и мелочи.

Численные утверждения ниже получены прогоном по всем зонам IANA
и вызовом расчётного движка, а не рассуждением. Если реализация
им противоречит — неправа реализация.

**Решения, которые уже приняты и не обсуждаются в рамках этого промта:**

- Правило «система не спрашивает пользователя о значении, которое
  подставила сама» (ADR-0008) **остаётся**. Оно сужается, а не отменяется:
  дата рождения — не подставленное значение, а ввод пользователя.
- Детерминированный выбор при удвоении времени **остаётся** `fold = 0`.
  Воспроизводимость важнее «правильного» варианта, которого не существует.
- Контракт `ResolutionWarning` не расширяется полем `details`.
  Различение несут коды: они по определению машинно-проверяемы
  (ADR-0008), и рецепту этого достаточно.
- CLI (`03-birth-resolution-cli.md`) в этот промт не входит.

---

**Задача.**

## 1. Несуществующая календарная дата — проблема даты, а не времени

### 1.1. Что не так сейчас

Когда несуществующий полдень нормализуется, резолвер принимает результат
всегда. Но семнадцать случаев несуществующего полудня распадаются на две
неоднородные группы:

```text
дата сохраняется, сдвинут только час — 12 зон
  Africa/Casablanca 1967-06-03 → 13:00
  America/Havana    1925-07-19 → 12:29

дата сдвигается на сутки, дня не было вовсе — 5 зон
  Pacific/Apia       2011-12-30 → 2011-12-31
  Pacific/Fakaofo    2011-12-30 → 2011-12-31
  Pacific/Kiritimati 1994-12-31 → 1995-01-01
  Pacific/Kanton     1994-12-31 → 1995-01-01
  Pacific/Kwajalein  1993-08-21 → 1993-08-22
```

Во второй группе **дня не существовало**: Самоа и Токелау в 2011 году
перешли через линию перемены дат, Кирибати сделало это в 1994-м.
Пользователь назвал дату — это его ввод, а не наша подстановка, —
и система её переписывает.

Последствие, посчитанное движком:

```text
Самоа, названо 2011-12-30 → посчитано 2011-12-31
  Луна 354.031° Pisces  →  6.115° Aries      ЗНАК МЕНЯЕТСЯ
```

Космограмма состоит из положений, аспектов и конфигураций; Луна в ней —
главное быстрое тело. Мы отдаём интерпретацию по знаку, которого
у человека нет, с предупреждением «Noon anchor adjusted to a valid
local time».

### 1.2. Правило детекции — не «дата сдвинулась»

Наивная проверка `normalized.date() != local_datetime.date()` **неверна**.
Переходы в 23:00 с переводом на 00:00 следующих суток встречаются часто,
и тогда несуществующее локальное время нормализуется за полночь, хотя
день полностью существует:

```text
Africa/Algiers 1920-02-14 23:00 → 1920-02-15 00:00   день существует
Africa/Ceuta   1927-04-09 23:00 → 1927-04-10 00:00   день существует
```

Перебор всех зон за 1900–2030 даёт **1135 таких случаев**. Наивное
правило обвинило бы дату в каждом из них.

### 1.3. `local_date_exists` — новая функция в `birth/tz.py`

```python
def local_date_exists(local_date: date, tz_id: str) -> bool:
    """Существует ли в этой зоне хоть один момент с этой локальной датой.

    Сутки существуют тогда и только тогда, когда у них ненулевая
    длительность: момент начала следующих суток строго позже момента
    начала этих. Для пропущенного дня оба локальных полуночных значения
    отображаются в один и тот же момент UTC.
    """
```

Реализация — O(1), без перебора часов:

```python
start = _utc_of_local_midnight(local_date, tz_id)
end   = _utc_of_local_midnight(local_date + timedelta(days=1), tz_id)
return end > start
```

где `_utc_of_local_midnight` разрешает полночь через
`resolve_historical_tz` и, при аномалии, через `resolve_anomaly`.

Проверка на контрольных значениях:

```text
local_date_exists(date(2011, 12, 30), "Pacific/Apia")       → False
local_date_exists(date(1994, 12, 31), "Pacific/Kiritimati") → False
local_date_exists(date(1967, 6, 3), "Africa/Casablanca")    → True
local_date_exists(date(1920, 2, 14), "Africa/Algiers")      → True
local_date_exists(date(1990, 9, 2), "Europe/Moscow")        → True
```

Функция экспортируется из `exact_orb.birth.tz` и из публичного
`exact_orb.birth.__init__`.

### 1.4. Новая ветка в `BirthDataResolver.resolve`

Проверка ставится **до** разбора исхода `resolve_historical_tz`
и действует в обеих ветках — и при известном времени, и при неизвестном:

```text
5.  tz = resolve_historical_tz(local_datetime, place.tz_id)

5a. if isinstance(tz, TzNonexistent) and not local_date_exists(birth_date, tz_id):
        return InputRequired([Issue("birth.date", INVALID)])

5b. далее как раньше: TzOk / TzNonexistent / TzAmbiguous
```

**Почему и при явно указанном времени тоже.** «Родилась 30 декабря
2011 года в Апиа в 14:00» — здесь неверна не только величина времени,
а сам день. Вернув `InputRequired { birth.time }`, мы отправили бы
человека исправлять поле, в котором ошибки нет, и он мог бы подобрать
любое время, ни одно из которых не существовало.

Правило не нарушает ADR-0008: мы спрашиваем про поле, которое человек
заполнил сам, и не спрашиваем про подставленный полдень.

## 2. Удвоение времени: отдельный код предупреждения

### 2.1. Что не так сейчас

Выбор `fold = 0` детерминирован и правилен, но кандидаты бывают разнесены
почти на сутки:

```text
Кваджалейн 1969-09-30, смещения +11:00 и −12:00 — 23 часа между вариантами
  fold=0 (выбрано) : Луна 58.379° Taurus
  fold=1           : Луна 70.326° Gemini      ЗНАК МЕНЯЕТСЯ
```

Предупреждение `noon_anchor_adjusted` с текстом про «valid local time»
не сообщает, что знак Луны под вопросом. ADR-0008 требует предупреждать
именно об этом: «предупреждения добавляются при смене знака Луны».

### 2.2. Что сделать

Разделить один код на два — по причине, а не по факту подстановки:

```text
несуществующий якорь  → noon_anchor_adjusted
                        "Noon anchor moved to <HH:MM[:SS]>, the nominal
                         noon did not exist in <tz_id>"

удвоенный якорь       → noon_anchor_ambiguous
                        "Noon anchor is ambiguous in <tz_id>:
                         offsets <o0> and <o1>; the earlier instant
                         (fold=0) was used"
```

Оба несут `source="time"`. Смещения печатать в человекочитаемом виде
(`UTC+11:00`, `UTC-12:00`), но код остаётся машинно-проверяемым — по нему
рецепт смягчает утверждения о Луне.

Время нормализации печатать как `HH:MM`, если секунды нулевые, и как
`HH:MM:SS`, если секунды ненулевые: например, Havana нормализуется
в `12:29:36`.

Поле `details` в `ResolutionWarning` **не добавлять**: различающего кода
достаточно, а расширение контракта потянуло бы правки в документах
компонентов и в ADR-0005.

**Это не закрывает вопрос целиком.** Полноценная защита — проверка смены
знака Луны в пределах суток на стороне движка (ADR-0008, до сих пор
не реализована). Здесь мы даём рецепту сигнал, а не измеряем риск.

## 3. Устойчивость `LocalPlaceCatalog.from_file`

### 3.1. Пустые строки роняют загрузку

```text
{"place_id":"1",...}\n\n   →   ValueError: Invalid JSON on line 2
```

Скрипт `build_place_catalog.py` пустых строк не пишет, но конкатенация
двух каталогов, ручная правка или редактор с автодобавлением перевода
строки — и приложение не стартует. Пропускать строки, пустые после
`strip()`.

### 3.2. Ошибка схемы без номера строки

```python
canonical_name=record["name"]      # KeyError('name'), и всё
```

Структурно валидная строка без обязательного поля даёт голый `KeyError`
без номера строки и имени файла. Это происходит на старте приложения:
обрезанный или переименованный экспорт GeoNames даст загадочную ошибку
вместо «строка 4123: нет поля name».

Обернуть построение записи так, чтобы `KeyError`, `TypeError`
и `ValidationError` превращались в `ValueError` с номером строки
и именем недостающего либо неверного поля — тем же способом, что уже
сделан для битого JSON.

## 4. Мёртвая ветка с неправдивой ошибкой

```python
raise UnknownTimezoneError("normalized local time is still anomalous ...")
```

Прогон **9 168 768 локальных моментов** по всем зонам IANA вокруг всех
переходов за 1800–2100 не дал ни одного случая, когда нормализованное
время снова аномально. Ветка недостижима.

Проблема не в её наличии, а в типе: `UnknownTimezoneError` для зоны,
которая прекрасно известна. Резолвер ловит его и возвращает
`error_code="UNKNOWN_TIMEZONE"` — ложь о причине.

Заменить на `RuntimeError` с внятным текстом (это внутренний инвариант,
а не пользовательский или конфигурационный случай) и **не ловить его
в резолвере**: пусть всплывает как внутренний сбой. Резолвер продолжает
ловить только `UnknownTimezoneError` от `_load_zone`.

## 5. `pre_1970` проверяется не по той величине

Гарантия IANA сформулирована относительно POSIX epoch, то есть
**1970-01-01 00:00 UTC**. Сейчас проверяется локальное время:

```python
if local_datetime < PRE_1970:
```

Окно расхождения равно смещению зоны и случается один раз в истории
каждой зоны, так что практического вреда почти нет. Но проверяется
не та величина, и это стоит одной строки: сравнивать
`utc_datetime` с `datetime(1970, 1, 1, tzinfo=timezone.utc)`.

Следствие: в `resolve_historical_tz` предупреждение ставится после
вычисления `utc_datetime`, а в `resolve_anomaly` — по вычисленному
там же моменту.

Заменить naive-константу на aware:

```python
POSIX_EPOCH = datetime(1970, 1, 1, tzinfo=timezone.utc)
```

## 6. Две мелочи

**`assert place is not None`** вырезается под `python -O`, после чего
`place.latitude` даёт `AttributeError` на `None`. Ветка недостижима
по построению, но `assert` — не тот инструмент для инварианта, от
которого зависит следующая строка. Переписать так, чтобы `place`
получался в ветке, где он заведомо есть, без утверждения.

**`self._places.get(place_id) or PlaceNotFound(...)`** работает только
потому, что pydantic-модель истинна. Достаточно кому-то добавить
`__len__` в `ResolvedPlace` — и найденное пустое место превратится
в `PlaceNotFound`. Заменить на явную проверку `is None`.

**Ограничения.**

- Не менять сигнатуру `BirthDataResolver.resolve` и состав
  `ResolvedBirthData`.
- Не расширять `ResolutionWarning`.
- Не менять правило `fold = 0` и не делать выбор конфигурируемым.
- Не трогать `cli.py`, `engine/`, `tools/`, `orchestration/`.
- Не отменять существующие тесты: из 73 меняется только то, что прямо
  следует из правок (коды предупреждений при удвоении). Все остальные
  обязаны остаться зелёными без изменений.
- Не реализовывать проверку смены знака Луны в движке — это отдельная
  задача по ADR-0008.

**Критерии приёмки.**

1. Весь существующий пак проходит; изменились только те тесты, где
   поменялся код предупреждения при удвоении.
2. `local_date_exists(date(2011, 12, 30), "Pacific/Apia")` — `False`,
   `local_date_exists(date(1920, 2, 14), "Africa/Algiers")` — `True`.
3. Резолвер на Апиа 2011-12-30 **без времени** возвращает
   `InputRequired` с `field == "birth.date"`, `code == "INVALID"`.
4. Резолвер на Апиа 2011-12-30 **с временем 14:00** возвращает то же
   самое: `birth.date`, а не `birth.time`.
5. Резолвер на Касабланке 1967-06-03 без времени по-прежнему возвращает
   `ResolvedBirthData` с `noon_anchor_adjusted`.
6. Резолвер на Кваджалейне 1969-09-30 без времени возвращает
   `ResolvedBirthData` с кодом `noon_anchor_ambiguous`, и в тексте
   предупреждения присутствуют оба смещения. Набор warning-кодов
   не обязан состоять только из него: дата pre-1970 также даёт
   `pre_1970_offset_unverified`.
7. `LocalPlaceCatalog.from_file` загружает файл с пустыми строками
   в середине и в конце.
8. Строка без `name` даёт `ValueError`, в тексте есть номер строки
   и имя поля.
9. `resolve_historical_tz(datetime(1970,1,1,2,0), "Europe/Moscow")`
   несёт `pre_1970_offset_unverified`: в UTC это 1969 год.
10. `resolve_anomaly` не поднимает `UnknownTimezoneError` для известной
    зоны ни при каком входе.
11. `grep -n "assert " src/exact_orb/birth/` не находит утверждений,
    от которых зависит следующая строка.
12. Запуск пака под `python -O -m pytest` даёт тот же результат.
    Это smoke-проверка поверх точного AST/grep-критерия из пункта 11.
